# Ownership is read live, and claim acts on it

linear decided ownership from a fixed table: each area had its named owners (data and integrations, compliance, maintenance, prompts and evals). The owner pointed out the table describes who was working on each area when it was written, not who owns it now: an owner is whoever is working on that project at the time. The owner also asked for one flow when `/triage-and-implement` has no ticket: linear reads the board, claim triages each ticket's owner and either DMs them directly in plain words or assigns the ticket to the owner, and triage-and-implement does the work.

## Decision

- **A new skill, claim, owns the per-ticket rules and the verdict**: team, assignee, in flight, and **owner now**. linear keeps only the board list and reads the rules from claim's file, so they live in one place.
- **Owner now is read from activity in the last 30 days**: the Linear project (lead, working rules in its description, who holds its tickets), the code paths (`list_commits` by path on `develop`, open PRs), and the ticket (creator, delivery line, comments). An In Progress, In Review or In Testing ticket, an open PR in the same code, or most of the area's changes in 14 days makes someone the owner; three or more commits, a project lead at work there, a split area or a fresh comment makes it "ask first"; a commit or two is history. The owner's own ticket or PR (the dashboard's owner, not an owner-now) is ours outright. A **covering ticket** comes first (added 5 Oct 2026, from a linear scan run): another open ticket whose description shows it finishes this one, such as a port of a Labs fix. When someone holds it, its state decides (in progress means theirs, To do or Backlog means ask first) and its holder is the one person asked, because the author of the code being ported has handed the work on; commit counts would name the wrong person. Commits count by **feature**, not file (5 Oct 2026, from two runs), since hub files such as `domain-call-list.tsx` are edited by six people for unrelated features; and the owner's own follow-up in a project the owner leads is ours. The product pair do product work, PRs in a restricted scope (5 Oct 2026): they are asked product questions only, never named owners of build work, except that prompt and eval changes stay with their fixed owners, one of the pair among them, building included: a fix that changes a prompt's instructions or the evals, not one that brings data into a prompt.
- **claim acts**: ours is assigned to the owner and moved to In Progress; an owner-now result DMs the people found, at most two, and nobody when anyone was asked about the ticket in the last 14 days, in a Slack DM or, since 5 Oct 2026, in a comment on the ticket (a DM conversation is followed up instead, and a comment's answer is reported). The DM leads with a TL;DR and follows ASD-STE100 style (short sentences, active voice, common words). A "dry run" shows the DM without sending it.
- **Every DM is followed up to a conclusion.** claim is one-shot, so its answer hands the caller a follow-up line, and the caller runs a 1-minute `CronCreate` loop (claim's FOLLOW-UP.md, in the org's extension) that reads replies, answers in the same style, and concludes: theirs, ours (assigned to the owner), passed on (the named person gets a DM and a loop), needs the owner, or no reply after 60 minutes. At most three replies per conversation. The owner asked for this on 5 Oct: a DM starts a one-minute loop that converses to a conclusion.
- **Each DM says an agent wrote it** ("Sent by Claude for the owner"), since it and the follow-up replies go out from the owner's account.
- **claim is forked with two writes open**: its `disallowed-tools` is linear's list with Linear's `save_issue` and Slack's `chat_post_message` left out (every other Linear save tool named one by one, since the `save_*` glob would close `save_issue`). `tests/test_skill_frontmatter.py` pins that difference.

## Consequences

- DMs go out in the owner's name without review: the one exception to drafting Slack messages for the owner to send. A wrong read DMs the wrong person; the 14-day check and the two-person cap bound the noise.
- `save_issue` can also create issues or change other fields; claim is told only to assign and set In Progress, which is an instruction, not a block.
- linear runs slower, since owner now reads a project and a code history per ticket.
- The blocklist names today's Linear save tools one by one, so a save tool Linear adds later is open in claim until it is named; and `chat_post_message` can post to any channel, so keeping it to DMs is an instruction, not a block.
- A pass-on can add a third person to a ticket's conversations; it is allowed once per ticket, after which the loop hands it to the owner.
- The follow-up loop runs in the caller's session, not the fork, so its replies and its assignment sit outside the fork's two-write limit and are bounded by FOLLOW-UP.md alone.
