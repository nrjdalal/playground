- herdr is the terminal, where Playground runs its sessions and the dashboard reads, writes to and answers every one.
  The Feed's answer shapes (`FeedReply`, `PERMISSION_MODES`, `PLAN_MODES`) live in `api/hono/src/lib/dashboard/feed.ts`.
  Outside the dashboard, the factory's `playground picker` answers a permission prompt through its session's herdr pane alone (playbook's SESSIONS.md).
  The dashboard's answer to a prompt is confirmed by the NeedsYou card's Submit (`feedNeeds()` in `web/next/src/lib/needs-you.ts`), which shows a permission's whole input and a plan's text above the choices, and offers only refusing when not all of one could be shown.
  What that Submit says while off is `submitWhy()` in the same file.
  The dashboard's permission and plan answers approve another session's actions, so they go only while `PLAYGROUND_APPROVALS_ENABLED` is on (off by default), and who may answer at all is `canApprove()`, to narrow once the owner picks a login only they can use.
  The answer route sends a prompt from the session the dashboard hosts on the Agent SDK to `answerHosted()` in `sdk.ts` (messages.md), under the same two checks, and answers every other by keys into its herdr pane (the herdr rule below).
  A new kind of write (closing a worker) arrives with a confirmation in the UI; when a session ends, and who closes it, is playbook's Lifecycle.
- ALWAYS: Route every herdr call through `api/hono/src/lib/dashboard/herdr.ts`, the terminal the dashboard reads every session from.
  `listLive` reads herdr's servers alone, so a session another terminal runs never shows, opted in or not; on a stack that has not opted in with `PLAYGROUND_ALL_SESSIONS`, `/api/health`'s dispatcher slots also count the roster's names alone, never the registry's,
  which names every session on the machine (`readDispatcherSlots()` in `workers.ts`).
  A stack that reads this machine reads each server `PLAYGROUND_HERDR_SESSIONS` names (`playground,playground-probes` by default, plus every other server socket in that folder, such as an older Playground's `factory` and `probes`, while the variable is blank) at `<PLAYGROUND_HERDR_DIR>/<name>.sock` (else `herdr` in the data folder, `~/.playground`,
  following `HOME` and never `CLAUDE_CONFIG_DIR` or `PLAYGROUND_DATA_DIR`, where ops-herdr serves them, so a session on another login reads the same servers);
  a fixture stack reads herdr alone, the fixture's own `playground` server, answered from its `herdr.json` on no socket (`FIXTURE_SOCKET` in `herdr.ts`), so its board, Feed and session rows are herdr panes; a server that is not running is skipped.
  A server holds its socket alone: a second `herdr server` on the same `HERDR_SESSION` and socket exits 1 (`herdr server is already running`) whether the first answers or hangs, and the first keeps its socket (herdr 0.9.5, measured), so a read that times out never double-starts a server and needs no guard.
  Every board takes a fresh `session.snapshot` and each pane's `pane.process_info` (a whole server of 30 panes in about 4 ms, measured, its panes asked one after another, since 30 asked at once took about 100 ms), with no pacing and no cache, inside one 3 s deadline a server (`readServer()`),
  so a server that is up but whose read fails (it hangs past the deadline, refuses, or answers what does not parse) is kept as an empty read marked `partial` and named rather than holding the board,
  and turns its panes into session records (`herdrRecords()`) before any read, so `liveRecords()` proves each.
  A pane whose processes did not answer whole marks its server's read `partial` too, and `listLive()` carries either as `Live.partial`, so a session missing from a cut-short read is never taken for ended (asks.md's relay rule).
  Its cost: while a server keeps failing, every send that misses its name reads fresh twice and then refuses `SESSIONS_FAILED`, an ended poster's relay included, until that server reads whole.
  A pane holds a session only when a foreground process has a registry file naming it, or herdr's own `agent_session` id while the registry cannot be read or that file is mid-rewrite (`herdrRecords()`); a pane with neither is no session, so only a roster agent paired with it reads Down; its surface is `herdr:<server>:<pane id>` and its workspace `herdr:<server>:<workspace id>`.
  Codex writes no registry file, so a pane whose label has a Codex launch record (`codexLaunches()`: a `codex openai` pin, and the thread its resume record's exec line names) and a `codex` process in its foreground holds that thread as an `agent: "codex"` record.
  Its state is herdr's `agent_status` first (blocked waits on a person, working runs, idle and done wait), then the C5 hook file (`@packages/config/session-state`) where herdr reports unknown and for a usage limit and its reset, and a stuck record `stateNow()` reads as past (an Escape fires no hook) ends herdr's blocked too (`herdrState()`),
  while it is no older than the blocked state this process saw begin, less 30 s, since a session restored without its settings (by herdr's own resume, which ops-herdr's config now turns off for `spawn.sh restore`) writes no new record and its file keeps an older one; a failed or usage-limit record never ends it.
  A start counts as seen only when the read before it was within 30 s, since the hub reads only while a Dashboard is open, and a read further from the last than that takes its state as begun at that read, as a fresh process does, since a picker answered and a permission raised between them both read blocked, and the older start would read the new prompt as answered;
  a board that leaves a server unread (a failed read) keeps that server's times; with none seen (the dashboard restarted, or its reads paused, while the prompt was up), any stuck record ends it, so a restored session's stale record can read its new prompt as idle until its next.
  The hub runs `herdrEvents()`: one subscription a server, opened afresh from a new snapshot on an error frame (`events_lost`, or a subscription herdr refuses, more slowly each time), on a pane opening, exiting, closing or moving, and when a server goes and comes back, each refreshing the board.
  An event frame names its kind as herdr's EventKind (`pane_created`, `pane_exited`, `pane_closed`, `pane_moved`), while a subscription asks by dotted name (`pane.created`), and a subscription given up says nothing more, so one stays open a server.
  Every request goes out whole (`lineWriter()`), since a unix socket on macOS takes at most 8 KB a write.
  A screen read (`terminal.ts`) takes `visible` alone and refuses a pane scrolled up, or one whose `pane.get` answer does not read; a null `scroll`, which herdr's schema allows and no live pane showed, reads as at the bottom.
  A herdr session has no Feed, so while herdr reads it blocked its prompt shows as a card: `herdrFeed()` in `workers.ts` builds a Feed item from the transcript's open call that raised it (factsIn's `calls`), picked by its hooks' stuck record (`herdr_wait`: a question is the open AskUserQuestion, a plan the open ExitPlanMode, a permission the open call of its tool),
  else the newest open call.
  A subagent's prompt, an elicitation or a login gets none, and shows as Stuck alone.
  herdr 0.9.5 has no call that answers a prompt, so a picker card's Submit answers it by keys; the answer is the owner's own Submit, the same contract as deliver() for the composer, so **voice** holds.
  The answer route hands it to `answerHerdr()` in `feed.ts` past `answerFeed()`'s guards, and its comment tells the procedure whole: it types nothing unless the pane shows the question the card shows, its words over its options (`showsAsk()` in herdr.ts; else `NOT_PENDING`), commits the attempt's `dashboard.answer` row before the first key,
  and reads `INTERRUPTED` while the question still shows after the keys.
  A herdr session's permission or plan card stays read-only, its footer pointing the owner to the chat (a dispatcher's own card names its terminal, since no manager answers it),
  and the route refuses it (`TERMINAL_ONLY`) whatever `PLAYGROUND_APPROVALS_ENABLED` says: those approve actions, and five review rounds of matching a card to the pane's permission box each found a way to approve the wrong call, so that matching waits for its own change,

- ALWAYS: Count a session record as live only through `liveRecords()` (`isLiveRecord()` in `api/hono/src/lib/dashboard/workers.ts`), which `listLive` applies to herdr's records before any read, then drops the transcript reads kept for sessions it no longer holds;
  it returns the branded `LiveRecords` that `composeWorkers` and the transcript reads require, so an ended session never reaches a row, a light, a picker or a needs-you count.
  A Codex record is live on the read that found its `codex` process in its pane, since it has no registry file to prove it by; every other agent's is never live.
  A pid alone proves nothing, since macOS hands a freed pid to the next process that starts (an ended `greed` once read as a red Waiting on you).
  Claude's registry file at that pid (`$CLAUDE_CONFIG_DIR/sessions/<pid>.json`, read once per refresh by `readRegistry()` in `peers.ts`, which every registry reader builds on) is written while a session runs and removed at a clean exit, but a crash leaves it.
  So the record is live when that file names its session id and its `procStart` equals the pid's start now (`processStarts()`, the probe's `ps -o pid=,lstart=` under `LC_ALL=C TZ=UTC`); a `procStart` in any other shape is dropped, so a change to how Claude writes it leaves the session id to decide rather than reading every session as ended.
  A file that does not read whole (Claude rewrites it in place) leaves the record's own word for that pid, and so does a session whose transcript is under another Claude config's projects folder, whose registry is not this one.
  A registry that cannot be read at all falls back to the record's own word, and the System panel names that fallback in `problems`; when ps cannot be run, the file's session id alone decides.
  Every board reads herdr's servers, the registry and the transcripts afresh, so a prompt shows and an ended session leaves on the next board.
  The hub runs one refresh at a time, starts at most one a second (`REFRESH_GAP_MS` in `hub.ts`), and gives up on a read after 8s with an error frame but starts no new one until it settles, so slow reads never stack.
  The hub tails each live transcript on `fs.watch`, and every refresh, the 10s safety one (`SAFETY_REFRESH_MS`) and one whose sessions read fails included, reads each open tail again from its offset, since FSEvents drops change events under load (`.agents/testing.md` holds the measure), so a line whose event was lost reaches the board within one refresh and none is sent twice.
- ALWAYS: Run the System panel's commands only through `api/hono/src/lib/system/probe.ts`, which the dashboard's start-time read (`starts`) shares: `COMMANDS` holds each one's fixed argv (`sysctl`, `vm_stat`, `ps`, `lsof`, `docker ps`, `docker stats --no-stream`, `docker context inspect`), all reads run without a shell, and `commandOf()` lets a probe take only a whole-number uid,
  a non-empty list of whole-number pids or an absolute socket path.
  `memory_pressure` stays off the list (its `-l` simulates pressure, and `kern.memorystatus_level` is the free share it prints), and `sysctl` is never handed a `name=value`.
  `tests/api/hono/src/lib/spawn-allowlist.test.ts` fails when a file outside those it names starts a process anywhere under the api's `lib/`, so a new reading arrives as a `COMMANDS` entry.
