- The live dashboard follows the branch its repo's main checkout sits on: an install clones `main`, so it follows `main`, and a developer who wants `canary` keeps their main checkout on `canary` (`scripts/ops/dashboard/upstream.sh` reads it, any other branch reading as `main`).
  It runs that branch's latest head on `origin`, never one off hashes, branches or worktrees, and only rolls forward: a head the running one already holds (`main` behind a checkout that rolled on `canary`) waits, logged once, until the branch passes it.
  Each git call that reaches `origin` goes through `net-git.sh`, with no prompt and no credential helper and stopped after 20 seconds, so a hidden keychain prompt costs one logged line and the head stays.
  Its checkout stays on the branch `live.branch` names (`live/dashboard` by default), since the source rule and portless need that name, and ops-dashboard's supervisor (`scripts/ops/dashboard/supervisor.sh`) rolls it.
  On each move of that branch it stops the stack, resets `live.branch` to its head (`redeploy-pull.sh`), installs, builds `packages/*` or migrates as the move needs, restarts each ops job whose source the move changed (`scripts/ops/README.md`), builds the head (`build_head`), serves that build and starts the follower, and runs `bun run verify`.
  The stack is a production build, never `next dev`: `bun run build`, run with `NEXT_PUBLIC_APP_URL` and `NEXT_PUBLIC_API_URL` set to the URLs `portless get` names, since next bakes them into its client, is copied to `ops/dashboard/builds/<sha>` (next's standalone server with its static files, and the API's `bundle/`, whose `main.mjs` holds first run's setup mode),
  and `bun run serve` serves it (`PLAYGROUND_BUILD`), the launcher's same checks run first.
  A head's build is made once and kept; one made for other URLs, as when portless's proxy moves, is built again, with one `supervisor.log` line naming both.
  Each pass keeps its own build and the last one that passed before it, so a fallback serves the head before's build without building it again; `playground update` reads a roll as Building… until its `built <sha7> in Ns` or `dev started` line, so the build's minutes never read as a failure.
  Its verify runs health and map, plus signin, ws and system where the checkout's `.env` turns `AGENT_SIGNIN_ENABLED` on, since those three sign in as the agent and a person's checkout keeps that off.
  A roll waits `ROLL_GAP` (30 minutes) after the last one and for `OWNER_IDLE` (5 minutes with no dashboard message), batching what lands meanwhile, or `ROLL_GAP` alone when the owner's idle cannot be read while the dashboard's Postgres container runs, holding while it is down; a file named `roll-now` in its state folder (`ops/dashboard`) skips both holds:
  `playground update` writes it, and with nothing to roll to it is answered in `results.log`, `CURRENT <sha7>` or `SKIP <sha7> FAIL` for a head in `bad-builds`, and removed.
  The dashboard's Postgres container is the one running container that publishes the dashboard checkout's `POSTGRES_URL` port on loopback alone, whatever its name, the rule `bun run ingest` proves (`api/hono/src/bin/dashboard-db.ts`, run with the dashboard checkout's own code and `.env`).
  The supervisor reads it for the owner's idle and the up or down hold, looks it up again before each stop, and writes each lookup's name (empty for none) to `dashboard-db` in its state folder, where `procs.sh`'s drain reads it; a lookup that fails reads as down and logs its reason once in `supervisor.log`.
  A head whose roll fails, its pull's install or build or its own build (`FAIL build: <error>`) included, is kept in `bad-builds` and never rolled again, and the dashboard falls back to the head it ran before (never after a migration, which it leaves for Ops; a pull that failed after a migration leaves the stack down until the loop's dev check restarts it).
  A roll that `bun run dev` refused to start (its dev log's reason, as `dev_reason` reads it, is a `dev: refusing to start:` line) falls back the same way and writes its own `FAIL dev refusing: <reason>` result, but it is no bad build.
  Only the settings refusal counts (`the API's settings could not be read`, the head's env schema asking for what `.env` lacks): it is counted by head in `refused` in the state folder, its third listing the head in `bad-builds`.
  Every other refusal is the machine's or the checkout's (cmux, the database, another stack, portless's proxy), so it stays uncounted and the roll is tried again after the holds.
  A pull that fails before it reaches the head, such as a fetch that cannot reach GitHub, writes an `ANOMALY` result, which `playground update` reports as a failure, restarts the head the dashboard was on, and leaves the roll to the next one, after the holds above or a `roll-now`.
  A roll that changes `scripts/ops/dashboard/` runs that head's own `run.sh` and `supervisor.sh` with no hand restart: the supervisor writes the roll to `reload` in its state folder and exits 75 with the stack down, `run.sh` execs the checkout's `run.sh` in its own pid, and the new supervisor starts the stack once and checks it.
  When that roll fails, the new supervisor lists the head in `bad-builds` (a refused one by the count above) before it falls back, so the head it falls back to starts on its own code and keeps off the failed head.
  `jobs.json` runs ops-dashboard from the dashboard's checkout, its own `run.sh` (`{dashboard}` in `packages/settings/src/jobs.ts`), and a start from a `run.sh` outside that checkout hands on once the same way to the checkout's own copy, so ops-dashboard always runs the `scripts/ops/dashboard/` of the head the dashboard is on, canary's rather than main's.
  It restarts the follower only when `bun run ingest status` finds no follower running: a follower it did not start is left running, and a status read with no answer in `HELD_WAIT` seconds (20) leaves the follower as it is, each named once in its log.
  Until first run's setup writes `POSTGRES_URL` into the checkout's `.env`, it leaves the follower stopped, names the wait once in `supervisor.log` and counts it no failure (a roll's line reads `follower=waiting for first run's setup`); the first check after setup writes it starts the follower and writes `START follower` to `results.log`.
  Writes stay on: it is the owner's own dashboard.
