- ALWAYS: Verify dashboard work with `bun run verify` (`--help` lists its checks) rather than a script of your own: a worker before it opens or updates a PR, the reviewer before it scores one, a runner after it restarts a stack.
  With no check it runs `all`.
  With no URLs it checks this worktree's stack; for the live dashboard, read-only, run it from the dashboard's checkout (on branch `live.branch`, so portless names its stack `dashboard.playground` and `dashboard.api.playground`) with no URLs and `--expect <live.branch>` (its checkout runs `origin/canary`'s latest head, `.agents/dashboard/live.md`).

- ALWAYS: Keep the dashboard map current.
  `packages/scripts/src/verify/dashboard-map.json` lists every page under `(protected)` with what it shows, how to reach it and the API routes behind it, the sidebar's groups, and any owner-rung API route no page calls: read it first to place a vague report (a cropped screenshot, a page's name).
  A change that adds, moves or removes a dashboard page, a sidebar group or an owner-rung API route updates the map in the same PR; `bun run verify map` and the map's test in `bun run test` fail until it does.
  A sidebar group label written as text is read as that text, and one rendered from an expression (`{label}`) in a file that imports `@/lib/dashboard` as each group `GROUP_ORDER` there lists, never from other `label:` literals in reach; any other expression label is reported.
  A page's `shows` is a list, one entry per feature, sorted A to Z: a new feature is a new entry in its sorted place, so two PRs adding features to one page usually touch different lines and merge with no conflict (two that sort into the same place, both to the end, two edits to one entry, or a list short enough that the formatter keeps it on one line still conflict),
  and both checks fail on a list out of order.
