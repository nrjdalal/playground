# code-review-loop

One reviewer session per PR scores it out of 5, round by round, until nothing but nits is left to change. Every round is a **subscription** kept by the session: each push gets a round, each finding stays open until a round sees it fixed, and each thread you opened you close. The method on two axes is core's `code-review`, loaded by name; this skill adds the score, the gate's verdict line, the rounds and the threads.

`${CLAUDE_SKILL_DIR}/scripts/state.py` reads a PR's state from GitHub and git each time it runs, with no memory of its own, so a round never rests on what the session remembers. `<repo>` is `owner/name` (`acme/app`), `<clone>` your review worktree, `<n>` the PR and `<branch>` its branch. Every reviewer posts from the same account, so the verdicts on a PR are one history: its rounds count on across reviewers, and the newest verdict is the PR's, whoever posted it.

Your brief names the PR, the worker you report to and your worktree. A work-org PR's review worktree goes in its repo's checkout under the work org's folder (`~/<org>/`), or in your scratchpad when there is none, outside the Desktop folder, which macOS privacy refused for sessions under herdr on 22 Oct ("Operation not permitted"), stalling every review there, while the clones under that folder kept working. Local CI is GitHub Actions' `Audit, Lint, and Build` and `test` green at the head, which the Builder's go starts and ops-checks-go stamps (The last 5/5). Run your checks one after the other, never in parallel in one clone: `bun run test` rebuilds `packages/*`, which a parallel `check-types` then cannot find. A clone whose `node_modules` came from `~/.playground/ops/run-slot.sh <your session name> -- cp -cR <sibling>/node_modules <clone>/` holds the root folder alone, so run `~/.playground/ops/run-slot.sh <your session name> -- bun install --ignore-scripts --cwd <clone>` before any check, adding `--force` when the copy printed any error; the `no-unslotted-run` hook refuses either outside run-slot. Before a fresh clone's first check, copy its `.env.example` to `.env`, set `POSTGRES_URL` (a loopback URL; nothing connects to it) and `BETTER_AUTH_SECRET` (`openssl rand -hex 32`), since `bun run test`'s package build checks both. Then run `~/.playground/ops/run-slot.sh <your session name> -- bun run check-types` first, which builds `packages/*`, since a `bun run test:file <files>` run before any build fails on `Cannot find module @packages/...` (`bun run test` builds them itself). A work-org PR keeps to the **classified** rule in every comment: the verdict line and the `ReviewBot` signature are the only names a comment carries.

On a colleague's work-org PR whose review ask came to the owner, the session that posts the review sends the Reply when the owner reviews from triage-and-implement's PR.md (the work org's extension skill, its folder from `playground ext which triage-and-implement`) right after posting.

## Each round

1. **Recover.** Check out the round's head in `<clone>` (`git -C <clone> fetch origin <branch>`, then `git -C <clone> checkout --detach <head>`; a round that needs a fixture stack takes `git -C <clone> switch -C review-<n> <head>` instead, since the dev skill's branch rule refuses a detached HEAD), since `code-review` reviews the clone's `HEAD` either way. Run `${CLAUDE_SKILL_DIR}/scripts/state.py pr <repo> <n>`, then read every comment, review and thread reply it lists as said since the newest verdict, and every open thread it lists, anyone's, before you write a word. On your own first round, read the PR's whole history instead (`gh pr view <n> -R <repo> --comments`), resolved threads included: the reason a thread closed is the best account of what the author already tried. Compare each one's time with the head's: a review written before the head speaks for an older commit. A PR that reads `MERGED` or `CLOSED` gets no round: tell your worker. On a dependency or CVE bump, run triage-and-implement's **duplicate** check (its phase 8, in the extension), its search and its lockfile diff, in the PR's repo first; a bump that phase 8 calls the duplicate gets no round: tell your worker. A finding another reviewer or a person made counts as open until a round sees it fixed. A lead's ruling (a comment whose first line starts `Lead ruling:`, playbook's **gate**) supersedes the FAIL it names, the newest ruling winning: count that FAIL's fault as moved once `gh api repos/<repo>/issues/<issue>` shows the issue it names exists, and as open while it does not. When `state.py pr` prints `GraphQL spent`, it read over REST: count each thread whose resolution reads unknown as open until the reset, and, since that read prints only each comment's first line and `gh pr view` is GraphQL too, take a first round's whole history from `gh api repos/<repo>/issues/<n>/comments`, `pulls/<n>/reviews` and `pulls/<n>/comments`. **Done when** `<clone>` is at the head and you can name the head, the SHA the newest verdict scored, every open thread, every finding still open from anyone, and, for a bump, the duplicate check's result.
2. **Place the push** (round 2 on). Run `git -C <clone> fetch origin canary`, then `${CLAUDE_SKILL_DIR}/scripts/state.py delta <clone> origin/canary <last scored sha> <head>`. It reads `OWN` for any commit of the PR's own in the push, and otherwise compares the PR's own changed lines on each side, since a path-scoped range diff across a merge of `canary` shows `canary`'s work as the PR's; context lines and hunk positions are left out, so a conflict resolved by hand that kept both sides reads `BASE-MERGE` too. For a stacked PR whose base squash-merged into `canary` since the last scored SHA, place the push by VERIFY.md's **Read a stacked PR's own lines** instead, since `delta` reads that whole base as the PR's. `BASE-MERGE`: when the merge is not clean, read each resolution (`git -C <clone> show --remerge-diff <merge>`), check the merge's conflict resolutions and every new `run(`, `Bun.spawn` and `claude_*` query it brought in against the fixture guards, then go to step 6 with the PR's standing score; a standing 5/5 is still a **candidate** there, so it runs The last 5/5's fresh full read and check-types at the new head before it posts (on one PR, round 2 posted 5/5 at a merge head with neither). `OWN: <files>`: read the PR's own commits since the last scored SHA (`git -C <clone> log --no-merges -p <last>..<head> ^origin/canary`, since without `^origin/canary` a merged `canary`'s commits list as the PR's), and each merge commit in that range by its own resolutions (`git -C <clone> show --remerge-diff <merge>`). A `--remerge-diff` hunk in a file outside the merge's Conflicts list (`git -C <clone> merge-tree --write-tree --name-only <parents>` names the same files) is an edit made inside the merge, not a resolution: score it blocking, since pr:merge's keeps-canary gate refuses the squash when the hunk drops a line `canary` added, and name the fix its README gives, redoing the merge plainly and putting the edit in a commit of the PR's own. The case is one PR's c45138e: stale.ts merged cleanly, yet that merge changed `canary`'s `kind` line. **Done when** every own commit since the last scored SHA is read, and every merge's hunk outside its Conflicts list is scored, or the push is shown to be a base merge.
3. **Read the spec.** Gather what was asked into one file in your session's scratchpad: for a Playground PR, the issue it closes (`gh issue view <n> -R <repo>` for its `Closes #<n>`, its "Done when"), the worker's brief (ask your worker for its path when your brief does not give it) and the ask the PR body states; a row edited after the head was pushed is the spec still, with the edit named in the verdict; for a work-org PR, the Linear ticket and every comment on it, since a lead's comment often holds the requirement, and its status: a PR still open against a Canceled ticket is a finding. **Done when** the file lists each "done when" item and each stated fix direction as its own line to check, each sample the ticket carries (emails, files, payloads) as its own line too, and, for a work-org PR, the ticket's status.
4. **Review on two axes.** A stacked child takes [VERIFY.md](references/VERIFY.md)'s **Read a stacked PR's own lines** alone (VERIFY's `<base ref>` is the parent's branch, whatever the child's GitHub base): its fixed point, its push delta and its base after the parent lands are that section's, by the PR's state there, so the `canary` formulas in this step never read the parent's lines as the child's, and a stacked child that fails playbook's stack test (DISPATCH.md's bundles) is a blocking finding. When the diff changes an agent-facing doc (a `SKILL.md` or its sibling files, `AGENTS.md` or `CLAUDE.md`, an `.agents/dashboard` rule, `scripts/README.md` or `scripts/hooks/README.md`, a `docs/<bucket>/<name>.md` page; playbook's **writing** rule), call the Skill tool with `writing-for-agents` once a session, before the first such judgement, and judge each changed one against it on Standards, a Playground docs page against `.agents/writing-docs.md` too; a PR body is not one. Round 1 and every 5/5 candidate (below): call the Skill tool with `code-review`, passing the fixed point (`git -C <clone> merge-base origin/canary <head>`), the spec file's path (so its issue-tracker setup does not apply) and [VERIFY.md](references/VERIFY.md)'s path for its sub-agents to check findings by; as standards sources it takes `AGENTS.md`, every `.agents/dashboard/<topic>.md` whose area the diff touches (AGENTS.md's dashboard pointers name each one's area), `scripts/README.md` and `scripts/hooks/README.md` when the diff touches spawn.sh, ops-herdr or a hook, every `SKILL.md` the diff touches or whose subject it changes, your brief's rules, and, for a diff that changes an agent-facing doc, the `SKILL.md` under the "Base directory" line your writing-for-agents load printed (with `.agents/writing-docs.md` for a Playground docs page). Its two sub-agents start with no memory of earlier rounds, which is what makes the read fresh. Other rounds: judge the delta from step 2 yourself on the same two axes, **Spec** (the right thing: every spec line delivered, nothing unasked) and **Standards** (built well). **Schema shape:** when the diff touches `packages/db/`, you are the schema's advisor (`db-migration`'s step 0): judge the shape on the choices that step names as hard to reverse, and score a change that is not additive as blocking until the PR names the owner's go by its Inbox `#iN`. Before you ask for a migration to be held or delayed, check what the head's code needs from it: a held migration that also adds columns leaves the restarted head without the columns its inserts and selects name (round 4). **Samples:** when the ticket carries samples, build your own **samples table** from the spec file's samples, one row per sample: the sample, the path that handles it end to end, and its outcome at the head, taken from running or tracing that sample through the head's code, and posted in the verdict ([COMMENTS.md](references/COMMENTS.md)); the PR body's table is the claim you check against yours. The unhandled samples are one blocking Spec finding listing their rows, unless the ticket's Status section records the split as triage-and-implement's phase 5 asks, the owner's words quoted with their link. Every round, a base-merge one included, re-runs every row at its own head. Then verify what every finding rests on yourself, by VERIFY.md, whichever read produced it. A claim taken from a script's usage comment rests on the code path that comment describes: read that path before you act on it, since a stale comment reads as true (spawn.sh's resume line, which said a resume opens a workspace of its own, cost another PR a round). A finding about a pointer, link or line missing at several places lists every place the read found, each as `file:line`, so one fix round closes it. For a dependency-bump PR, an advisory answered no-plain-fix-exactly-pinned stands only after the audit skill's rung 2 read of each root parent's newest in-range version and its dependencies (`npm view <parent> version dependencies`), since a parent's range often already carries the fix. **Done when** every spec line is marked delivered, partial or missing, every changed agent-facing doc is judged against writing-for-agents, a diff under `packages/db/` has its shape judged, a ticket with samples has your samples table with a row for each, for a dependency bump, the parent read is done, and every finding is measured or marked reasoned, and, for a stacked child, the fixed point you pass `code-review` is the one [VERIFY.md](references/VERIFY.md)'s **Read a stacked PR's own lines** names for its state.
5. **Hand small fixes over.** Hand each small, mechanical fix to the worker as a checked patch, and keep the PR you score free of your commits: [ADR 0004](../../../../.agents/adr/0004-an-independent-reviewer-is-the-gate.md) makes the gate a reviewer independent of the code it scores, so a head holding your own commit has no independent score. Make the edit in `<clone>`, save `git -C <clone> diff > <scratch>/fix.patch`, restore the clone with `git -C <clone> checkout -- .`, then check the patch applies with `git -C <clone> apply --check <scratch>/fix.patch`, and put the patch in the verdict and your report; the worker applies it word for word as a commit of its own, which your next round scores like any other push. A patch only rewords, renames or deletes; anything that adds behaviour or rule text goes back to the worker as a finding. **Done when** each finding is either written up for the worker or handed over as a checked patch, and the head holds no commit of yours.
6. **Score** the PR, not the delta: a faultless push leaves open findings open, so the score stays at the lower mark until a round sees them closed.

   | Score | Means                                                                     |
   | ----- | ------------------------------------------------------------------------- |
   | 5     | Nothing left you would change but nits, which are listed. Merge as it is. |
   | 4     | Good; merge after small fixes. Findings are improvements, not defects.    |
   | 3     | Competent work with a real defect to fix first. The usual first score.    |
   | 2     | A core claim, the approach, or the fit to the spec is wrong.              |
   | 1     | Should not merge.                                                         |

   Any blocking finding caps the score at 3, and any should-fix finding left open at 4. In a work-org PR, scope beyond its ticket and the Product team's answers is a should-fix, never an improvement (`.agents/decisions.md`). A finding against a rule written in the code (a ratchet, a check whose rule says it never rises) stays blocking when your brief lists it as agreed, unless that agreement quotes the rule's owner. A round left with only nits is a 5/5 candidate (The last 5/5), its nits listed in the verdict, or handed over as your step 5 patch, for the worker to take or leave. A nit the worker leaves gets no tester or local CI round of its own. A PR body with no `test:skills` result in it is a nit, since GitHub Actions runs the suite at the head. Before scoring, ask what can be removed (YAGNI): a speculative option, layer, setting or dependency beyond the spec's Done when is a should-fix. So is a PR body, Playground's or the work org's, that is not the [pr](../pr/SKILL.md) skill's template (a `## TL;DR` on top, Summary, Evidence and Merge Danger, `## Links` last), or whose TL;DR speaks in jargon rather than what the owner sees. The template itself is settled by the owner: no finding, nit or suggestion targets `extensions/core/skills/pr/SKILL.md`'s wording, sections or order, and none caps the score; a review checks only that the file is upstream's plus its TL;DR and Links blocks, as its drift test holds, and that a body fills the template. So is a changed agent-facing doc that writing-for-agents would change: a step with no completion criterion, a prohibition where the positive fits, one meaning written in two places, or sprawl that disclosure would cure. Score from the findings, never from the effort shown: a brilliant write-up with one real defect is a 3, and no nit is made up to justify a lower number. A lower score after an earlier 5/5 at the same head is posted as it is: the newest verdict is the one `bun run pr:merge` reads, which is the point. **Done when** each finding carries its axis and its weight (blocking, should-fix, nit), and the score follows from them.

7. **Post** the verdict comment and the inline review, then close the threads the head settles, all by [COMMENTS.md](references/COMMENTS.md). Right before the verdict posts, read the head's checks again by VERIFY.md's **Read the head's own checks**, since a check still pending at your earlier read can go red while you review: each check red there is a blocking finding, with its job link and its failing test or error line, and step 6 scores again with it before anything posts (on a work-org PR a verdict posted on checks read while pending, and `frontend-build` had gone red at that head). **Done when** the head's checks were read again right before the verdict posted, every check red there is a finding in it, `state.py pr` shows your new verdict at the head, and its open threads are exactly the findings still open (over REST, where every thread reads unknown, that check waits for the reset, as COMMENTS.md says).
8. **Report and wait.** Send your worker the score, the counts and the verdict's link, in 5 lines at most, by name, or, when that send fails, to the `uds:` address its newest message came from (playbook's SESSIONS.md, Message a session). Then start `${CLAUDE_SKILL_DIR}/scripts/state.py wait <repo> <n> <head>` as a background task (Bash `run_in_background`): it ends with `MOVED <sha>` on the next push, which starts the next round whether or not the worker announced it, or `CLOSED <state>` when the PR merges. A 5/5 is a round like any other: stay up, leaving your roster entry at `working`, and keep a waiter on the head until the waiter ends with `CLOSED`, since a canary move after the 5/5 brings a merge round only you can score at once (on 18 Oct three reviewers ended at 5/5 and were spawned again for it). ops-tick's auto-end may end you once you sit idle 30+ minutes with every head scored, and your worker resumes you under the same name on the next push (playbook's SESSIONS.md, End). After a compaction, a resume, or a notice that background tasks did not finish before the previous session ended, run `state.py pr` for each PR you hold and start a `state.py wait` wherever none is running, since an account flip kills the waiters with no notice. A 5/5 also goes stale with no push and no conflict: each time you fetch canary, in any PR's round, or a message names a PR that landed, diff what landed since the canary each waiting 5/5 was scored against (`git -C <clone> diff --stat <that canary> origin/canary`), grep the waiting PR's diff and body for every `file:line` and quoted text in those files, and score each match again (one PR quoted spawn.sh's resume usage line, which another PR rewrote while git merged both cleanly). **Done when** the waiter is running, re-armed after any of those signals, or the PR is closed, and every waiting 5/5 is checked against what has landed since its score.

## The last 5/5

A round that would score 5/5 is a **candidate**, never the verdict: start it again at step 4 with `code-review` on the whole diff from the merge base, setting every earlier verdict aside, unless this round's step 4 already ran `code-review` on the whole diff at this head, which keeps that read. Finish every mutation and restore before you start code-review, since its sub-agents read the clone as it stands. A head made only by merging `canary` in, after the fresh full read, is a new head whose merged diff that read never saw, so it needs a fresh full read of its own before 5/5. The read is whole however small the delta, and whatever a re-review message asks for. A `code-review` whose sub-agent failed or came back empty is no fresh read: run it again. Post 5/5 only when that fresh full read finds no blocking or should-fix finding (its nits join the verdict's list) and `bun run check-types`, run in `<clone>` through `~/.playground/ops/run-slot.sh <your session name> -- env NODE_ENV=production SKIP_ENV_VALIDATION=true bun run check-types` (in a clone still without the `.env` above, `@packages/db`'s build stops on "Invalid environment variables" before any type check runs unless they are set), is green: a red run is a blocking finding for the worker, with the errors it printed, and the round scores below 5. A run your worker has already measured at the same head is not queued again: ask for its result at that SHA and cite it. A box run's id is `ci-<first 12 of the tree>-<random>`, so check that the cited run's prefix equals the first 12 characters of `git -C <clone> rev-parse <head>^{tree}` before citing it. When `origin/canary` has moved past the head's merge base and changed a file the PR changes (`git -C <clone> diff --name-only <merge base> origin/canary` against the PR's own files), also run the touched tests (below) on a local merge with `origin/canary`. The merge also runs, whenever `origin/canary` has moved past the head's merge base and whatever files it changed, when the PR's own diff adds or changes a repo scanner, as the touched tests' fourth rule finds one (below), or a data file one reads, since the scanner reads text the head lacks: the guards (`tests/test_kill_by_name.py`, `tests/python-allowlist.test.ts`, `extensions/core/lists/playground-terms.json`, `scripts/check-em-dashes.sh`) and PG-1949's owner-text ratchet among them; with `origin/canary` unmoved, the head's own touched tests cover it. First `git -C <clone> merge-tree --write-tree <head> origin/canary`: a conflict there is a blocking finding, which goes to the worker with the merge, and no merge runs. On a clean one, `git -C <clone> merge --no-edit --no-verify origin/canary` on the clone's head in your own `<clone>`, never a worker's worktree: a throwaway local commit, never pushed, so `reset --hard <head>` restores the clone. Then `bun install --ignore-scripts --cwd <clone>` when the merge changed `package.json` or `bun.lock`, and check-types as above when it changed `packages/*` (a test reaches a package through its built `dist`), then the touched tests (below), then `git -C <clone> reset --hard <head>`, and the same install and check-types again, so the clone is back at the head. A merge git calls clean can still break, as one PR did against another's `KIND` under `set -u`: a red run there is a blocking finding. Name the run in the verdict's body as `touched tests on a merge with canary <c7>: N pass`. Take `<c7>` from `git -C <clone> rev-parse --short HEAD^2` right after the merge, never from an earlier read of `origin/canary`, since a fetch between the two names a canary the run never merged (one PR's verdict named d21c8bd for a run on ac070f7). Post the 5/5 verdict and its `Review • 5/5` label. GitHub's `Audit, Lint, and Build` and `test` check runs, green at that head, are the gate after the reviewer, never an input to its score (playbook's **ci** rule). A run of the touched tests goes in the verdict's body as `touched tests: N pass`. The verdict line is the first line of its own comment, since `bun run pr:merge` reads a review from first lines alone. **Done when** the fresh full read found no blocking or should-fix finding, check-types ran green, the touched tests (under the long-list exception, the changed modules' own tests with PR CI green at the head) ran green on a local merge with canary whenever canary changed a file the PR changes, or the PR adds or changes a repo scanner with canary moved, and `<clone>` is back at the head with its install and build, the 5/5 verdict and its `Review • 5/5` label are posted at the head, every thread you opened is resolved, and your worker has the head; the two checks green at that head are the next gate, `pr:merge`'s, never part of this done.

**The touched tests** come from the diff, and `${CLAUDE_SKILL_DIR}/scripts/state.py touched-tests <clone> <merge base> <head>` lists them, one path per line relative to `<clone>`, each test once and only where it exists at `<head>` (at the head, or on the local merge at `HEAD` with `$(git -C <clone> rev-parse HEAD^2)`, the merged canary, as the base). It selects by four rules:

- every test that mirrors a changed file, its path under `tests/` with the source's extension swapped for `.test.ts` or `.test.tsx` (AGENTS.md's mirror rule: `web/next/src/components/dashboard/composer.tsx` is tested by `tests/web/next/src/components/dashboard/composer.test.ts`);
- each test file the diff changes;
- each test file whose text names a changed file's path with its extension dropped, as an import does (`../../../../../web/next/src/lib/outbox`), or, for a `web/next/src/` file, as `@/` and the rest (`@/lib/outbox`), or, for a `web/next/src/` or `api/hono/src/` file, as the path relative to that root inside a whole quoted string, with its extension, and also without it when the relative path holds a folder (`"components/dashboard/app-sidebar.tsx"`, `"lib/health"`, read by a root the test builds; a bare stem would match a quoted name like a branch, so it keeps its extension; the sidebar-footer miss on one PR). One PR's review found `tests/web/next/src/lib/chat.test.ts` red this way: it imports the changed `outbox.ts`, and its own mirror, `chat.ts`, was not changed. It also names a changed file from the test's own folder: a relative import (`./audit-fake`, which `audit-canary.test.ts` imports), or, for a test in the folder mirroring the file's, its bare name in quotes (`tests/scripts/briefs/slots.test.ts` reads `"new-tester.md"` by `join("scripts/briefs", name)`), both missed until one PR and another PR;
- the tests that scan files across the repo, which no touched file selects: each whose text holds `ls-files`, a `git grep` (in a shell line or as argv, wrapped across lines or after an option like `-C`: `GIT_GREP` in the script), `Bun.Glob`, `new Glob(`, `readdirSync` or `readdir(` (the cmux and herdr boundaries, `tests/AGENTS.test.ts` and `tests/web/next/src/ui-copy.test.ts` among them, the last missed by one PR's own list, and `old-proxy.test.ts`'s `git grep`, missed by one PR's), plus the three whose imported source scans the repo, `SCANS_THROUGH_SOURCE` in the script. In a Python repo (a `pyproject.toml` at its root) also each `tests/test_*.py` that calls `rglob(`, `.glob(`, `os.walk` or `read_text(` and spells in string literals (`"src/a"`, `ROOT / "src" / "a"`) a folder or file holding a changed one: one PR's touched tests ran green while CI went red on `tests/test_pms_note_injection.py`, which scans `connectors/integrations/` and names no changed path. In a Python repo, a changed `src/**/templates/*.md` also lists each test that pins a built prompt's digest (`sha256(` then `prompt`, or `DIGEST`): one PR changed `maintenance.md` alone and went red in CI on `tests/test_exit_goodbye.py`.

Run the list in two steps, `<clone>` its real path (`pwd -P`) in both.
First write it to a file: `${CLAUDE_SKILL_DIR}/scripts/state.py touched-tests <clone> <merge base> <head> > <scratch>/touched.txt`.
**Done when** it exits 0 and, in a TypeScript repo, the file holds at least one path: rule 4 always lists the repo scanners there, and xargs runs nothing on an empty list and exits 0, which reads as green on zero tests, so a failed or empty list sends you back to the clone and the base.
A Python repo's list can be empty with nothing wrong, since a dotted import (`from pkg.a import f`) spells no path stem and its scanners join only when one names a changed file's folder: append each test that imports a changed module (`git -C <clone> grep -l <dotted name> -- tests`), and its list is done once those are in, even when it stays empty.
Then run it: `xargs ~/.playground/ops/run-slot.sh <your session name> -- bun --cwd=<clone> run test:file < <scratch>/touched.txt`, and in a Python repo its own pytest form in place of `bun --cwd=<clone> run test:file`, run from the clone as `/usr/bin/env -C <clone> <venv>/bin/python -m pytest <flags>`, since a Python repo's scanners can read `src/` relative to the working directory, which gave 22 false reds run from the session's own folder on 23 Oct; a run that printed a `session-timeout` line reads as failed, whatever its summary says.
run-slot sends the checkout `--cwd` names, as it stands, to the runner box, which maps that path to its own copy, so the form reads the same there as on the Mac. **Done when** it exits.
The long-list exception: in a Python repo, when the list runs past about 100 files (a `reply_service` change listed about 386 on 28 Oct), green PR CI at the exact head stands as the merge evidence, and the local run takes the changed modules' own tests alone: each test file the diff changes, and each test named for a changed module (`test_<module>.py` for `<module>.py`). The verdict's body names it as `touched tests (changed modules): N pass; PR CI green at <sha7>: <run link>`; every other part of the 5/5 holds as written.

`test:file` sets `NODE_ENV=test` itself, which the fixture rule reads, so the run, one file or many, carries no `NODE_ENV`, and it runs the files inside the test sandbox, where a bare `bun test` stops at `tests/require-sandbox.ts`. `NODE_ENV=production` belongs to check-types and a commit alone. A red seen only on the box counts once a Mac rerun of those files reproduces it: `~/.playground/ops/run-slot.sh <your session name> -- env RUN_SLOT_HERE=1 bun --cwd=<clone> run test:file <files>`, which skips the box and waits for a Mac slot. Until then it is the box's, sent to Ops with its line from `~/.playground/ops/runner-host/runs.log`. A docs-only PR's touched tests run the same way while the box queue is long (playbook's **slots**).

One PR scored 5/5, then went red in local CI on cmux.test.ts, and another PR scored 5/5 twice while `tests/web/next/src/components/dashboard/composer.test.ts`, the mirror of a file it changed, was red, since its run took the tests of the lib files read instead. **Done when** every test the command listed ran green, or, under the long-list exception above, every changed module's own test ran green and PR CI is green at the head.

When the merge with canary moves a path a test fixture uses (one PR moved the roster folder), prove the fixture still reaches its reader: point the reader at a missing path, run that test file, confirm each case that reads the fixture goes red, then restore the reader with `git -C <clone> checkout -- <file>`. A case that stays green reads nothing: One PR's hook test wrote its roster at the old path, and `scripts/hooks/role.ts` fails open on a missing roster, so its roster cases passed. **Done when** every fixture-reading case went red and the reader is restored.

## The recovery scan

A lead's sweep runs `extensions/core/skills/code-review-loop/scripts/state.py scan <owner/name>` with the factory's repo (`factory.repo`) from the Playground checkout (`$PLAYGROUND_REPO`), since the sweep runs outside this skill. It asks GitHub which open PRs have a head no verdict scored, with no cursor, no seen-list and no cache in the path, so it catches the PR whose reviewer closed, crashed or was never spawned. Each row is `UNREVIEWED`, `STALE <s>/5 at <sha7>` or `SCORED <s>/5`, with its holder in brackets: the roster agents holding the PR, else `outside author <login>: the builder triages (a colleague's: the dispatcher decides per CHANNEL.md's Triage; another's app PR: read-only review then the gate; skills/factory: closed)` for a PR another account opened, which the Builder triages without asking, sending the dispatcher one line per PR; else `no agent; parked in <plans file>` when a plans file names it, else `no agent, in no plan: lost`. A row not scored at its head, held by a worker, whose PR has no live reviewer in `ListAgents` gets one, spawned by that worker. A parked row stays as its plan says. A lost row is dispatched, or put up the chain before its PR is closed. **Done when** every unscored row held by a worker has a live reviewer, and the `RESULT` line's lost count is 0 or each lost row is dispatched or put up the chain.
