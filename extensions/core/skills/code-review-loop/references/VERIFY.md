# Verify, don't read around

The findings worth posting come from checking something. A review is sometimes wrong, and its usual failure is a confident finding that rests on a misreading, so make each one cheap to check.

- **Run the numbers.** A claim about a value, a threshold or a count gets the query, the test or the scratch script that measures it. To prove a suspected logic bug, write a scratch test in your scratchpad that imports the worktree's modules by absolute path, run it with `bun --cwd=<clone> run test:file <its absolute path>`, and hand the worker the repro for its red-first test.
- **Follow the supply.** A field the code now reads is dead when nothing writes it: grep the writer. A route a page calls is dead when no router mounts it.
- **Ask whether each test can fail** for the reason it exists. A test that sets up the very condition it claims to guard against passes against any input. A test that asserts call order from `ast.walk` reads nesting depth, not source order, and counts a call made unreachable as present: print the list first, test it with a call made unreachable rather than deleted, and take order from `lineno`. A source-text assertion can match the comment above the code; a `>=` passes where an exact count belongs; and a new test file outside the runner's reach (`bun test` skips dot-directories) passes by never running, so find its tests in the run's output.
- **Check every spec line on its own.** A sound PR can still miss what was asked: a requirement read from the ticket is a spec finding, even when the diff reads as a design nit. Say when the PR knowingly departs from the spec, and send the question up the chain rather than letting it pass. An item the PR defers ("raise this separately") needs its issue: search for it, and when none exists that is the finding.
- **Read the head's own checks**: `gh api repos/<repo>/commits/<head>/check-runs`. `gh pr checks` can report an older run, and the check-runs list can still show `in_progress` for a run that has finished: when it matters, read that one run by name and compare its `started_at` with its usual length.
- **Prove the instrument moved.** A mutation that changed text but no behaviour, a command that ran nothing and a field read under the wrong name (REST `pulls/<n>/files` keys a path as `filename`, GraphQL as `path`) all come back green or empty. Confirm a mutation took and nothing upstream normalises it away, keep stderr in sight (no `2>/dev/null`), keep a piped run's exit its own (`set -o pipefail` in the same shell as the pipe, inside a `bash -c` script's quotes, or `${pipestatus[1]}` under zsh, which leaves `PIPESTATUS` unset), give a bun option before its subcommand as `--opt=value` (`bun --cwd <dir> test` runs package.json's test script in place of the tests), treat empty output where a number belongs as a failed command, never zero, and in zsh brace a variable before a colon (`${H}:src`, since `$H:s` is a history modifier), pass a list as an array (`"${T[@]}"`, since zsh does not split `$T`) and check it is non-empty before a runner gets it.
- **Copy the process state.** A fixture or probe that stands in for a real process copies what the real program does to its own state (its working folder, env and argv), not only its command line: start it from the real launch line, copy the real entry file's first lines (a `chdir` included), then read what the code reads. On 1 Nov, a review read the dashboard's branch from the working folder of the process that serves it: the worker's evidence and the review's first probe both ran a stand-in `server.js` that never changes its folder, so both read the right branch, while the real Next standalone `server.js` begins with `process.chdir(__dirname)`, so on the supervised dashboard the serving process's folder is the build folder and the branch drops; reading Next's own template caught it.
- **Read a whole file list.** The PR's own files come from the clone, `git -C <clone> diff --name-only <fixed point> <head>`, and another PR's (a stack's parent, an overlap claim) from `gh api --paginate repos/<owner>/<repo>/pulls/<n>/files --jq '.[].filename'`, since `gh pr view <n> --json files` stops at 100 with no sign it cut the list (one PR read 100 of its 143 files, measured).
- **Mutate what the test loads.** A mutation canary edits the file the test actually imports: a test reaching a `packages/*` module goes through its `dist`, so a mutation in `src` changes nothing until a rebuild. Check the mutation is on disk before the run and the tree is clean after it.
- **Search inside the review.** Keep every search inside `<clone>`, the portless folder and the paths your brief names, and stop each background task you started before you report: one sub-agent's background `find /` outlived its report and ran 1h46m at 45% CPU, a third of a load spike.
- **Restore before the fresh read.** Finish every mutation and restore before you start code-review, since its sub-agents read the clone as it stands.
- **Pair every absence with a control.** "Not found" and a search that never ran look the same: the same command also finds a sibling term that must be where the missing one would be, and the verdict names that control. A loop whose rows all read negative gets a row that must read positive, and two reads called equal each get a line count, since two failed reads always agree. Before calling a branch untested, grep the tests for its effect (the row or column it writes) and for its entry point, not only its name, mutate the branch to see which tests go red, and read the repo's testing guide before suggesting a test: a test can drive a method through its entry point and assert on the column it stores without naming it.
- **Feed an extractor real input.** A change to a regex or a parser that reads text people wrote (PR bodies, comments, transcripts) runs against a sample of real ones, such as the last merged PRs' bodies, and the verdict names how many matched before and after.
- **Close every case in round 1.** List every case the change can meet and check them all in round 1, so a review never finds one hole a round. Code that parses git's output (a diff, a log, a status) reads real `git diff` output from a scratch repo under each setting that changes it: `core.quotePath` (on by default, it quotes a path holding a non-ASCII byte, and git quotes one holding a tab, `"` or `\` even with it off, so read paths with `-z` and split on NUL), `diff.noprefix`, `diff.mnemonicPrefix`, `diff.interHunkContext`, a textconv driver, CRLF line endings, and a path with a space (git ends its `---` and `+++` lines with a tab); a parser that pins its own flags gets the same run, which proves each flag took. A UI swap whose spec keeps behaviour the same puts each swapped control beside canary's in every state it has (running, failed, pending, read-only), each under reduced motion, without colour, and by its accessible name and value. A PreToolUse hook that gates a command reads the checkout before any part of the call runs, so probe the command chained after the one that sets up its state (`git add -A && git commit -m m && git push`, `x; git commit`, `sed -i ... && git commit -a`), and inside Claude Code's own shapes, such as a message built by `$(cat <<'EOF' ... EOF)`, whose command the hooks' shell reader visits before the one it feeds. One PR met its git settings one round at a time; One PR took three extra rounds, one state each: a running cue under reduced motion, a failed row shown by colour alone, and a mode menu whose name lost its value when a Select became a menu button; and another PR found the chain in round 4, the heredoc message in round 5 and a staged `web/next/café.ts`, read as `"web/next/caf\303\251.ts"`, in round 7.
- **Read a stacked PR's own lines.** While the base PR is open, the fixed point is `git -C <clone> merge-base <base ref> <head>`, never the base's branch ref, which moves with every commit the base gains: on one PR, a diff against its base PR's ref read that base's later b7c5067 as reversed. Once the head has merged a canary its base lacks, diff instead from the tree of `git -C <clone> merge-tree --write-tree $(git -C <clone> merge-base <base ref> <head>) $(git -C <clone> merge-base origin/canary <head>)`, since the merge base alone counts that canary's work as the PR's: on one PR it gave 83 files where the PR's own were 16. Once a stacked PR's base has squash-merged into canary, `state.py delta` reads that whole base as the PR's change. Once the head has merged canary (until then `origin/canary...<head>` still holds the base), compare the PR's own added and removed lines on each side instead: `git -C <clone> diff -U0 <old base>...<last scored>`, where `<old base>` is the SHA of the base's tip under the last scored SHA (its branch may be gone), against `git -C <clone> diff -U0 origin/canary...<head>`, where a line in one and not the other is what the push changed, a merge git called clean included. On one PR that found a `manager)` case in spawn.sh doubled by a three-way merge git called clean. When the worker rebases the stack onto canary instead (`git rebase --onto origin/canary <old base>`), confirm the rebased head with `git -C <clone> range-diff <old base>..<last scored> origin/canary..<head>`, where a pair marked `!` is what the rebase changed.
- **Grep for every action an absolute rule covers.** A PR that adds a rule with no exceptions ("never", "every", "only") gets one search before scoring: each touched skill and each skill or script that calls it, for every action the rule covers, and each hit either complies or carries a named exception. One search finds what would otherwise take a round per hit.
- **Run the rule test when the rules move.** A PR that touches AGENTS.md, CLAUDE.md or an `.agents/dashboard/*.md` file gets `bun run test:file tests/AGENTS.test.ts` before scoring: it pins each `ALWAYS:` rule by its opening words in AGENTS.md and its topic file, each dashboard topic file to its pointer, and the every-turn load to 97% of `BUDGET` (`MARGIN`, which keeps 3% of it free for PRs that pass alone and merge together), so a reworded rule or a grown AGENTS.md fails there.
- **Test each part of a gate on its own.** A scratch input that satisfies a check's precondition itself tests the logic, never the gate; vary each part of the gate separately, renames and deletions included when it keys off diff paths, and cut the cases again whenever the PR moves the rule they were written for. A guard written as `flag and not was_flag` guards only the run's first failure: fail an earlier step, not only its own.
- **Verify the invariant, not the state.** After a property holds, mutate what supplies it and look for anything else that writes over it; a mutation that turns nothing red is the finding.
- **Enumerate before you act.** A sample that agrees proves nothing when the conclusion leads to an action you cannot take back: page through every item, and state the sample size wherever a sample stands in for the whole. To correct an author's count, compute it every way that could give their number (test functions and collected cases), say which you used, and read a whole-suite total from the head's CI log.
- **Anchor each claim to its ref.** What a PR does reads from its head; what is live reads from the base; name the ref each claim reads from. On a deploy-config repo, each environment syncs from its own branch: read its values on the branch its ArgoCD app's `targetRevision` names (`git grep targetRevision <ref> -- argocd/`) before weighing a claim about that environment, since its values file on the PR's branch can differ. Re-run a description's own commands against today's base, check the merge state of each sibling PR it calls pending, and confirm its `file:line` anchors still hold. Before calling a PR unmergeable from a ruleset's config, look for a PR already merged into that base, and say "unsatisfiable by review" rather than "cannot merge". A claim that a tool is on a runner reads the runner of the run it cites (`gh api repos/<repo>/actions/runs/<id>/jobs --jq '.jobs[]|.runner_name+" "+(.labels|join(","))'`), and for the box that runner's own PATH, since a job on `srv1330087-runner-<n>` searches `~/runner-<n>/.path`, not the PATH `ci.sh exec` gives (which finds `bun` where a job cannot): from a Playground clone, `~/.playground/ops/runner-host/ci.sh exec <clone> -- bash -c 'PATH=$(cat ~/runner-<n>/.path) command -v <tool>'`, one box run, whose exit 255 means the box ran nothing. On one PR, a 6 Oct run on a GitHub-hosted runner passed for proof that the self-hosted box had `gh`, which it lacks.
- **Measured or reasoned.** "I ran it and got N" and "this looks like it would" carry different weight; write the second in those words. Measure a value a scratch check needs where you can; one you made up is labelled constructed beside the value itself, not only in a later note. Before posting a finding, name the one fact that would make it wrong and check it; one you cannot check makes the finding conditional, said as such, never a settled claim above a caveat. A suggested fix is a hypothesis too, whoever suggests it (you, the author, a tester): apply it in a scratch copy and run the check that found the problem before it goes in a `Fix:` line or a commit. A fix to a reader that serves several shells or dialects is tried on each one it names, with the real binary, before it goes in a `Fix:` line: a reviewer's fix to the hooks' shell-option reader, tried on bash alone, let zsh's `-O`, which takes no value, swallow the word after it, and no-stash refused the shape at one round's head and allowed it at the next (measured, 1 Nov 2026).
- **Measure an outside tool's answer shape.** Whether a field in a third party's answer is present, missing or null is measured from a real read or from its schema's required list, never assumed: on one PR a review asked for `pane.agent !== null`, while herdr 0.9.5 leaves `agent` out on a pane with no agent and its schema lists it as optional.
- **Judge real screens.** A claim about how the dashboard judges a pane's screen (deliver.ts's `inputState`, `holdsMessage`) is tested on real Claude panes: `herdr pane list` gives the ids, keeping the panes whose `agent` is `claude`, `herdr pane read <id> --source visible --lines 40` is a pure read, the call `readScreen` makes, and a scratch script runs deliver.ts's pure judges over each screen, skipping a pane whose `scroll.offset_from_bottom` is above 0, as `readScreen` refuses a scrolled pane; no session is spawned and nothing is sent. Record each pane's width, from `herdr api snapshot`'s `layouts[].panes[].rect.width`, beside its judgment.
- **Probe Claude Code itself.** A claim that Claude Code stops on a command shape gets a headless run: `claude -p --permission-mode bypassPermissions` in the shape `no-headless-login`'s reason gives, in an empty scratch folder, its variables set to paths inside it, doing that shape; a refusal prints the rule's own text.
- **Trace each effect through A, B, A.** A timer or a subscription that clears UI state is keyed on that state, never on the prop that set it: walk each effect's cleanup through its deps changing A, then B, then back to A, and check the state still clears (a tick keyed on a session's light ran its cleanup on working, idle, working and stuck for a whole turn).
- **Look where a moved element was.** When a PR moves an element out of a flex column or grid with `gap-*`, measure the space it left behind against the reference it copies (a `gap-4` left between a stream and its composer gave 52px where the reference has 36).
- **Read a colour rule through inheritance.** An icon with no colour class of its own takes its parent's: an audit of state colours lists every state icon, coloured or not, and reads the class each one inherits.
- **A focused field's lit border is never clipped by its container.** The app draws no focus ring, so a focused field shows its border: Tab to every input and button that sits at the edge of a scroll box, a pane or an overflow-hidden parent, at desktop and phone, and look at all four sides of its border: a box that clips (`overflow` other than visible, a resizable pane) needs its content inset so the border shows whole (one was seen clipped on its left side).
- **Name what you skimmed.** Each verdict ends with what was read in full, what was skimmed, and what was not verified, so the author knows where their own judgement still has to work.
- **Own your slips.** A false start that could have changed the conclusion (a test run against the wrong checkout, a check read before it finished) goes in the verdict in one sentence.

Done when every finding in the verdict is marked measured or reasoned, and the verdict names what was not verified.
