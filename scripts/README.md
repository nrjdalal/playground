# scripts

The factory's own scripts: `spawn.sh`, which starts and resumes every factory session, `link-skills.sh`, which installs the skills, the herdr servers' ops job, a worktree's `node_modules` clone and `bun run test:skills`.
AGENTS.md keeps one line for each, and this file holds the text that line stands for.
It also holds `bun run hooks:differential`, the sweep and replay a hook PR's Evidence quotes, and the rule for an edit script's replacements.
Read a section before you change its script or its tests, or when it refuses a start you did not expect.
The factory's hooks are in [hooks/README.md](./hooks/README.md).

## spawn.sh

- While `playground focus` stands (the data folder's `focus.json`, playbook's LIFECYCLE.md), spawn.sh refuses every start, naming focus's session and its end, but two: a reviewer or tester that reports to the focused session (a resume's, the worker its roster row names),
  and a `--priority` start while a priority file stands in the data folder: `priority.json`, an urgent window, or any `priority-<name>.json`, an org's own urgent window or a session's own window, each writer keeping its own file.
  A job's own `priority-start.json` passes the load and slots gates alone, never focus; with no priority file, a `--priority` start is refused, naming the command that opens one.
- A session opens a priority window only with `playground priority on <session> --reason "<why>"`, which writes `priority-<session>.json` naming the session, who opened it, the reason and the time, and lifts it with `playground priority off <session> --reason "<why>"`; a window written by hand passes no review of who opened it or why.
  spawn.sh reads no window's content, so while one stands every `--priority` start passes, not only the start of the session it names: lift it once that start is done.
  A lead opens one only on the owner's or the dispatcher's word, never on its own.
  Each `on`, `off` and lapse is a line in the data folder's `ops/priority.log`, and ops-tick's `priority-lapse` beat lifts a window still standing after `LAPSE_HOURS` (`packages/scripts/src/playground/priority.ts`), telling ops, so a forgotten window stops passing starts by itself.
  Tests: `bun run test:file tests/packages/scripts/src/playground/priority.test.ts`.

## The herdr servers

- The herdr servers belong to one ops job, `bun run ops:herdr` (`packages/scripts/src/ops-herdr/`): it starts each that is down on the binary the repo's `pin.json` beside it names, with its `config.toml`, so both change only through a merged PR, and `bun run ops:herdr stop <session>` refuses while the session holds a pane, since a stop exits every pane;
  `stop default` stops herdr's own default server (`~/.config/herdr/herdr.sock`), which no job starts, refusing only while one of its panes runs an agent.
  The binary is Playground's own copy at `~/.playground/bin/herdr`, following HOME alone as the sockets do, and `playground herdr pin` (`packages/scripts/src/playground/herdr-pin.ts`) puts it there: it downloads the pinned version's release asset for this Mac, checks its SHA-256 against the pin before the move, and refuses a mismatch naming both sums.
  The pin holds GitHub's digest of each release asset, keyed `darwin-arm64` and `darwin-x64`, and the job takes this Mac's, refusing a machine the pin names no asset for; a herdr on PATH is the human's own, which nothing runs.
  Moving to a new herdr is a PR to `pin.json`: its version and every asset's sum.
  Once it has started a server, any of `PLAYGROUND_HERDR_SESSIONS` (`playground,playground-probes` by default; a name that is not a word is named on its beat and skipped), it runs `spawn.sh restore` pointed at that server, since the pinned config turns herdr's own resume off,

  A person brings herdr back with bare `playground`, which runs its `start` first.
  A server hands its panes the shell basics alone, so `spawn.sh`'s herdr launch file sets `TMPDIR` to `$(getconf DARWIN_USER_TEMP_DIR)`, keeping one already set: every start, resume and restore writes that file, so a running server needs no restart for it.

  playbook's LIFECYCLE.md, Ops jobs, has the rest.

  Canary's hooks load from canary's whole tree at the sha, unpacked by `git archive` and installed from its own lockfile (`bun install --frozen-lockfile --ignore-scripts`), so every hook loads canary's packages, `extensions/core` and dependencies, and the install leaves the shared git hooks alone.
  Each run builds its tree in a folder of its own and renames it to `hook-differential/<sha>` in the temp folder, so two runs against one sha share the finished tree alone; the tree, `node_modules` included, stays there for the next run against that sha, beside any folder a run that lost the rename left.
- It prints one line of counts per hook, the figures a hook PR's Evidence quotes: forms, cases, the same, newly allowed and newly refused, split by the form's class; calls, the same, newly allowed and newly refused.
  The first 20 changed cases of each hook go to stderr, so read them there, and past 20 one more line says how many it cut, `<hook>: <n> more changed lines not shown (--all prints them)`.
  `--all` prints every changed case, and the stored result keeps every one.
  A sweep lists only the cases outside the form's class and the newly refused ones, and transcript text stays out of the repo and the PR.
- A run at a clean worktree stores its counts and changed cases under a key in the data folder (`hook-differential/results/<key>.json`), once it finds the worktree still clean at the key's tree and a sweep's forms module still the key's blob; a run whose inputs moved under it stores nothing.
  The key hashes the head's tree sha (`HEAD^{tree}`), the `--canary` sha, the mode with its inputs (a sweep's forms module blob sha, a replay's `--hours` and its newest transcript's mtime), the sorted `--hook` names, `--all` and `--role`, and those alone: a hook that reads files outside the tree (the home, a gitignored `dist`, the forms module's own imports) needs `--fresh` once those change.
  A run whose key matches a stored result under 24 hours old prints that result under a first line `reused: <key> from <iso>, head <tree sha>, canary <sha>`, queueing and building nothing, so a reviewer at the author's head and base quotes the author's sweep.
  A worktree with any modified or untracked file, any changed part of the key, `--fresh`, or a result 24 hours old runs fresh; a replay's key moves with every new transcript line, so a replay mostly runs fresh.
- Started bare with no stored result to reuse, it queues itself through `run-slot.sh`, as `commit-slot.ts` queues a commit's build, and says so on stderr with the queue's depth; inside a ticket, or where `run-slot.sh` is not executable, it runs as it is.
  Tests: `bun run test:file tests/packages/scripts/src/hook-differential.test.ts`.

## An edit script's replacements

An edit script that writes code or text with JavaScript passes each replacement that may hold `$` through a replacer function, `s.replace(a, () => b)`, or `split(a).join(b)`, since a string replacement reads `$$`, `$&`, `` $` ``, `$'` and `$1` as patterns: `"a".replace("a", "echo $$")` gives `echo $`, and an edit script once turned `$$` into `$` in `run-slot.sh` with no error.
In the repo's TypeScript, `tests/packages/scripts/src/replace-dollar.test.ts` fails on a literal replacement holding `$$`, `` $` `` or `$'`, or `$&` after a string search, naming the file, the line and the fix.
