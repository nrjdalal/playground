# The factory's hooks

Each Claude Code hook in this folder, in full: what it refuses or writes, for whom, and why.
AGENTS.md names each hook and points here, and this file holds each one's text.
Read a hook's section before you change the hook, its tests or its registration, or when it refuses a call you did not expect.
Widen what a hook allows only by one literal form it reads whole, tracking no shell state (variables, functions, loops, traps), and have it refuse every other form with a reason that names the literal one.
Every bypass form a review has found stays refused through a widening: each is a row of `tests/scripts/hooks/fixtures/refused-forms/`, one file a source (`<n>.ts` holds #<n>'s rows), which `tests/scripts/hooks/refused-forms.test.ts` runs through each guard it names, and a bypass a new review finds that canary refuses joins it as a row in the same PR.
The test spells every path flag a row names again (its `PATH_FLAGS` lists each, with the joins its program reads), by its other joins, a relative folder, a `./` hop, an `<x>/../<x>` hop and a link, and holds each spelling to the row's verdict.
`no-raw-spawn` guards `scripts/spawn.sh` and refuses hc, so its text sits in [the spawn.sh section of scripts/README.md](../README.md#spawnsh).
Their tests are `bun run test:file tests/scripts/hooks`.
Every hook reads a wrapper (`doas`, `env`, `nice`, `nohup`, `stdbuf`, `sudo`, `time`, `timeout`, `xargs` and the rest of `WRAPPERS` in `scripts/hooks/shell.ts`) by that wrapper's own list of options, a cluster (`-Hp`) letter by letter and a value attached (`-pwc`, `--prompt=wc`) or as the next word, so the program it finds is the one the wrapper runs.
Homebrew coreutils' `genv`, `gnice`, `gnohup`, `gstdbuf` and `gtimeout` read as `env`, `nice`, `nohup`, `stdbuf` and `timeout`, with those options, and env's lone `-` reads as its `-i`, with env's options read on after it, as BSD env reads it; GNU env ends its options at a lone `-`, so this reads more of GNU's words than GNU runs.
zsh's dash modifier, a lone `-` where a program word stands, behind another wrapper too (`- sh`, `- eval`, `nice - ls`), is a wrapper of `WRAPPERS` too, since zsh runs the command after it, a builtin in the same shell; a builtin behind it counts as one the shell may not run, so a `cd` behind the dash leaves both folders judged, and a lone `-` as an argument (`cat -`) keeps its reading.
Every hook matches a program's name with case ignored (`program()` in `scripts/hooks/shell.ts`), since macOS's filesystem runs `RM`, `Herdr` and `/bin/RM` as `rm`, `herdr` and `/bin/rm`; arguments and subcommands keep their case.
The shell's own builtins whose effect a hook follows (`cd`, `export`, `source`, `eval` and the rest of `SHELL_OWN`) keep the case they are written in, since in another case one runs no builtin (macOS's `/usr/bin/cd` runs `builtin cd` in a child), so `CD` moves no folder;
a builtin named by a path (`/usr/bin/cd`, zsh's `=cd`) is read the same way, and `builtin` and `command` run one only as their bare lower-case words (`COMMAND cd` runs `/usr/bin/command` in a child).
An option missing from that list is read both as a flag and as taking the next word, and an option's value in a variable as one word, as none and as several; each hook judges the command under every reading through `run()`, so a missing option costs at most a refusal, and adding it to the list fixes one.
A hook that calls `parse` itself (no-desktop-owner-app's shell scan, no-false-green, no-kill-by-name's xargs read, and `shell.ts`'s read of a substitution's output) takes the first reading, the flag and the one word, as canary read them.
A command's parse makes at most 16 other readings (`READINGS`), so a call holding many such options is read in bounded time; past them, an option is read as a flag alone, as canary read it.
Only the first reading moves the folder, sets variables and records files for the commands after it; each other reading runs on its own copy of them, taken before the command.
Each `withDeadline` call holds its own deadline in its async context (an `AsyncLocalStorage` in `scripts/hooks/shell.ts`), so checks that overlap in one process each time out on their own.
Each `inspectAs` call in `scripts/hooks/no-playground-leak.ts` (no-extension-repo-write, no-playground-leak, no-public-leak) holds its policy, Slack's cleared conversations and its move state in its own async context too, so checks that overlap in one process keep their own verdicts.
`run()`'s count of scripts held open (`MAX_RUNS`) stays one per process, since overlapping checks can only add toward its cap, which refuses a call and never lets one through.
Every hook reads a command's stdin through `stdinOf`: the last file, here-string, heredoc or process substitution on fd 0 of its own, else its pipe, else text it cannot read, so a hook that refuses stdin it cannot read keeps that refusal.
Every hook reads an unquoted heredoc's body as the shell expands it: each command substitution there (`$(…)`, a backquoted command, one inside `${…}` or `$((…))`) is lexed as a command of the line and visited as a word's `$(…)` is, so a guard judges a call the shell runs while it reads the body,
whatever strips the body's tabs (`<<-`), however many heredocs the command holds, and whichever command or descriptor the heredoc feeds (`cat 3<<EOF`, a loop's `done <<EOF`);
a quoted delimiter (`<<'EOF'`, `<<"EOF"`, `<<\EOF`) expands nothing, and a backslash keeps a `$` or a backquote literal, so those stay text.
A quote inside a `${…}` or `$((…))` is a plain character in that body and in a double-quoted word, as the shell reads it there, so each substitution past one is lexed too (`textCommands`), while an unquoted word's quote still quotes.
A script a shell reads from stdin (`scriptStdin`: a shell's or a source's, a root shell's in [no-raw-delete](#no-raw-delete), code a pipe feeds) is judged under that reading and, where it differs, the shell's own, each as a script of its own.
The shell's own reading applies the input redirects left to right, a duplicate onto fd 0 (`<&N`, `0>&N`, `<&N-`) taking whatever last fed descriptor N (`3<<< '…' <&3`), and a brace group's, a subshell's or a loop's input redirects before each body command's own (`{ sh; } <<< '…'`),
the group's redirect taking the place of a pipe into the group (`<reader> | { sh; } <<< '…'`) while a pipe inside the body stays the command's own.
It reads a here-string's `$(echo …)` of words it can read as those words, zsh's `\n` a line break and any other backslash unread, and a here-string of one variable the line set earlier (`S='…'; sh <<< "$S"`) as that variable's value.
It follows no descriptor an `exec` feeds, which it reads as unfed, and no variable set other than by a plain assignment, which it reads as that assignment's value.

## Plan a hook's ships

Plan the ships before you build a guard, since every wrapper runs its script from the main checkout, which follows `main` ([Registered in both settings files](#registered-in-both-settings-files)):

1. Look for a hook script on `main` whose role read or input fits the new rule (`git show origin/main:scripts/hooks/<hook>.ts`), and extend it there: a new event or tool on a script `main` already holds lands in one PR and goes live with the next ship, as no-chat-question's PreToolUse path on `AskUserQuestion` beside its Stop gate and writing-first's events do, each branching on `hook_event_name`.
2. When no script fits, plan a new hook file as two PRs: the script and its tests in one ship, then its registration in both settings files and its bundle in a later one, since `bun run test:skills`'s hooks-on-main step fails a wrapper whose script `origin/main` lacks.

Done when your plan names the hook script, whether it is on `origin/main`, and the ships the guard needs to go live: one, or two.

## Registered in both settings files

- A session resumed without its `--settings` or `PLAYGROUND_ROLE` (a bare `claude --resume`, or herdr's own resume, which ops-herdr's `config.toml` keeps off: playbook's SPAWN.md, Role and settings) still loads the checkout's project settings, so `.claude/settings.json` registers every PreToolUse hook `scripts/factory-settings.json` does, with the same matcher and the same command string,
  since Claude Code runs a handler defined in both files once only when the two commands match byte for byte (measured on Claude Code 2.1.302: one space apart, it runs twice; `tests/scripts/hooks-abs-path.test.ts` holds every hook in both files to it).
  That one command finds the checkout with no `$HOME` in it: `$PLAYGROUND_REPO`, which spawn.sh's launch exports as its main checkout, else the main checkout git names for `$CLAUDE_PROJECT_DIR` (`--git-common-dir`, so a session in a worktree runs the main checkout's guards); when neither names a folder holding the hook's script, it runs nothing and exits 0.
- A hook's script lands on `main` in one ship and its registration in a later one, since every wrapper runs its script from the main checkout, which follows `main`, and a factory session on `canary` loses the hook's tool the moment `canary` registers a script `main` lacks.
  A hook leaves in the reverse order: its registration in one ship and its script in a later one, since a worktree branched before the first still registers the hook in its `.claude/settings.json`, and its wrapper refuses every call the hook guards once the main checkout lacks the script.
  Its bundle goes with its registration, since `bun run hooks:bundle` builds only the guards `scripts/factory-settings.json` registers, and the wrapper runs the script in the bundle's place.
  `bun run test:skills`'s hooks-on-main step (`packages/scripts/src/hooks-on-main.ts`, CI's `test` check) holds every tracked `*.json` file and `SKILL.md` frontmatter outside `tests/` that runs a hook script to it: it fails naming each wrapper none of whose scripts (both of a bundle-then-source wrapper's) `origin/main` holds, and fails when `origin/main` does not read, after fetching it.
- A PreToolUse guard fails closed, since Claude Code blocks a call only on exit 2: its wrapper turns any other exit but 0 (a crash, a damaged bundle, Bun missing) into exit 2, its refusal naming the hook, the code and `bun install` in the checkout,
  and under `PLAYGROUND_ROLE` a missing script or an unresolved checkout refuses too, naming the restore route (ops-restore puts the checkout back, else Ops by playbook's LIFECYCLE.md, Restoring the main checkout); with no role it runs nothing and exits 0, as above.
  A timeout lets the call run, since Claude Code treats a hook timeout as a non-blocking error.
  On Bash, guards' `onFailure: "block"` refuses a call whose guards time out or fail to start ([guards](#guards)).
  Every other wrapper (SessionStart, Stop, PostToolUse and the rest) stays open on a crash, since a Stop hook at exit 2 keeps its session going and a crashing one would loop it.
  `tests/scripts/hooks-abs-path.test.ts` holds both shapes and runs them over stub guards.
- A PreToolUse guard's wrapper runs its bundle, `scripts/hooks/bundled/<hook>.js`, which `bun run hooks:bundle` (`packages/scripts/src/hooks-bundle.ts`) builds from `scripts/hooks/<hook>.ts` with everything it imports, so the guard starts with a missing or damaged `node_modules`; every other hook runs its source.
  Git rewrites a file it moves in place, removing it and writing it again, so a guard that starts mid-move could load a missing or half-written bundle and fail closed.
  So `playground update`, and ops-tick's canary pull when the worktree it moves is the main checkout, first write each bundle the move adds or changes beside its path, rename it over the path and stage it (`packages/scripts/src/swap-bundles.ts`), and the move then leaves it alone.
  A swap that fails at any step puts back what it wrote, and a move that fails puts HEAD's bundles back, each by the same rename, so the checkout is left at HEAD and the next pull moves it.
  While the checkout holds no bundle, as the main checkout holds none until a ship brings them, the wrapper runs `scripts/hooks/<hook>.ts`, which keeps every guard running across that gap; with neither file it refuses under `PLAYGROUND_ROLE`, as above.
  The source stays the one place a guard's logic is edited: after an edit to a guard or to anything it imports, run `bun run hooks:bundle` and commit `scripts/hooks/bundled/`.
  `bun run hooks:bundle --check` names each stale bundle and writes nothing (it reads the index, so stage the edit first), and `tests/packages/scripts/src/hooks-bundle.test.ts` fails on a bundle a fresh build would write otherwise.
  The pre-commit `hooks-bundle` job in `lefthook.yml` runs that `--check` on a commit staging a guard, a bundle, `bun.lock` or a file in a package folder the bundles import (`tests/lefthook.test.ts` reads those folders from the bundles), so a stale bundle stops at the commit, naming the fix.
  `--check` reads the index, what the commit carries, through `git write-tree`: each guard's source, each checkout source it imports and each bundle, so an unstaged edit to a file's text beside the commit decides nothing, and a staged guard edit whose rebuilt bundle is left unstaged is refused; the job skips a merge commit, whose bundles the rebuild below commits on its own.
  CI builds a PR on its merge ref, the head merged with `canary`, so a `canary` change to a bundle input can stale a head whose own bundles are fresh.
  The pre-push `hooks-bundle` job runs `--check --merged origin/canary` when a bundle input is among the files the branch changed since `origin/canary` (`git diff --name-only origin/canary...HEAD`, which lefthook reads only for a `run` that names `{files}`), so a docs-only push checks too, merges included.
  It reads the tree `git merge-tree --write-tree HEAD origin/canary` writes and names the rebuild on the merged tree.
  A merge that conflicts in `scripts/hooks/bundled/` alone is read with its conflict markers, which read stale, and one that conflicts elsewhere prints the paths and passes, since pr:merge's merged-tree gate (`packages/scripts/src/pr-merge/README.md`) reports it.
  Limits: `origin/canary` is the local ref as the last fetch left it, so a push after canary moved checks the older canary, and pr:merge's gate covers the fresh one; a package's import (zod's) resolves from the checkout's `node_modules`, so a `bun.lock` change `canary` brings in is not in the merged read.
  `--check` builds its tree in the mirror, a temp folder it removes afterwards, which holds a copy of every source, `tsconfig.json` and `package.json` file the tree holds, in the tree's own layout.
  So every import the tree reaches resolves as a build of that tree would, whatever its specifier (relative, `@/`, `@packages/*`) and whichever folder it starts from, with the tree's own tsconfigs: a source only `canary` adds, and a path mapping only its tsconfig holds, build and pass.
  Only `node_modules` entries are links: each to the checkout's own, and a workspace package's to the mirror's same path, so a bare `@packages/<name>` import reads the tree's copy of that package with its own tsconfig.
  An import the tree cannot resolve fails the build, exit 1 with Bun's error (`Could not resolve`), so no bundle passes unread: a source `canary` deletes that the head's guard still imports is one, since the mirror lacks it.
  The working files decide nothing the tree holds, so an imported file deleted from disk alone, or an untracked file beside an import, leaves the check as the tree reads.
  The job merges the checked-out `HEAD`, so a push of another ref is judged by `HEAD`'s tree, and pr:merge's gate by the PR's own.
  Write mode also removes a bundle no build writes, a removed guard's: each `.js` file directly in `scripts/hooks/bundled/` that no build writes, one file at a time, and nothing else there.
  The bundles are committed, so a git restore of a deleted checkout brings them back with no install (so a guard that cannot start needs its bundle back, by `git checkout` or `bun run hooks:bundle`, where the wrapper's refusal still reads `bun install`).
  Two branches that both change a shared hook file conflict there, so merge `canary` into a hook PR with `bun run hooks:merge-canary` (`packages/scripts/src/hooks-merge-canary.ts`), from a clean tree.
  It takes `canary`'s side of each conflicted bundle, commits the merge, rebuilds the bundles with the merged checkout's own `hooks-bundle.ts` and commits the rebuild on its own, then runs `--check`.
  A conflict outside `scripts/hooks/bundled/` aborts the merge and names its paths, and a merge that changes `bun.lock` stops after the merge commit for a `bun install` before you run `bun run hooks:bundle`.
  `bun run hooks:bundle` refuses to write while a merge is in progress (`MERGE_HEAD` set), naming that order, since bundles rebuilt inside the merge commit read to pr:merge's keeps-canary gate as lines lost from `canary`; `--check` runs during a merge once its conflicts are staged, since `git write-tree` reads no index that holds unmerged paths, and says so.
  pr:merge's `types` gate runs `--check` on the tree the squash makes when the PR touches `scripts/hooks/` or `packages/`, and refuses a bundle stale there ([packages/scripts/src/pr-merge/README.md](../../packages/scripts/src/pr-merge/README.md)).
  Each guard is its own build, since a build that also takes a guard it imports keeps that guard's `import.meta.main` block live, and the bundle would then judge by both guards' rules.
  Each bundled module reads `import.meta.dir` as its own source's folder, which the build writes against the checkout the bundle sits in (two folders up from `bundled/`), and `packages/settings/src/rendered.ts`'s `../../../extensions/core` URL lands on the repo root while `bundled/` sits three folders deep, as `packages/settings/src/` does.
  `role.ts`'s read of the session names still runs `setting.ts` in a process of its own, and keeps a fresh install's names when that read fails.
  `tests/scripts/hooks/refused-forms.test.ts` runs each bundle from a scratch checkout no `node_modules` reaches and holds it to its source's verdict on every row.
  A headless scan run from outside the checkout exports `PLAYGROUND_REPO` as the factory's checkout and passes `--settings` naming that checkout's `scripts/factory-settings.json`, so its guards run rather than exit 0: the board scan's loop takes the checkout from `beat.py`'s `checkout()`, the end-of-day scan's `scan.sh` from its own path.
  Four factory hooks act for every session: session-state writes every session's state, since the Dashboard is to show them all, no-off-palette-label guards every session's labels, since the label rule covers any label, no-desktop-owner-app guards every session's agent-desktop calls, since the owner's pointer and apps are the same whichever session drives them,
  and no-raw-delete guards every session's deletes, since a delete is final whoever runs it.
  Every other factory hook acts for a factory session alone, `PLAYGROUND_ROLE` or else its name in Claude Code's registry, placed by the roster's `kind` for that name and then by the factory's names (`scripts/hooks/role.ts`), so a session the owner opens in the factory's checkout passes them untouched.
  Claude Code loads project settings from the session's own folder alone, so a factory session restored where they lack the hooks (another checkout, an older one, a subfolder) is respawned with its settings (playbook's SPAWN.md, Role and settings), and `scripts/ops/up.py --sessions`, which reads each session's command line and its own folder's `.claude/settings.json`, names each one.

## Guard lists

- A guard that reads a list (no-desktop-owner-app's `desktop-owner-apps.json`, no-playground-leak's `playground-terms.json` and `slack-cleared.json`, no-release-comment's `release-owners.json` and spawn.sh's GLM gate's `glm-refused-sources.json`, all in core's `extensions/core/lists/`, and no-public-leak's,
  which only the extensions hold) loads it through `guardList` in `scripts/hooks/lists.ts` inside its check, at every call,
  and fails closed on it:
  on a machine with extensions (its data folder holds `extensions/`) the list comes from `extensions/hooks/<list>.json`, which every list write derives as the union of every scope's `lists/<list>.json` (the login's, each org's, then core's), read by `packages/settings/src/rendered.ts`, and never from this folder.
  A root that lacks the list refuses the guarded call, naming the file and the owner's command that writes it: `playground ext import --from-tree extensions/core/lists` for a list core ships, and `playground ext put <login> list <list> <file> --reason <why>` for one it ships none of (no-public-leak's, whose refusal also names its five keys), since that import never seeds it.
  The session tells its lead, and the dispatcher hands the owner the command to type as a `!` command in the dispatcher's terminal window, since the Dashboard's composer types no `!` command.
  A factory session writes nothing in the root itself and changes no list or guard setting through the CLI, but the two tuning values the Ops lead sets: [no-extensions-write](#no-extensions-write) refuses the rest, so a list changes only on the owner's own command.
  With no extensions, the list is core's file; with no file either, the guard takes its empty default.
  A list file that is there but empty, malformed or missing a key refuses the guarded call, extensions or not; an explicit empty list (`[]`, or every key empty) is the owner's choice and loads.
  A broken list refuses only the calls its guard checks, so every other call runs.
  Each refusal above, for a missing list and a broken one alike, follows one read rule.
  The leak guards and no-extension-repo-write give a list's or `policy.json`'s refusal to a call that names `curl`, `gh`, `git`, GitHub, Linear or Slack, unless it only reads, as `scripts/hooks/read-only.ts` judges it: a Bash line of exact read shapes from a closed set, each with its own option list, which takes a read over a `.git` path; an MCP call keeps the refusal.
  `GUARD_LISTS` in `packages/settings/src/rendered.ts` names every guard's list, and a root that lacks one refuses its guard, so a new guard list goes there and into core's `lists/`.
  A shell or Python script reads the set through `bun packages/scripts/src/playground/rendered.ts <file>`: exit 0 prints the path, 2 is extensions that lack the file, 3 is no extensions.
  A shell script that judges by a list of words reads it whole through `bun packages/scripts/src/playground/guard-list.ts <guard> <list>`, which takes `guardList`'s fallbacks and prints the words as JSON, or exits 2 with its refusal, as spawn.sh does for `glm-refused-sources`.
  Its tests are `bun run test:file tests/scripts/hooks/guard-lists.test.ts tests/scripts/hooks/read-only.test.ts tests/packages/settings/src/rendered.test.ts tests/packages/scripts/src/playground/guard-list.test.ts`.

## The folder a hook reads

- The shared reader (`scripts/hooks/shell.ts`) follows the folder a command runs in from the Bash tool's cwd through the line's `cd` steps, and holds two readings of it.
  `Env.cwd` takes a `cd`'s own target wherever the reader reads it: the reading every hook had before the proven folder arrived, kept so a hook that reads that field alone keeps the verdicts it had.
  `Env.cwdSure` names a folder only where the shell is sure to run that `cd` once, and `places` gives every folder the shell may be in otherwise.
  The three hooks below read the folder through `places`, and moving another hook onto it is a change of its own: a guard written as "refuse where the path is inside the folder I guard" reads a folder it cannot place as outside that folder, so it fails open until it judges each of `places`'s folders.
  Sure means, for `Env.cwdSure`: `cd` is the command's own first word, or a bare lower-case `builtin` or `command` runs it, since every other wrapper runs no builtin (`env cd`, `xargs cd`); it stands outside a pipeline, a background and an `||`'s right side (`cmd || cd x`);
  it stands outside every body the shell may run no time or many (`if`, `while`, `until`, `for`, `case`, a function, a brace group, `coproc`);
  and no count or loop runs it again.
  A reserved word counts in command position alone, so an argument that spells one (`echo if`, `grep -q done`) opens and closes no body.
  The folder a sure `cd` names has to be there for the reader to name it, but for a `cd` an `&&` joins to what follows: such a `cd` has certainly run and succeeded for each command that chain joins after it, since a `cd` that does not run, or that fails, stops the chain before them.
  So the reader names its folder whether or not the folder is there as it reads the line, which is how the worktree line of [AGENTS.md](../../AGENTS.md)'s Workflow rule reaches its new worktree (`git worktree add <path> && cd <path> && git merge origin/canary`, `mkdir -p <path> && cd <path> && git commit -m x`).
  That reading holds for the commands of that `cd`'s own run and no others: a run ends at each operator that runs the next command whatever the one before it did (a `;`, a newline, an `&`, an `||`), and there the folders from before the `cd` are the shell's again beside the one it named (`Env.cwdChain`, held under that run's own token in `Env.cwdChainToken`),
  since such a command runs whether or not the `cd` did (`false && cd <path>; git commit -m x`, refused in both folders).
  A command keeps the named folder by proof alone, its own run matching the `cd`'s, and every other command reads the folders from before it: an `&&` carries the run on, a pipeline's stages run with the command the run reached (`cd <path> && echo x | tee f`), and a group, a body or a substitution carries the run it was entered through,
  so `cd <path> && (git commit -m x)` keeps the folder while `cd <path>; (git commit -m x)` and `cd <path> || (git commit -m x)` read both.
  An `||` after a sure `cd`'s run hands the command it runs, with its own run, the folders from before the `cd` beside the one the shell was in (`Env.cwdOr`, `orElse`), since that command may run where the `cd` failed (`cd <path> || git commit -m x` and `cd <path> && make || git commit -m x`, refused from the main checkout).
  That holds for a subshell, a substitution or a script the command holds too (`cd <path> || (git commit -m x)`, `cd <path> && true || eval 'git commit -m x'`).
  The commands after that run keep both where the `||` follows the `cd` itself (`cd <path> || echo no; git commit -m x`), and go back to the folder the `cd` named where it follows a later command of the run, or runs an `exit` in the line's own shell, which ends the line where the `cd` failed (`cd <path> || exit; git commit -m x` runs).
  A `return` there keeps both folders, since `bash -c` fails a top-level `return` and carries on (`cd <path> || return; git commit -m x`, refused from the main checkout).
  An `exit` in a subshell or a pipeline ends that alone, a brace group piped on included, so the line keeps both folders after it (`cd <path> || (exit); …`, `cd <path> || exit | cat; …`, `cd <path> || { exit; } | cat; …`).
  A `!` in front of the `cd` keeps the folders from before it from the start, since it turns the `cd`'s own failure into success and the run carries on with the shell where it was (`! cd <path> && git commit -m x`); an even count of them reads as none.
  A script a command reads (`sh -c`, `eval`, `source`) reads with no run of the line's, since every command in it runs because that command ran; what the script's own trailing run leaves joins the line's on the way out, under the reading command's run,
  since a `cd` an `&&` made sure at the end of an `eval` or a `source` may not have run either (`eval 'true && cd <path>'; git commit -m x`, refused in both folders).
  A sure `cd` the script ends on is the line's for an `||` after the reading command (`eval 'cd <path>' || git commit -m x`, refused from the main checkout).
- A `cd -P` takes the folder the kernel lands in, each link followed before a `..` after it, where a plain `cd` folds the `..` by text (`cd -P <link>/..`); any `-P` among a `cd`'s or `pushd`'s options counts, whatever else is there (`-qP`, `-PL`, `-P -L`), since zsh lands physical for each.
- Every other `cd` leaves `Env.cwdSure` unnamed and keeps each folder the shell may be in: the folder before it, and each folder its target names, read against every folder the shell may already be in (`Env.cwdMaybe`).
  A relative target that climbs adds every folder above it wherever the shell may run that `cd` more than once: under a count (`repeat`, `timeout`), in a loop's body, between a loop's head and its `do` (a `while`'s or `until`'s condition, the body of zsh's short `for`, `select` and `foreach`), in a function's body, and in the script an `eval` or a `source` reads in such a place.
  A function's body, a brace group or any compound (`f() if …; fi`), runs once when the line names the function just twice, by its definition and one call outside every loop and body, a redirect's target being a file rather than a call.
  A name past a plain word (`f+`, `a/b`), a call through a word the reader cannot read (`$n`, `${b:1}`), a call it reads only once decoded (`$'\x66'`), and any `eval` or `source` on the line each read the body as one that may run again.
  A zsh head whose body is a brace group in its own words (`repeat 3 { cd ..; }`, `while true { … }`, `if true { … }`: `Command.opaque`) sets `Env.cwdAnywhere`, since the reader does not read that body.

  An `&&` before the loop (`false && while cd /tmp; do …`) may skip it, so its `cd` keeps the folder before it for every command after the loop, the ones the same chain joins included, though those run only once the loop has run.
  A `cd` through a steady variable reads the folder the variable names, in a hook that holds them (`Env.hold`, which no-main-checkout sets from `steady.ts`), so its climb is read from that folder; the start-folder reading the `cd` had stays beside it.
  A `cd` that opens a function's, a brace group's or a coprocess's body adds its folder to `Env.cwdHeld`, which no later `cd` clears, since the line may call that body at any point, and a relative `cd` after it resolves from those folders too, since the body may already have run.
  A `cd` later in the body is read where it stands, as one the shell may not run, so a sure `cd` after the body clears it, as `Env.cwd`'s own reading does too.
  `popd`, `cd -` and a bare `pushd` take every folder the line has named (`Env.cwdBack`).
  In a hook that follows zsh's `~-` (`Env.old` set), a `cd ~-` or `pushd ~-` takes those folders too, the start folder among them, and a `cd ~+` or `pushd ~+` each folder the shell may be in, each beside the folder literally named `~-` or `~+` and the one `Env.cwd`'s own reading lands in.

  A command in a body the shell may keep for a later call (a function's, a brace group's, a coprocess's: `Command.kept`) is judged both ways, its `~-` at the folder the reader names and as unknown, since it may run now or after a later `cd`.
  `Env.cwdUnread` marks a `cd` whose landing folder nothing names (`cd "$X"`, zsh's two-operand `cd`, a `popd` whose stack the reader cannot see).

  `no-extensions-write` refuses a writing redirect by a relative path there too, before a reader or an echo lets it run.

  It also refuses one that targets an app on the `desktop-owner-apps` guard list ([Guard lists](#guard-lists)): an `--app` value, or a `launch` or `close-app` target, matched without case and with or without `.app` or a path before it.
  Core's list is empty, and the owner's login extension holds the owner's apps, which change only by the owner's Approve on an Inbox `apps` decision, whose Approve has the Dashboard write the list (`.agents/dashboard/asks.md`).
  It reads the list and nothing else, so no flag, environment variable, `export`, `env` or write in the same call frees a call.
  The list changes only by the owner's own act, since [no-extensions-write](#no-extensions-write) refuses a session's edit of it in any call; a session that runs agent-desktop under another name breaks the rule, which a text hook cannot see.
  Its refusal names the two ways out: the owner runs the command with the `!` prefix in the dispatcher's terminal window, which runs outside the hooks, or takes the app off the list by approving the `apps` decision a session's lead posts.
  It refuses what it cannot read, as a call that may hide either: a word built from a variable or a substitution, the program in a variable in a call that names agent-desktop, arguments xargs appends, `batch`, `--window-id`, `notification-action`, an interpreter's code that names agent-desktop, and a script file run in a call that names agent-desktop.
  An interpreter's code passes when each agent-desktop in it sits in prose: a closed single- or double-quoted string, its opening quote after the start, whitespace or one of `( , = : + ;` and its closing quote before the end, whitespace or one of `) ] } , ; . + :`, with no quote, backslash, `$`, brace or newline, where the name follows a plain word that is no flag, launcher, shell or wrapper,
  and the string, read as a shell line the way the hook reads a Bash call, runs no agent-desktop, sources or runs no script file, and holds no `flock`, `setsid` or `watch` that names it.
  A `bun run` of a closed list of package scripts (`ask`, `thread`, whose entry points take argv as plain data and run nothing from it) reads that script's literal arguments as data, so a note that only names agent-desktop in prose runs.
  The allowance holds only from the main checkout (resolved by `mainCheckout()` in `packages/scripts/src/main-checkout.ts`, that file's precedence), whose tree [no-main-checkout](#no-main-checkout) keeps a session out of, so the script's `package.json`, its prebuild and its entry file (`api/hono/src/bin/dashboard-ask.ts`, `dashboard-thread.ts`) are files no session writes.
  `mainCheckout()` is resolved from the hook's own location, not the call's folder (the main checkout is the one tree [no-main-checkout](#no-main-checkout) keeps a session out of), so a planted `scripts/spawn.sh` cannot forge it.
  The effective cwd, after any `cd` in the line, must be that path itself (`realOf(cwd) === realOf(mainCheckout())`, so `bun run` reads the same `package.json` this gate checks, not a nearer one under a made folder), map the script to `bun --no-env-file packages/scripts/src/verify/prebuild.ts api && bun <entry>`, and hold the entry file.
  That prebuild takes a fixed target, so the arguments `bun run` appends reach the entry alone.
  Every other `bun run` keeps its verdict: a linked worktree whose `package.json` and entry match the main checkout byte for byte, a made folder even one that git-inits itself with its own `scripts/spawn.sh` or sits under `.claude/worktrees` with its own `package.json`, an unknown cwd (no cwd, or a `cd` to a variable or a substitution).
  So does any of these with an argument built from a variable or a substitution.
  A command that acts on the app in front when no `--app` names one (`snapshot`, `find`, `screenshot`, `press`, the window and notification commands) needs an `--app`; `snapshot` and `find` under a `--root` ref, and every ref action, pass, since the snapshot that gave the ref was checked.
  It reads agent-desktop behind `bash -c`, a pipe into a shell, `env` and the other wrappers `scripts/hooks/shell.ts` knows, `run-slot.sh --`, `npx`, `bunx`, `find -exec`, `flock`, `setsid` and `watch`, and a script file the call runs, by its text.
  Behind `flock`, `setsid` and `watch` it also reads each word holding a space as a shell line, and `watch`'s words past its options joined into the one line its `sh -c` runs.
  It loads the list only for a call that runs agent-desktop, and fails closed on it, its refusal naming the file and the route to the owner's list write that fixes it (tell your lead, and the dispatcher hands the owner the command); it fails open on a call it cannot parse.

## no-env-dump

- A factory session never prints its environment: `scripts/hooks/no-env-dump.ts`, run on Bash by [guards](#guards), refuses an `env` with no command (`env`, `env -0`, `env FOO=1`), `printenv`, a bare `set`, and a bare `declare`, `export` or `typeset`,
  since the environment holds tokens and the output lands in the transcript (13 Oct: a planning subagent's `env` printed this machine's GitHub and Slack tokens).
  `env VAR=x <command>`, `set -e` and `export VAR=x` run.
  It fails open on a call it cannot read, and its tests are in `bun run test:file tests/scripts/hooks` too.

## no-extension-repo-write

- A factory session changes no extension repository's git data or name: `scripts/hooks/no-extension-repo-write.ts`, run on Bash by [guards](#guards) and registered beside no-public-leak on the GitHub MCP tools, refuses such a write, since `ops:ext-sync` renders each one's `main` into the extensions root every guard reads.
  Its repositories are each `ext.repos` value in the root's `policy.json`, each scope clone's `origin`, which follows a rename, and `<login>/playground-<scope>` for each scope clone `ext.repos` does not name, under `PLAYGROUND_LOGIN` and the root's `login` file both, matched in any case and with percent escapes decoded, as GitHub decodes them.
  It reads every write through no-playground-leak's engine with `anyWrite` set (`inspectAs`), which refuses a write to one of them whatever its text, and a write whose target it cannot place.
  Those writes are a `git push`, `send-pack` or `subtree push`, a git alias expanded from its config (its body split as git splits it, quotes and backslashes included), a gh or `gh api` write, a curl to one on `api.github.com` or `github.com` (a read included), and a GitHub MCP write.
  Its gh writes include a DELETE, `gh pr merge` and `update-branch`, the publish-step group's `create`, `delete`, `edit` and `upload`, and `gh repo edit`, `rename`, `delete`, `archive`, `unarchive` and `sync <destination>`.
  It reads a push's target as git does: each push URL of the remote named, `--repo`'s value when none is named, else each push URL of every remote and each URL `remote.pushDefault` or the current branch's `pushRemote` or `remote` holds, another branch's left out.
  It reads the current branch's keys alone for a bare push, an alias of push included, written before any other git or gh command or a program it cannot name, in the folder the call starts in; after one, or in another folder (a `cd`, `git -C`), it reads every branch's `pushRemote` and `remote`, since the branch it pushes from may have changed.
  It reads that order as written, so a loop or a shell function that runs a branch switch before a push written earlier, a background push racing a branch switch (`git push & git switch …`), and a named program whose own code switches the branch (`make`, a script by its path, `source` or `.` of a file, `bun run`), are outside its reach.
  It reads a `gh api` endpoint and a curl URL where the request lands: dot segments resolved, `{owner}`, `{repo}`, `:owner` and `:repo` filled from the checkout, and curl's host and path read as a URL reads them, `uploads.github.com` with `api.github.com`.
  It cannot place, so refuses, a curl glob (`{…}`, `[…]`) on a GitHub host without `-g`, and a curl beside a word naming GitHub with a `Host` header, `--connect-to`, `--request-target` or `--resolve`.
  It reads that state when it checks the call, so after an earlier command in the same call changes it, it cannot place a push, an alias run or a write gh places by the checkout, and refuses it with the fix: run the setup in a call of its own first.
  Those changes are a `git config` write, `git remote add`, `remove`, `rename`, `rm` or `set-url`, `git clone`, `init` or `submodule`, `gh repo clone`, `fork` or `set-default`, `gh config set`, and any other command naming a `.git` path or a git config file.
  A config file it reaches only through `include.path` or a link, written in the same call by a command that names neither a `.git` path nor a git config file, is outside its reach.
  It cannot place, so refuses, a push with `-c`, `--config-env`, `--git-dir` or a `GIT_` variable in the call, a literal URL an `insteadOf` or `pushInsteadOf` prefix matches, a remote whose URL is a local path, a `!` alias, an alias with an unclosed quote or a trailing backslash, an alias `-c` sets, `gh alias set` and `import`, and a REST write to `repositories/<id>`.
  An `xargs` with no replace string appends arguments from its input, which the hook cannot read, so it refuses a push whose remote that input names and any curl that `xargs` runs, while a push whose remote is named (`xargs git push origin`), `xargs git add` and an `xargs` gh conversation verb pass.
  Under such an `xargs`, a gh write whose repository that input names and a `gh api` with a method, field or input of its own are refused, while a `gh api` with none reads and a pull request that input names is placed as a number is, by `-R` or the checkout.
  An `xargs -I` string is unplaceable too: it refuses a pull request the string puts in place, and a curl that may write (a method other than GET or HEAD, a form, an upload, or data without `-G`) to a URL it puts in place, while a curl that only reads passes.
  It refuses a repository made or renamed at one of those names, `*` standing for the account gh picks itself, and a name it cannot read counts as one.
  Those are `gh repo create` (its name or its `--source` folder's), `rename` and `fork --fork-name`, `gh api`'s repo PATCH with a `name`, `generate`, `transfer`, `forks` with a `name`, `user/repos` and `orgs/<org>/repos`, and MCP `create_repository`.
  A push of branches other than the default passes, the policy's `branchPush`: a `git push` run plainly that names its remote and one or more refspecs it reads as literals, each writing a branch other than `main`, `master` and the remote's `HEAD`, its flags only `-u`, `-f`, `--force-with-lease`, `--force-if-includes`, `--no-verify`, `-n`, `-q` and `-v`.
  It refuses every other push to one of them: one with no refspec, a refspec naming `HEAD` or `@` as its branch, a tag, another `refs/` path, a glob or a delete, `--all`, `--mirror`, `--tags`, `--follow-tags`, `--repo` or `-o`, a bare name a local tag also holds, and a push in a clone whose `remote.<name>.push` remaps its refspecs.
  A destination written without `refs/heads/` that is already a tag on GitHub updates that tag on a force-push, and a bare name whose tag an earlier command in the same call makes (`git tag x && git push origin x`) pushes that tag, since it reads the tags before the call runs; both are outside its reach and never reach the default.
  A remote given by its URL takes `main` and `master` alone as its default, which the sync's `main` is.
  `gh issue develop` and the head `gh pr create` pushes pass too, since the sync reads only `main`.
  `bun run ext:merge <owner>/<repo> <n>` (`packages/scripts/src/ext-merge/`, `--help` lists its gates) is the one route from such a branch to the default: it squash-merges the PR at its head once the signed-in account opened it, a reviewer session other than its author has scored it 5/5 there and its checks have passed, and its command names neither git, gh nor curl, so the hook lets it run.
  Issue and pull request conversation passes: `gh issue` and `gh label`, `gh pr create`, `comment`, `edit`, `review`, `close` and `reopen`, `gh api` on `issues`, `labels` and `pulls` but a pull request's `merge` or `update-branch`, and the matching MCP tools.
  A commit is refused only in a clone of one of them, and every call passes on a machine with no extensions root.
  There a commit passes on a branch the push rule lets through, since it changes only the clone: HEAD, read before the call runs, is a named branch other than `main`, `master` and every remote's `HEAD` branch (`branchHead`).
  The call also carries no `-c`, `--config-env`, `--git-dir` or `GIT_` variable and runs no git, gh or unnamed program before the commit (`movedBefore`), since any of them could move HEAD or where git writes.
  A commit on the default, on a detached HEAD, or after `git add` in the same call stays refused, so a session commits as a call of its own.
  Its refusal names the two routes: a commit on a branch, as a call of its own, that branch pushed by its remote and refspec and landed by `bun run ext:merge`, and for any other write the owner typing the command as a `!` command in the dispatcher's terminal window, which the dispatcher hands the owner when a session tells its lead; no flag, environment variable, role or note frees a call.
  A program it does not know may run git, gh or curl named among its words (`uv run git push`), and a word whose path ends in `/git`, `/gh` or `/curl` reads as that command too, since a folder argument and the command run by path look alike; that refusal says so, names a path not ending that way as the way through for a folder or file, and says the command written by its own name is read the same.
  It fails closed, as the leak guards do and only on a call that may write, when `policy.json` does not read or no login names the default repositories, and on any call that may write when the reader fails on it (a script nested too deep or too large) or is still reading it at its 8s deadline, inside the hook's 15s timeout, whatever it names.
  `withDeadline` alone does not bound a hook whose time goes on spawns, since `tick()` reads the clock only in lex and walk steps, so each command it visits calls `pastDeadline()` in `scripts/hooks/shell.ts`; a Worker timer, as no-extensions-write runs, is the other route.
  It refuses a closed list of write forms, the literal ones its tests pin, so a same-user session can still get past it by a form outside that list, such as a script file it writes and then runs.
  Outside its reach are a program whose own code pushes or calls the API (a script by its path, `bun run`, `bun -e`, `python -c`, a binary, an HTTP client other than curl such as wget or httpie, and GNU `parallel`, which appends its input as `xargs` does), a fork that keeps its source's name, and a gh alias set before it.
  A pull request named by a shell value (`gh pr merge $N`) is placed as a number is, by `-R` or the checkout, so a pull request URL held in a variable is outside its reach.
  The words a plain `xargs` appends are read for neither flags nor a pull request URL, so a `gh api` read or a `gh pr merge` it runs can carry a method, a field or `-R` in that input, and `echo <ext>/pull/1 | xargs gh pr merge` passes in a clone of another repository.
  In a checkout it cannot resolve (`cd $X`, `git -C $X`), it reads a git alias from the global and system configs alone, so an alias in that checkout's own config is outside its reach.
  A `bash -c` script over 128 KB that names git, gh or `repo` is refused when the reader fails on its size, which waits on the reader's script-size work to narrow.
  `gh workflow run`, `gh secret set` and `gh repo deploy-key add` pass, since none writes a branch or the name itself, while their `gh api` routes are refused.
  A GraphQL mutation, which names its repository by node id, and a curl whose URL the run computes are refused only when the data they send names one of the repositories, so a curl URL with a computed part (`$U`, `$(…)`) passes even when its literal part names one; a URL in a curl config file (`-K`, `~/.curlrc`) and a redirect a server answers with (`-L`) are unread.
  An `ext.order` name with no clone and no `ext.repos` entry is not guarded, and the sync does not push it either.
  Its tests are `bun run test:file tests/scripts/hooks/no-extension-repo-write.test.ts`.

## no-extensions-write

- A factory session changes nothing a guard reads to allow or deny a call: `scripts/hooks/no-extensions-write.ts`, run on Bash by [guards](#guards) and registered on the file tools (Edit, MultiEdit, NotebookEdit and Write), guards the extensions root (`extensionsDir` of the data folder) and every file under it.
  Each guard reads its list and `policy.json` there, each scope's `lists/` and `settings.json` render into them on the next write (its `git add -A` takes a hand edit along), and a root that is gone sends the guards back to core's smaller lists.
  Two fences hold the root: a sandboxed session (a probe, or a `--sandbox` start) meets spawn.sh's sandbox entry, the root under `denyWrite`, so the kernel refuses its write whatever the shell spelling, and every other session meets this guard.
  Under both sits the root's file lock, the fence for every process: macOS's user immutable flag on the root and everything under it (`chflags -R uchg`), so a plain write meets EPERM.
  The CLI is its lifter: `withLock` in `packages/settings/src/folder.ts`, which every writer of the root goes through, lifts the part of a locked root its write touches, locks it again after and logs both steps' time, and `playground ext lock` and `playground ext unlock` set and clear it.
  A write to one scope that leaves the root's own files alone lifts that scope's folder alone, so every other scope stays locked while it runs; a write that touches the root itself (its `policy.json`, its `login` file, a `hooks/` list or a new scope) lifts the whole root.
  Each lift appends one line to the data folder's `ops/log/ext-lock.log`: its time, the folders it lifted, the lift and relock's duration, load5 and the caller (its entry script, with the session's role when it has one), and a write that fails still relocks and logs its line.
  The walk skips a file inside its tree gone by the time it reaches it, since git maintenance can remove one of a scope's `.git` files mid-walk, and fails on a missing tree or any other error.
  The ops tick's extensions-lock beat locks a root that stands unlocked, at its top or at a scope folder a write killed mid-way left lifted, every 5 minutes (playbook's LIFECYCLE.md); a machine with no `chflags` (Linux) has no lock.
  It refuses a file tool's path in the root, `~` expanded, and a redirect into it, a group's, a subshell's, `exec`'s, a shell's, `eval`'s, `source`'s, `.`'s, `cd`'s, `pushd`'s, `popd`'s or a bare one included, and zsh's `>!` and `>>!` with them.
  A command run through `run-slot.sh` is read as the words after its `--` (`slotWords`), on a copy of the line's env: run-slot runs them in a process of its own, so a `cd` or `pushd` there moves no folder for the commands after the call, while a command among those words is judged where its own `cd` lands.
  It refuses any program but a reader that names the root, a path in it, a folder above it (`~/.playground`, `~`) or a glob there (`*`, `?`, `[…]`, `{…}` or zsh's `(…)`, in a redirect's target too), links followed, in any word: the program word, an option's attached value (`-o<path>`, `--out=<path>`), a variable the call sets (`GIT_DIR=<clone>`), or the stdin xargs hands it.
  Each stdin word is judged as written and as xargs reads it: with no `-0` or `-d`, xargs drops a pair of `'` or `"` and keeps the character after a backslash, so `.play'ground'` reads as `.playground`; a quote left open makes its stdin text it cannot read, refused under a remover.
  A word read as GNU's `-a` (`--arg-file`), another option's value spelled like it included (`-E -a`), hands xargs words from a file the hook cannot read, while its stdin is still judged for the root as xargs' words, so a remover under one is refused anywhere, as one fed text it cannot read is, and a writer's file words count after an unread `cd` (below).
  It refuses any program but a reader whose words or heredoc hold the root's path as text, whole or as seen from a folder above it the command runs in, so an interpreter's script and a commit message that names it are refused alike, as is an inline body that names a gated call (`playground ext sync`); write such text to a file and pass the file.
  `tee`'s heredoc is data it copies to its targets, which are judged as every writer's are, so a body naming the root runs into a file outside it (an ops job's row in `jobs.json`), wherever `cat`'s heredoc runs: on a line the hook reads as feeding no code (below).
  A commit message holding shell-like text (`cd <path> && make || true`), which the hook can read as words of the line, goes through `git commit -F <file>`, the file written with the Write tool first.
  It walks an unquoted heredoc's body as the shell does (the shared reader, above): a `playground` call in a command substitution or between backquotes there is judged as one typed on the line, since the shell runs it while it reads the body, while the same text under a quoted delimiter or behind a backslash is text the shell never runs, so that line runs.
  The readers are `[`, `cat`, `cmp`, `diff`, `echo`, `grep`, `head`, `jq`, `ls`, `printf`, `readlink`, `realpath`, `shasum`, `stat`, `tail`, `test` and `wc`;
  `rg` with no `--hostname-bin` or `--pre`; `find` with no `-delete`, `-exec`, `-execdir`, `-fls`, `-fprint`, `-fprint0`, `-fprintf`, `-ok` or `-okdir` action; and git's `blame`, `cat-file`, `diff`, `grep`, `log`, `ls-files`, `rev-parse`, `show`, `status` and `worktree list` with no `-c`, `--config-env`, `--exec-path`, `--ext-diff`, `-O`, `--open-files-in-pager`, `--output` or `--textconv`.
  A reader run with `EDITOR`, `GIT_*`, `LESSOPEN`, `PAGER` or `VISUAL` set in the call is judged as any other program, since each makes it run one, and so is one with `HOME` or `XDG_CONFIG_HOME` set, since each points git at a config file that can.
  A reader is its command's own first word, a reserved word before it (`!`, `then`, `do`) skipped (`ownFirst` in `scripts/hooks/shell.ts`), so a reader behind a wrapper or an assignment (`timeout 5 grep -r x .`, `LC_ALL=C grep -r x .`) is judged as any other program, and from `~` one naming `.` is refused; run it bare.
  A command of reserved words alone (`fi`, `done`) runs nothing; one with no program read otherwise (`sudo -s`, a group, a redirect or an assignment alone) has its whole line judged.
  A line holding a command that runs its input as code (`stdinShell` and `codeFed` in `scripts/hooks/shell.ts`) runs whatever is printed into it, so from every folder no reader on it is spared: a shell given no script or stdin's name as one (`sh`, `sudo bash`, `sh -`, `sh /dev/fd/0`), a `source` or `.` of stdin's name, a root shell with no command of its own,
  a shell, an `eval`, a `source`, a `.` or a program the hook cannot read (`$SHELL`) that a pipe or xargs feeds, whatever its arguments, an interpreter it feeds (`node`, `python3.12 -c '…'`, `bun -`, `xargs python3`) unless it runs a script file or a module of its own past options its family's table names (`node x.js`, `python3 -m json.tool`, any other option reading as code),
  and a loop or group whose body holds one.
  In that reading, every env's split string, a quoted env's and one behind another wrapper's included, is read as the words it runs (`env -S 'sudo -s'`), with a `\_` or a whitespace escape splitting, a quote or another backslash dropped, and a `${…}` read as a word the hook cannot read.
  env's long options are read by any unique prefix (`--split='sudo -s'`, `--u X`), and `-a` and `--argv0` take a value, as GNU env reads them, and a lone `-` is read as the wrapper lines at the top say.
  A root shell is sudo's `-s`, `-i`, `--shell` or `--login`, doas's `-s`, or pkexec with no program of its own (`<reader> | pkexec`), alone or in a cluster of the wrapper's flags ahead of its first value-taking letter (`-Es`, `-su root`, `-su#0`; in `-us` the `-u` takes the `s`).
  Such an option counts behind any wrapper and quoted or not (`'-s'`, `-su'root'`, `'sudo' -s`), and an option or a program in a variable counts as one.
  `su` not handed a command is a root shell, busybox's `su` applet and one behind any wrapper included (`<reader> | su`, `<reader> | su -s /bin/sh root`, `<reader> | busybox su`).
  `su` reads as handed one only by `-c` or `--command` with its command, after option words of `-f`, `-l`, `-m` and `-` alone, so any other option word, one taking a value included, and any word before the `-c` it cannot read (a variable, a substitution, a glob) reads as a root shell.
  A line that runs its own command after another option (`su -lc <cmd>`) is then read as a root shell on purpose, so an option's value never hides a `-c`.
  Each word is read as an option of every privilege wrapper before it: the first unquoted word naming one, and any word whose unquoted value is `sudo`, `doas` or `pkexec` (`'doas' sudo -i`, `doas sudo -i`); any other word ending in a wrapper's name (a quoted path, or a path after the first wrapper) is read as an option, never as a wrapper.
  A long option's unambiguous prefix counts as that option, as sudo's getopt_long reads it (`--sh`, `--lo`), while sudo itself refuses the ambiguous `--s` and `--l`.
  The root shell is looked for under each reading of the wrapper's options (above); once the parse runs out of readings, any sudo, doas, pkexec or su among the command's words counts as a root shell and any shell's name as a shell.
  Every spaced text of every program on such a line, each `\n`-separated part of it and an awk program's strings are read as command lines.
  A root shell's stdin is read as its script, and one the hook cannot read (a download, a file it cannot see, a bare `sudo -s`, one only the shell's own reading reaches, as [the stdin lines at the top](#the-factorys-hooks) set out) is refused: run its commands as calls of their own.
  An `eval`'s words are its script, so an `eval` is refused the same way, in any folder and any shell and behind `builtin` or `command`, unless each of its words is quoted text or plain characters (letters, digits, `_ . / = - , : @ %`; `unreadWord` in `scripts/hooks/shell.ts`).
  Any other character can fill a word with code the shell runs: a variable, a substitution, or a glob a shell option makes of it (`*`, zsh's `^x`, a ksh `@(x)`), which a file's name then fills.
  For any program but a reader, each text that holds a space (a word, the value after its `=`, an option's attached value, a variable the call sets or exports) is judged as a command line of its own, a leading `!` dropped, since a program may run it (`watch`, `tmux`, `ssh -o ProxyCommand`, `rsync -e`, a git alias, a pager).
  An inline evaluator's program (bun's or node's `-e`, `--eval`, `-p`, `--print`, `-pe` or `-ep` ahead of any script, agent-browser's `eval` after its options) is judged with each regex literal masked (`maskRegexes`), since a regex is neither a path, a glob nor a redirect.
  Its strings, templates, comments and other punctuation are judged as written.
  The mask applies only where every folder the shell may be in lies outside the extensions folder and each folder above it, such as a worktree, so from the home and the data folder the program reads exactly as canary reads it.
  A `/` opens a regex only after a token that an expression must follow (`REGEX_AFTER`: opening punctuation, a binary or prefix operator, `=>`, a reserved word such as `return`).
  After any other token the scan masks nothing, since a `/` there may divide: `)`, `]`, `}`, a postfix `++` or `--`, TypeScript's non-null `!`, a generic's `>`, a member named like a keyword, `await`, `yield` or `of` as a name.

  It finds the row by the session's registry name, the same read role.ts makes, and takes its PRs from the row's `pr` and the pull URLs in its `prs`.
  A PR is outside when its author is not the repo's owner on a repo a user owns, read once with `gh api repos/<repo>/pulls/<n>` and kept in the data folder (`hook-outside-pr/`); a PR it cannot read counts as outside, that failure is kept for an hour, and the reason names the PR and its kept file, whose removal makes the next call read it again.
  An org repo's PRs are its colleagues', so a checker of those, or of the owner's own PRs, runs them as before.
  A row with no PR, or only an issue's URL, is read mode too, and its reason names the one-line fix its worker or lead runs, `bun scripts/roster.ts set <name> pr=<pull url>`, since a row written before `spawn.sh` required a checker's `--pr <pull url>` can name none.
  In read mode a Bash or Monitor line passes only when every command on it is on the allowlist, so a command the hook cannot read is refused.
  The allowlist is the script's constants, each with its why beside it (`UTILITIES`, `GIT_READS`, `GH`, `INTERPRETERS`, `PLAYGROUND_READS`), plus `read-only.ts`'s `readsWords` and `sed` printing a range or making one substitution that writes no file.
  `gh` passes with no `--`, since gh's clone hands git every option after it, and never as a checkout: `gh pr checkout` or `gh pr co` wherever the verb sits among gh's flags, and `gh issue develop`.
  git passes only where it would find a repository with a work tree: the first folder up from where it runs, its symlinks followed as git follows them, that holds `.git`, or `HEAD`, `objects` and `refs`, decides, since a PR can ship the second as plain files whose config names programs a read runs (`diff.external`).
  git takes one `-C` and no other option before its subcommand (`-c`, `--git-dir`, `--work-tree`), and no `GIT_DIR` or `GIT_WORK_TREE`, set on the call or exported, so the folder the hook walks is the one git uses.
  git takes no option that starts a program or writes a file (`GIT_RUN_NAMES`), by its full name or any start of it, since git takes an unambiguous start (`--open=` for `--open-files-in-pager`).
  It holds git's literal moves, each with `-q` allowed: `clone <github url> <dir>`, `worktree add [--detach] <path> <rev>` and `worktree list`, and `checkout` or `switch --detach <rev>` where neither the folder nor one above it up to its work tree's root holds `node_modules` for a git hook's lefthook to load.
  `fetch` takes a remote's name or a GitHub URL, never a path, which names a repository the PR can ship, and only options that name no program or source (`FETCH_OPTIONS`, `--depth=<n>`), and `remote` takes no verb but `get-url` and `show`.
  It holds a skill's script under the data folder's `orgs/*/skills/` or the main checkout's `extensions/*/skills/` (code-review-loop's `state.ts`), run by its path or by node, python or python3, judged where the path resolves, so a `..` climb out of those folders is refused; bun by name is left out, since it reads the folder's `bunfig.toml`, whose preload runs first.
  A script run by its path is judged by the runner its first line names (`runnerOf`, which reads `env`'s options, assignments and `-S` as env does).
  One whose runner reads no folder's files (bash, node, python, python3, sh or zsh), or that has no shebang, passes anywhere.
  Any other (bun, bun-canary, an `env` line read as another word, a script the hook cannot open) passes only where the working folder sits in the main checkout's own tree, the first folder up from it holding `.git` being the main checkout.
  bun reads files from the folder it runs in before the script (`bunfig.toml`'s preload, `.env`'s variables, and whatever a later bun adds), so the rule judges the place rather than each file; the PR's clone at any depth, a scratch folder outside every work tree and a folder the hook cannot read are refused, and a reviewer runs `state.ts` from the main checkout.
  It holds a shell's `-c` script, whose commands are judged one by one, and a shell running such a skill script; `shell.ts`'s `visitShells` shows the hook each shell a line starts, since the walk follows a script file it cannot read as an empty one.
  It holds the factory's own run-slot, `<data folder>/ops/run-slot.sh`, whose command after `--` is judged in its place, and the `playground` command's read verbs (`PLAYGROUND_READS`) in a folder with no `bunfig.toml`, since it runs under bun and `playground add` starts a session no read mode holds.
  A program named by a path, a variable set on a command, and a bare assignment, a loop or a `read` that sets a variable the session exports (`PATH`) are refused, since each can run a file the PR holds.
  Its reason names the reads (the Read, Grep and Glob tools, `gh pr diff`, `git diff` and `git show <rev>`) and asks the verdict to say the code was read, not run, scored on the PR's own GitHub checks.
  A checker in read mode cannot run the PR's tests, by design, so CI is its test signal.
  Its tests are `bun run test:file tests/scripts/hooks/no-outside-pr-code.test.ts`.
  Its registration in both settings files lands in a later ship than its script, as [Registered in both settings files](#registered-in-both-settings-files) says.

## no-prepare-write

- A prepare-only session, one whose roster row reads `mode=prepare`, works a ticket the org has registered and not yet posted: its brief keeps it to the local branch until it claims, and this check holds it there.
  An org's start job sets the mode at the prepare-only start (`roster.ts set <session> mode=prepare`) and clears it at the claim: the session's waiter runs `roster.ts set <session> mode=` the moment before it prints its Claim line, so the claim's own assign runs at once, and the job's next beat clears it too, as a backstop.
  A clear that fails still prints the Claim line, which then tells the worker to retry a refused assign after that beat, since the refusal is not final.
  The mark and this check each do nothing without the other, so the job's revision and this check go live in either order.
- While the mode stands, `scripts/hooks/no-prepare-write.ts` refuses a factory session's writes that reach the org before the claim, a closed list, each in any form the shared reader (`scripts/hooks/shell.ts`) finds:
  - `chat_post_message`, a chat post, on a Slack server;
  - `create_branch`, `create_or_update_file`, `create_pull_request`, `delete_file`, `merge_pull_request`, `push_files` and `update_pull_request_branch` on a GitHub server;
  - `gh api` with a write method (any but GET or HEAD) to `repos/<owner>/<repo>/` then `contents/<path>`, `git/refs`, `git/refs/<ref>`, `merges`, `pulls`, `pulls/<n>/merge` or `pulls/<n>/update-branch`, the endpoint in any spelling (a leading `/`, the API host), or to an endpoint it cannot read;
  - `gh api graphql`, the endpoint in any spelling (`/graphql`, the API host, an Enterprise host's `api/graphql`), whose query names `createCommitOnBranch`, `createPullRequest`, `createRef`, `deleteRef`, `mergeBranch`, `mergePullRequest`, `updatePullRequestBranch`, `updateRef` or `updateRefs` anywhere in its text, a string or a comment included, or whose query it cannot read,
    since a match that over-refuses fails safe;
  - `gh pr create`;
  - `git push`, past git's own options (`GIT_TAKES`, through no-stash's `gitCommand`), since a prepared branch on the org's remote reaches the org before the claim, and behind any other program but `echo`, `printf` and `man`, which only print it;
  - `save_comment`, a tracker comment, and `save_issue`, a tracker issue save (an assign or a state change), on a Linear server.

  Every other call runs: reads, local git, a GraphQL query or any other mutation, every other `gh api` write (a `git/commits` or `git/trees` POST, which moves no ref) and every other gh call.

- It is a check with no process of its own: [guards](#guards) runs it on Bash, and [no-playground-leak](#no-playground-leak)'s process runs it first on the MCP tools, since that hook's matcher already takes every GitHub, Linear and Slack tool, so it went live in one ship ([Plan a hook's ships](#plan-a-hooks-ships), step 1).
- It fails open, since the session's brief is the first bar: a session the registry or the roster does not hold is not marked, and a read that fails, a roster that does not parse among them, lets the call run and writes one JSON line naming the session, the tool and the error to the data folder's `ops/no-prepare-write.log`, so a broken read shows.
  Its tests are `tests/scripts/hooks/no-prepare-write.test.ts`.

## no-raw-delete

- A delete goes to the 7-day trash through `playground rm <path>`, a worktree through `playground rm --worktree <path>` (with `--discard` once its PR has merged or closed, whatever it holds), so a delete aimed wrong comes back (2 Nov: two code-review sub-agents each deleted recursively in their own scratch folders, though their prompts said to run none).
  The trash takes up to 5,000 files or 2 GB, so the refusal also names the lead's cleanup for a bigger tree and `bun install` for a `node_modules`; an ended session's whole `scratchpad/<folder>/` skips the file count and keeps the 2 GB cap.
  Inside `~/.playground`, `playground rm` clears two places and refuses every other path: the caller's own `scratch/<name>/` and `scratchpad/<name>/`, by the session name Claude Code's registry gives it, and an ended session's whole `scratchpad/<folder>/`.
  A folder counts as ended when it is a real folder no live roster row names as itself or as `<folder>-<role>`, so Ops clears a closed session's folder on a lead's word (`endedPadOf` in `packages/safe-delete/src/index.ts`).
  `scripts/hooks/no-raw-delete.ts`, run on Bash by [guards](#guards), acts for every session and every sub-agent, whose hook input carries its own `agent_id` beside its parent's `session_id`, and refuses with a reason that names `playground rm`:
  an `rm` or GNU rm's `grm` with `-r`, `-R` or `--recursive` (any prefix GNU rm takes, anywhere among its words), `find -delete`, `rm` under xargs, `gxargs` or `parallel`,
  `find -exec`, `-execdir`, `-ok` or `-okdir` and `fd -x`, `-X`, `--exec` or `--exec-batch` running `rm` behind any wrapper, fd's option last in a cluster of its flags that take no value too (`-HX rm`) and its value attached too (`--exec=rm`, `-xrm`),
  `git clean` with `-d`, `-x` or `-X` and no dry run, with or without force, since `clean.requireForce` can be off,
  `git worktree remove` with `-f` or a prefix of `--force`, `rimraf` with or without a version (`rimraf@5`), del-cli (`del`, `del-cli`) in a program's place or as a package runner's package (`npx del-cli`, `pnpm dlx del-cli`), so `redis-cli del` runs, `rsync --delete` or its `--del` alias, `rsync --remove-source-files` or its old `--remove-sent-files`,
  `shred` or `gshred` with `-u` or a prefix of `--remove`, `tar` or `gtar` with a prefix of `--remove-files`, `chmod -a` or `-N`, which strip a file's access entries, and `chflags`.
  An `rm` word that may spell `-r` is refused as one it cannot read: a variable or a substitution, a brace (`-{r,f}`) and a glob in an option; so is a program word it cannot read (a variable, a brace, a glob such as `/bin/r?`) given `-r`, or led by an unquoted word it cannot read (`$RM $FLAGS`).
  An unquoted variable alone in a program's place (`$c`, `${c}`), set or exported earlier in the call to a line with a space, is read as that line, since bash splits it into words (`c="rm -rf x"; $c`); a quoted one (`"$c"`) stays one word.
  A recursive delete inside an unquoted heredoc body's command substitution or backquotes is judged as one typed on the line (the shared reader's heredoc rule, at the top), in a tab-stripped heredoc, any of several on one command, one on a descriptor other than stdin or one feeding a loop alike, since the shell runs it while it reads the body; under a quoted delimiter it is text.
  A readable word ends that lead, so `$T git clone $S/x` runs, and a glob holds `*`, `?` or a closed `[…]` the shell sees outside quotes, a half-quoted one (`'/bin/r'?`) included, so test's own `[` (`[ -n "$R" ]`) is no glob.
  A plain `rm` runs when every path it names sits inside the session's own worktree (the `.claude/worktrees/<name>` folder its `cwd` is in) or its own scratchpad (the `scratchpad` folder under `/tmp/claude-<uid>/` named by its `session_id`), each path resolved through its links.
  Any other path is refused, so a session working in the main checkout removes no file there, as the **main** rule keeps that checkout to upkeep.
  It reads a delete wherever the shell runs one, through `shell.ts`'s walk (wrappers such as `nohup` and `sudo`, `sh -c`, `eval`, substitutions), and more ways:
  the words after run-slot's `--`, each word of `screen` or `tmux` that starts no option as the command it runs, the script `at` or `batch` takes from stdin or `-f`, and every program it judges named among another program's words (`arch -arm64 rm -rf`, `busybox rm`, `npx rimraf`);
  a printer's or a search's words stay text.
  A root shell's here-string, heredoc, input file or process substitution (`sudo -s <<< '…'`, `su <<'EOF'`) is read as its script, as the shared reader runs a piped one, each part it cannot read (an unset variable, a download's output) taken as a line break so the rest is still judged, as a plain shell's script is.
  A job a redirect (a duplicate onto fd 0 included), a pipe or `-f` feeds `at` or `batch` that it cannot read is refused, a program's output included (`at now < "$F"`, `ls | at now`), while `at -l` runs.
  A word it cannot read among those words, given `-r` after it (`arch -arm64 $R -rf`), is refused as a program it cannot read; a data program's words stay text (`gh pr checks $N -R <repo>`).
  A plain `rm` met that way is judged for recursion alone, so `docker rm -fv "$ID"` and `bun rm <package>` run.
  It also reads every word holding a space, the text after an `=` and a leading `!` too, as a command line of its own.
  The programs in its `DATA` list (printers, searches, `sed`, `awk`, `jq`, `gh` and the interpreters) take text as data, so their words stay text, and git's only command line is a `-c alias.<name>=!…` value, so a commit message or a `git grep` pattern stays text.
  `agent-browser eval`'s script is JavaScript the page runs, so its words stay text too (`agent-browser eval 'a?.b ?? 1'`), in the literal form alone: the bare word `agent-browser` with `eval` as its first argument or right after a `--session <name>` or `--session=<name>` (`browserEval`), on a call whose every command opens with that bare word (`scriptStaysText`).
  Any other command on the call keeps the spaced-word rule for each eval on it, such as a function, alias, hashed name or `PATH` the call defines, a prefix assignment, a group or a pipe into another program; so do agent-browser by a path or behind a wrapper, any other option before `eval`, an eval line read out of another command's word, and agent-browser's other commands.
  It is a speed bump, not a wall: a script file a session writes and runs passes it, as does an interpreter's own delete call (`fs.rmSync` in `bun -e`), and only an OS sandbox contains those.
  It fails closed only on a call it cannot read that reads as a delete, and its tests are `bun run test:file tests/scripts/hooks/no-raw-delete.test.ts tests/scripts/hooks/refused-forms.test.ts`.
  The repo's own scripts are held by `tests/no-raw-delete.test.ts` instead, which reads the repo's text and fails on a raw recursive delete outside its allowed folders and named carve-outs.
