# scripts/ops

The factory's ops scripts, moving here from `~/.playground/ops`. The code lives here; everything it writes (heartbeats, pid files, logs, `jobs.json`, the outbox) stays in the state folder, `ops` in the data folder (`~/.playground/ops` by default). `run-slot.sh` lives here too, linked into the state folder by `scripts/link-skills.sh` (its state, `run-slot*`, stays in the state folder, or `RUN_SLOT_OPS`), and so are `notify.sh`, which the Checks lane and the merge train call by that path, and each script in `checks/`, `merge-train/` and `usage/`, linked into its folder in the state folder (`ops/checks/` and so on), where its state stays; every job not listed below still runs from the state folder until it moves. Moving the live jobs onto these copies is a cutover Ops runs, pointing three places at the main checkout's `scripts/ops`: `jobs.json`'s commands, `~/.zshrc`'s `--once-per-cmux` hook (which runs `up.py`'s jobs pass after a cmux restart), and ops-sweep's `up.py` call. Until all three move, up.py's cmux ancestry check does not run (a PR tracks the cutover). Every script that names the factory's checkout takes it from `$PLAYGROUND_REPO` first: a Python job through `beat.py`'s `checkout()`, else the main checkout of the folder the job runs in, else that of the checkout `beat.py` sits in, a TypeScript job through `packages/scripts/src/main-checkout.ts`, else the main checkout of the checkout its code sits in, and spawn.sh before its own `$MAIN`; both lookups end at `playground` in the folder that holds that checkout, so no path names a person's folder. `beat.py` is linked into the state folder with the other moved scripts, and `tests/scripts/ops/checkout-path.test.ts` refuses a fixed checkout path in `scripts/ops/`, `scripts/spawn.sh` and the `ops-*` jobs. ops-sweep runs from `packages/scripts/src/ops-sweep/` (`bun run ops:sweep`), its state staying in `ops/sweep/` in the state folder.

## run-slot

How run-slot runs the factory's **slots** rule (`extensions/core/rules/slots.md`), beside its row above.

- Slots open one to four as the load allows, each giving 2 load units; a run counts its item's size, small 1, medium 2 and big 3, and `run-slot.sh size <your name>` prints yours: `RUN_SLOT_SIZE`, else small for a `commit-<worktree>` pre-commit build, else your roster entry's `size` or your worker's, else plan.json's item for your branch's issue, else medium.
- A quarter of the units, at least 1, stays for small runs, the work org's runs and the runs that gate a merge.
- The queue serves a run whose roster entry, or its worker's, has a `pr` or `repo` on the work org first; then Checks for a PR in `merge-queue.json`'s ready line, by `goAt` and then `readyAt`; then the other runs that gate a merge (Checks, local CI, the merge train, the dashboard's build); then the rest.
  Each class goes small before medium before big, oldest first, and a waiter whose run does not fit yet lets the next one that fits go; a lead's `run-slot.priority` wins over all of them.
  A ticket with no rank, and one that has waited 20 minutes, keep their place by age, so no newer run passes them.
- A type check goes to the box only from a checkout's root, since one from a subfolder reads the other workspaces' `dist`, which the box lacks, and it stays on the Mac while the checkout lacks a package's `dist`.
- `RUN_SLOT_HERE=1`, in run-slot's environment or as an `env` word of the command, keeps a run on the Mac, where it waits for a slot; a docs-only PR's touched-test run takes it while the box queue is long, and so does a run that sets `TMPDIR` to a Mac path, since the box has no `/private/tmp`.
  The box takes its runs first come, first served, so the queue's merge-first order holds only for runs that wait here.
- `run-slot.clone-off` holds a `node_modules` clone until memory passes spawn.sh's gate and both the 1-minute and 5-minute loads are under 30, since load5 lags a fresh spike; `run-slot.clone-allow` lists grep patterns (`tester-.*`) for the sessions whose clones still go.
- `git fetch`, `git rebase` and a `git merge` that finishes by itself run light, outside run-slot, since lefthook.yml has no merge hook; one sent through run-slot anyway takes `run-slot-commit`.
  Commit through `run-slot.sh <your name> -- git commit ...`, which holds `run-slot-commit` and builds under it; a plain `git commit` in a worktree joins the full queue through `packages/scripts/src/commit-slot.ts` as `commit-<worktree folder>`, a wait that can pass the Bash tool's 10 minutes, so run a plain one in the background.
  env-keys' build of `@packages/env` stays bare.
- A tester that waits for a phase has the run touch a flag file and waits for the file, never `tail -F <log> | grep -m1`, which keeps running after its match; it reads the flag once more before it goes idle while it holds a slot.
- A tester drives at any load, since run-slot queues only its heavy runs.
- To count the kernel's idle kills across a load spike: `/usr/bin/log show --last 5m --predicate 'eventMessage CONTAINS "killing_idle_process"' | grep -c 'memorystatus: killing_idle_process'`, with `--start '<YYYY-MM-DD HH:MM:SS>' --end '<...>'` for a spike that has passed.
  The full path matters, since zsh's `log` is a builtin, and so does the full phrase, since macOS also logs each `log show` with its predicate.
- run-slot's slots open by the load alone, where spawn.sh's load gate also reads the CPU's busy cores.
- run-slot warns when one argument after `--` is a list of existing paths zsh did not word-split, naming the fix (`${=VAR}` in zsh, or xargs), and the run goes ahead.

## ops-unstick

How ops-unstick runs its part of the factory's **unstick** rule (`extensions/core/rules/unstick.md`), beside its row above; the session-state hook's part is in [the hooks README](../hooks/README.md#session-state).

- A pass reads every live session's screen, cmux's and herdr's (`herdr pane read --source visible`), then sleeps 120s, and reads a screen only once its transcript has been quiet 60s (`QUIET_READ`), so a block lands 2 to 5 minutes after it appears.
- An API-error stop no hook recorded gets one resume line after 2 minutes idle and a line to its lead, and the lead again 10 minutes on; a stop on autocompact thrashing names small reads, and a fresh start from the brief if it thrashes again.
- A block no hook recorded goes to the session's manager at first sight and every 10 minutes after, with the session, the dialog and its wait.
- During an account move, while `ops/unstick/move.json` names the dispatcher running it and an `until` still ahead (`{"to": "<session>", "until": "<date -u +%FT%TZ>"}`, written as the move starts and removed when every session is back), each limit alert waits and that dispatcher gets one line every 10 minutes instead: how many sessions the limit holds, every other block by session and kind, then the limit sessions' names.
  A file that does not read is logged and means no move.
- It alarms the Builder when the merge queue holds open PRs and no session has taken a turn in 10 minutes.
- It writes what blocks each session to `ops/unstick/state.json` (`blocked`, each `{kind, line, name, since, surface, workspace}`, `surface` being cmux's surface id or `herdr:<server>:<pane id>`, beside `unreadable` and `writtenAt`), and the Dashboard shows each listed session as Stuck, or as Paused · usage limit when the limit alone holds it, while `writtenAt` is under 3 minutes old; an entry whose `surface` and `name` point at two live sessions marks neither and is named in the System report's problems.
- The job runs `run.py` from the main checkout, which follows `main`, so a change reaches it once the publish step ships it and Ops restarts the job; `tests/scripts/ops/unstick/run.test.ts` tests it.

## Usage forecasts

How to read an account's week for the factory's **usage** rule (`extensions/core/rules/usage.md`).

- The readings are the `<account> week` rows of `~/.playground/ops/optimizer/spare-history.jsonl`, one line per pass, and the move's time comes from the move itself, as the session that made it reported it.
- The pace is the gain in `seven_day.used_percentage` from the first reading at or after the move to the latest, divided by the hours between them, once those readings span 3 hours or more, since each is a whole percent; set the time it reaches 90% against the same account's `seven_day.resets_at`.
- `~/.playground/ops/optimizer/usage_table.py`, kept outside the repo, prints the report's table from every `~/.playground/usage-*.json` and ops-usage's `ops/usage/stored-login.json`, the fresher reading per account: each account's 5-hour and week percent, week reset and read time, an account read more than 15 minutes ago marked stale with its age.

## Ops switches

An ops switch is a file under the state folder that bends run-slot while it stands: `run-slot.3-off`, `run-slot.4-off`, `run-slot.clone-off`, `run-slot.load5-cap`, `run-slot.single`, `runner-host/off` and `runner-host/slot-off`.
Turn one on with `run-slot.sh set <who> <switch> [<value>] --reason "<why>" [--for <n>m|<n>h]`, its switch named without the `run-slot.` or `runner-host/` prefix (`run-slot.sh set ops slot-off --reason "box queue 17 deep" --for 2h`); a set with no reason is refused.
It writes `<who> <iso set> <iso expiry> <reason>`, with the value on the line below: for `load5-cap`, the highest load5 (the third field of `sysctl -n vm.loadavg`) a run may start under, and the default expiry is 4 hours.
Every run-slot run drops each switch past its expiry, moving it to `<name>.expired-<ts>` with an `expire` line in `run-slot.runs.log`, so the readers that only look for the file (the merge train, Checks, the leads' sweep) find it gone too.
A file with no such line, as a hand-written one, counts as set at its mtime with the default expiry.
Lift one before its expiry by moving it to `<name>.lifted-<ts>` (`mv run-slot.3-off run-slot.3-off.lifted-$(date -u +%Y%m%dT%H%MZ)`).
While one stands, `playground sweep ops` lists it once an hour with its age, expiry and reason (a hand-set `runner-host/slot-off` kept the runner box idle for two days).

## When a job restarts onto new code

A move of the dashboard's checkout or the main checkout restarts each ops job whose own source the move changed: `packages/scripts/src/ops-restart/cli.ts <checkout> <old sha> <new sha>` runs at the end of `dashboard/redeploy-pull.sh` and in the `release` skill's step 5.
ops-tick's canary pull calls none, since it moves only the worktrees on `canary`, and no job runs from one.
A job's entry is the first path in its `jobs.json` command, or in its launchd plist's arguments, and only a job whose entry, followed through its links, sits in the moved checkout counts: ops-checks-go, ops-merge-train and ops-usage, whose entries link into `scripts/ops/`, are picked, while a job run from a file of the state folder's own is never picked.
Its source is the entry's folder, each repo file the entry imports (TypeScript's relative imports followed through, a Python module beside it or one folder up) and each `@packages/<name>` it imports, whole, with each workspace package that package depends on.
Each picked job is stopped by its heartbeat's pid, only while that pid's command line still holds the entry, and waited on up to 60s.
One `up.py --restarted <names>` pass then starts the stopped herdr and cmux jobs again: once any running pass ends, it removes their starts from `up-state.json`, since `up.py` skips a job it started within its 10-minute GRACE; launchd starts its own.
A paused job stays down, ops-herdr is left running for Ops, and ops-dashboard rolls onto new code itself (`dashboard/supervisor.sh`'s reload).

## runner-host

A VPS that runs the suite for ops' local CI and Checks through `ci.sh`, so the suite leaves this Mac's run slots; GitHub's workflows run on hosted runners alone ([README's CI](../../README.md#ci)). `host.sh` reaches it as root with `~/.ssh/playground_runner`, whose public half goes into the VPS provider's panel first.

1. `scripts/ops/runner-host/host.sh survey <ip>` prints the OS, RAM, disk, listeners, services and containers, and changes nothing. Done when it prints `clean:` and exits 0; exit 3 means something live runs there and exit 4 that it could not read the listeners or the containers, and either keeps setup off that host.
2. `scripts/ops/runner-host/host.sh setup <ip>` surveys again, then copies `setup.sh` and `tools.sh` over and runs `setup.sh` with a fresh registration token on its stdin. It leaves a `runner` user with a full name (git needs one) and no sudo, swap (2 GB on 8 GB of RAM or more, else 4 GB), Docker, Bun, uv, Go, Ruby and zsh (what the suite's steps call), a runner per 2 cores and 6 GB as systemd services (labels `self-hosted,playground`, registered to `factory.repo` alone, which `host.sh` passes to `setup.sh`), key-only ssh, ufw allowing ssh alone, and unattended upgrades, then runs `tools.sh`, which names anything the suite needs that is missing. A second run changes nothing. Done when every runner reads `active` and `tools.sh` prints no `missing` line; `host.sh status <ip>` reads both again later.
3. GitHub's `auto-check-build` and `auto-test` run on every pull request on hosted runners, with no label, so nothing on the box starts them.

Before Actions, run-slot sends a checkout's test, type check, lint or build there through `ci.sh exec <dir> -- <command>`, its working tree as it stands, written through a scratch index so the checkout's own index stays as it is: tracked edits go, and an untracked file goes only as source under a source folder (`api/`, `packages/`, `scripts/`, `skills/`, `tests/` or `web/`, ending `.css`, `.md`, `.mdx`, `.mjs`, `.sh`, `.sql`, `.ts` or `.tsx`), since `.gitignore` does not name every key; any other untracked file exits 255, as does a box that cannot take it, and 255 runs it on the Mac instead, and ops' local CI and Checks run their suite there through `ci.sh <rev>`: it uploads a `git archive` of the revision's tree, never a token or a key, and `suite.sh` runs local CI's steps as the `runner` user in a systemd unit of its own, in a tree under `/srv/ci/.claude/worktrees/` (where a Mac worktree sits, since some tests read their own path), beside a Postgres container of its own (a run whose Docker does not answer stops red, or with 255 in exec mode). Since that tree has no history, `ci.sh` also sends the `bun.lock` at the revision's merge base with `canary` as `/srv/ci/<run>.base`, and suite.sh's audit step reads it with `audit.ts --new-over`, so a run fails only on an advisory the revision adds. Its steps find a `docker` shim first on their PATH (`/srv/ci/bin/docker`), which labels every container they start with the run, the tests' own unnamed ones included, and the unit's `ExecStopPost` (`suite.sh <run> stop`) removes the run's containers, their volumes and its tree however the unit ends, a stop from outside included; the next run removes those of any run whose unit never reached its stop. Runs wait for the slots `/srv/ci/slots` counts, first come first served (each waiter's ticket in `/srv/ci/queue/`, a dead run's dropped): an exec run takes one slot and a suite every slot, shared, as does an exec of the whole `bun run test` or of a `bun run test:file` naming no file, while `bun run test:skills` takes one slot as any exec does, and one suite runs at a time, the next waiting for it to end, since two suites at once took 632s each against 316s alone (dispatcher, 24 Oct), the old memory gate (`SUITE_PEAK_KB`, `SUITE_MARGIN_KB`) kept in `room()` for the undo, and an exec run waits for every suite, while `ci.sh` reads its lines every 20s, so a dropped ssh never ends a run, and every 5 minutes (`RUNNER_HOST_PROGRESS` seconds) prints one progress line on stderr naming the run's place in the queue, or its state and last line, with the minutes elapsed, its stdout staying the run's own. suite.sh reads the suite's pass or fail from its last `test-sandbox:` line, sums both test passes' counts, and prints one `ok|fail <step> <s>s` line a step and exits 0 or 1, or 255 when the box cannot be reached, and the caller then runs the suite on this Mac under run-slot. `RUNNER_HOST_LINUX_ONLY` names tests known to fail on Linux alone, one a line, in place of ci.sh's own list, which is empty while no test waits for a Linux fix. A failure only in a named test, with no error outside a test and as many failures as named tests, runs that test's file again on this Mac, and passes only when it passes there; the re-run runs only when the caller's checkout is clean and its `HEAD^{tree}` is the tree the box ran, else the run stays red with a `re-run skipped:` line saying why.

A box run stops with its caller.
As the unit starts, `ci.sh` prints `ci.sh: ci-<run> started on the box; ci.sh cancel <run> stops it` on stderr, and a TERM, INT or HUP to `ci.sh` stops the unit too.
To stop a run of your own whose `ci.sh` has gone, or one queued by mistake, run `~/.playground/ops/runner-host/ci.sh cancel <run>` with the id from that line; it takes only a run id and prints the unit's state after, done when that reads `inactive`.
A run whose `ci.sh` died past any trap (a SIGKILL, a restart) stops itself: every poll touches `/srv/ci/<run>.beat`, and suite.sh stops the unit, queued or running, once that heartbeat is 11 minutes old, just past the 10 minutes `ci.sh` waits on a box that does not answer.
Every ssh of every `ci.sh` rides one connection per user (`ControlMaster=auto`, `ControlPersist=60`, its socket `~/.ssh/lm-%C`), so a poll costs the box no new handshake.
ssh refuses a socket path past 86 bytes, so on a `$HOME` over 37 characters every `ci.sh` call exits 255 and the run falls back to the Mac.

A web image build goes there alone through `ci.sh web <rev>`, the route `no-mac-web-build` names ([why](../hooks/README.md#no-mac-web-build)).
It uploads `<rev>`'s tree as `ci.sh <rev>` does, and suite.sh's web mode takes every slot alone, so it waits for every suite to end.
It prints the build's output and exits with its code, or 255 when the box cannot take it, and nothing falls back to the Mac: commit what it should build first, since only a commit's tree goes.

Every caller runs the live copies, `~/.playground/ops/runner-host/ci.sh` and the `suite.sh` beside it, which `ci.sh` uploads on every run, never this folder's. So a fix to either reaches the box only once it is copied there: after each merge that changes one, Ops copies both from `canary` together (a new `ci.sh` beside an old `suite.sh` runs a stop the old copy refuses), each to a dot-file in that folder, then `mv`s it over the old one, since bash reads a running script as it goes. After `git fetch origin canary`, `host.sh drift` compares both live copies with `origin/canary`'s and exits 1, naming the file, when one differs; done when it prints `same ci.sh` and `same suite.sh`. A change made to a live copy lands in this folder in the same hour, since the next copy from `canary` drops whatever only the live copy holds.

The box runs the suite about 4.8 times slower than the owner's 15-core Mac, so size a box time limit from the box's own times. Measured on 27 Oct with `bun run test`:

- Mac, 15 cores at load 12 to 18: the parallel pass took 252 to 454s in 8 runs (median about 330s) and the serial pass 31 to 66s.
- Box, 4 cores at load 10 to 18: the parallel pass took 1234 to 1830s in 6 runs (median about 1590s) and the serial pass 188 to 215s.

Every job in `.github/workflows/` runs on `ubuntu-latest`, so a fork's pull request never runs its code on a machine of ours (`runnerProblems`, [README's CI](../../README.md#ci)). `auto-check-build`'s `Audit, Lint, and Build` and `auto-test`'s `test` run on every pull request into `canary` or `main`, with no label. `auto-canary-into-main` runs on each push to `canary` and by hand (`workflow_dispatch`): it opens the draft ship PR when none is open, through `GITHUB_TOKEN`, which needs the repository's "Allow GitHub Actions to create and approve pull requests" setting, and moves no version, so a ship stays the manual steps Ops runs. `audit-canary` runs on each push to `canary` and keeps one `canary audit: <ids>` issue for `canary`'s own advisories, since a PR's Audit step fails only on what that PR adds (the audit skill). `auto-labeler` is parked: a dispatch carries no pull request, so it does nothing until it gets a trigger of its own. Each workflow holds a `concurrency` group per pull request, so a push cancels the run on the head before it, and `pr:merge` refuses a cancelled check on the head until a run passes there; push again, or ask Ops to re-run it. The `runner` user is in the `docker` group, which is root on the box in all but name, so a job can read the runners' registration files; the survey keeps anything else off the box, so that is all it could reach.
