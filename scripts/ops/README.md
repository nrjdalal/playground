# scripts/ops

The factory's ops scripts, moving here from `~/.playground/ops`. The code lives here; everything it writes (heartbeats, pid files, logs, `jobs.json`, the outbox) stays in the state folder, `ops` in the data folder (`~/.playground/ops` by default). `run-slot.sh` lives here too, linked into the state folder by `scripts/link-skills.sh` (its state, `run-slot*`, stays in the state folder, or `RUN_SLOT_OPS`), and so are `notify.sh`, which the Checks lane and the merge train call by that path, and each script in `checks/`, `merge-train/` and `usage/`, linked into its folder in the state folder (`ops/checks/` and so on), where its state stays; every job not listed below still runs from the state folder until it moves. Moving the live jobs onto these copies is a cutover Ops runs, pointing two places at the main checkout's `scripts/ops`: `jobs.json`'s commands and ops-sweep's `up.py` call; up.py refuses any argument it does not know, an old `~/.zshrc` hook's included, and runs no pass. Every script that names the factory's checkout takes it from `$PLAYGROUND_REPO` first: a Python job through `beat.py`'s `checkout()`, else the main checkout of the folder the job runs in, else that of the checkout `beat.py` sits in, a TypeScript job through `packages/scripts/src/main-checkout.ts`, else the main checkout of the checkout its code sits in, and spawn.sh before its own `$MAIN`; both lookups end at `playground` in the folder that holds that checkout, so no path names a person's folder. `beat.py` is linked into the state folder with the other moved scripts, and `tests/scripts/ops/checkout-path.test.ts` refuses a fixed checkout path in `scripts/ops/`, `scripts/spawn.sh` and the `ops-*` jobs. ops-sweep runs from `packages/scripts/src/ops-sweep/` (`bun run ops:sweep`), its state staying in `ops/sweep/` in the state folder.

- `up.py`: Starts every unhealthy job from `jobs.json` that ops starts in a terminal as a pane in the Ops workspace on the factory herdr server, from any terminal; a job row's runtime, whatever word an older install stored, reads as `herdr`, and a hand-kept row that names no runtime, which the render never parsed, is a terminal job when it has a command and no launchd label. Every start runs its job through `exec`, so the job's pane closes when the job exits. A failed start is logged whole and tried again on the next pass, and every pass exits 0. A job whose holder runs an executable an update deleted, or whose heartbeat pid does while a holder or launchd holds it, (one `lsof` read a pass) is stopped by its recorded pid and started in herdr, with the reason in `up.log`; a launchd job on one is told once through `notify.sh` and never signalled. `--restarted <a,b>` first drops those jobs' starts from `up-state.json` under `up.lock`, waiting out a running pass, so its 10-minute GRACE holds back no job ops-restart stopped. `--sessions` lists the commands that bring back the roster's sessions that are down, and each factory session whose `--settings` and own folder's `.claude/settings.json` both lack the factory's hooks, which Ops' sweep acts on.
- `once.py`: Starts a job only when no copy of it runs, then becomes it.
- `beat.py`: Writes a job's heartbeat, `ops/<job>.json`, and names the main checkout (`checkout()`).
- `notify.sh`: Queues one line for ops (or `NOTIFY_TO`, a session, or a manager kind or `dispatcher` that `roster.ts who` resolves) in the outbox; it never types into a pane. With `NOTIFY_MAC=1` the line also shows as a macOS banner, for what must reach the owner away from the Dashboard (ops-tick's dashboard watch). A line stops at 400 characters unless `NOTIFY_WHOLE=1`, which the channel watch sets so each post goes whole.
- `ptable.py`: The process table; `started <pid>...` and `group <pgid>` read a pid's start and a process group's members from the kernel's table (`sysctl kern.proc`), which Claude Code's sandbox allows where it refuses the setuid `ps`. Reads only.
- `dashboard/`: ops-dashboard: `run.sh` runs `supervisor.sh` (the live dashboard's stack, served from each head's production build, and its follower, rolled to each head of the branch `upstream.sh` reads, its build before the stop queued in run-slot as `ops-dashboard` (`.agents/dashboard/live.md`), and checked each tick that the bare aliases hold its ports, `alias.ts`) and the off-loopback Docker watch (`watch-stuck.py`; a stuck session alerts from its own hook, PG-2184). Both stop the stack by its recorded process groups (`procs.sh`) on SIGHUP, or once their parent has exited, as when its herdr pane closes.
- `merge-train/`: ops-merge-train: `run.py` is merge-on-ready. Every 60s, in its own worktree reset to `origin/canary`, whose `sync()` installs when `bun.lock` moved and builds `packages/` when the reset moved it, it reads the open PRs' heads and check states, and on any change runs `pr:train ready`, which merges the first PR in queue order whose every gate passes. Its state (`run.lock`, `train.log`, the `no-ready` flag) stays in `ops/merge-train/`, which the script names by path rather than from `__file__`, so a run by its repo path reads the live state too. ops-restart follows ops-merge-train's link into this folder and restarts it when a file here changes.
- `optimizer/`: The idle-session backstop: `idle_sessions.ts [hours]` lists live sessions running with nothing to do (a checker whose worker is gone or whose PRs, its own, its roster `prs` list's, its worker's and those its transcript links, are all merged, closed or already scored, a worker whose PRs are all merged or closed, or a roster entry that reads paused or ended), each with its measured Claude spend over the last N hours; it reads only and writes only its PR cache (`~/.playground/ops/optimizer/pr-cache.json`). `auto_end.ts` ends what it flags, from ops-tick's auto-end beat and right after `pr:merge`, and cleans the worktrees each ended session used, by the factory's SESSIONS.md End.

## run-slot

How run-slot runs the factory's **slots** rule (`extensions/core/rules/slots.md`), beside its entry above.

- Slots open one to four, each giving 2 load units: `run-slot` always, and `run-slot-2` to `run-slot-4` while memory passes `mem_ok` and the CPU, in `top -l 2 -n 0`'s second sample, is idle at the bar or more with load1 under the stop (`lanes_open`), the stop 45 unless the `run-slot.load1-max` switch sets another and the bar 40% unless `run-slot.idle-min` does ([Ops switches](#ops-switches)).
  Outside single-slot mode, slots 2 to 4 also stay shut while load5 is at or over `load_line`'s cap (`run-slot.load5-cap`'s while it stands, else 22), until the queue's oldest waiter has waited `LOAD_WAIT` (300 s) since it first asked (`load5_held`, timed by `oldest_asked` from each ticket's sixth field, the first ask a reread's new ticket keeps, so a waiter, `room`, `slots` and `can-take` read one verdict, held for a look or a count as `LANES` is); in single-slot mode `run-slot-2` opens only under that cap, with no ceiling.
  Two checker suites in `run-slot` and `run-slot-2` took load5 to 17.96 on their own against the owner's cap of 15 while the CPU gate stayed open (issue 1403, 7 Nov 11:07Z).
  `ops-dashboard` and `ops-merge-train` take a slot at the cap, as `slot_open` lets them.
  The idle share is the gauge, since the factory's resting sessions hold load1 at 14 to 20 on 15 cores while the CPU sits 53 to 67% idle (3 Nov), and a load1 30 stop kept the lanes shut 109 of 120 minutes with the CPU about half idle while heavy runs waited up to 122 minutes (retro 36, 4 Nov), and a 50% bar from load1 30 left the CPU at a median 48% idle with 14 of its 30 CPU shuts at 40 to 49% (5 Nov, 06:19 to 07:45Z); the load1 stop stays a hard stop for the spikes a fresh run shows only a minute late, load1 64 after a burst of starts and 73 after a clone.
  `mem_ok` asks for a free share of 40% or more, pressure normal and swap-ins under `SWAPINS_MAX` (100) a second in this reading or the one before it, the rate `swapin_rate` reads from `vm_stat -c 2 1`'s second sample, as spawn.sh's `swapins()` does, since the first counts since boot; so two readings in a row at 100 or more shut the lanes, since a one-second sample spikes and falls back (5 Nov, 06:19 to 07:45Z: 17 of the 24 memory shuts came at pressure 1 with 70 to 80% free, from readings such as 128, 242 and 1116 between 0, 8, 20 and 44); an unread `top`, or a `vm_stat` missing either sample, keeps the lanes shut, said once a run on stderr.
  The swap-in rate stands in for swap use, since macOS grows its swap files as they fill, so used over total read about 88% at 08:47Z on 3 Nov, a record of past swapping that a 70% line would turn into one lane all day.
  Every look shares one reading of the gauges, the disk's included, through `run-slot.gauges` for 10 s, since a `top` takes a second and about 0.7 s of system CPU.
  One look refreshes it under the `run-slot.gauges.lock` folder while the rest keep the reading they have, since 26 waiters each running their own `top` at a stale reading took load1 to 56.8 (3 Nov, 10:53Z); with no reading yet they read `busy`, which keeps the lanes shut, and says so once a run.
  A lock aged 30 s, a killed refresher's, is taken over, and a refresher removes the lock only while it carries the mtime it took; two looks taking over together both refresh, which costs one more `top` and no torn reading, since each writes it whole through a rename.
  A count of the open slots (`capacity()`, which `slots`, `room` and every take read) takes one lanes verdict for slots 2 to 4 (`lanes_now`), since a check per slot counted slot 2 shut on a stale reading and slots 3 and 4 open on a new one that landed between them; outside a count each check reads afresh.
  Every run's look rewrites the verdict in `run-slot.lanes`, as does the head's every poll while the gauges shut a slot, and a read subcommand (`room`, `can-take`, `head`, `slots`) takes one written in the last 30 s, so it sees the lanes as the queue's head saw them, since the CPU gate can read 55% then 33% idle seconds apart (issue 1216); it reads the gauges itself when none is that fresh: when no run is waiting, when the head last read the lanes open, or when an older copy wrote the file only on a change.
  Each change between open and shut that a run's look finds is a `lanes` line in `run-slot.runs.log`, `open` or `shut` with `idle=`, `load1=`, `free=`, `pressure=`, `swapins=`, `disk0_tps=` and `disk0_mbs=`, while a read subcommand logs none.
  A `shut` line also names why, the first gauge that shut the lanes: `why=load1` at the load1 stop or more or unread, `why=cpu` under the idle bar or unread, and `why=mem` when `mem_ok` fails; `free=` and `pressure=` are `mem_ok`'s free share and pressure level (`-` when unread), so a day of lines tells the causes apart from the readings alone (retro 39, 5 Nov).
  The last two are disk0's transfers/s and MB/s in `iostat -d -c 2 -w 1 disk0`'s second sample (`-` when unread), logged so a bound on disk load can be read from a day of lines; no verdict reads them yet.
  Each write the oldest waiter makes to `run-slot.next` is a `next` line in `run-slot.runs.log`, the line it wrote with its writer and time, so a window where `head` named a waiter that line passed over reads back who the oldest named and when (issue 1477).
- A run counts its item's size, small 1, medium 2 and big 3, but a light run (a quick kind, a `bun install` or `add`, a filtered `turbo run`, a bare `tsc` or `bunx tsc`, or a `check-types` whose every task turbo's dry run finds cached, the dry run given 10 s) counts 1 whatever its session's size, and `run-slot.sh size <your name>` prints yours: `RUN_SLOT_SIZE`, else small for a `commit-<worktree>` pre-commit step, else your roster entry's `size` or your worker's, else plan.json's item for your branch's issue, else medium.

- Another factory on this machine runs its own pool, so `slots.peers` lists its ops folders: each live holder of their `run-slot` to `run-slot-4` counts its units in `held_units` (2 for a line with none), and a holder whose pid has died counts nothing; run-slot reads those folders only, never reclaiming or writing there.
- A read subcommand, one that runs on as a bare `true` (`can-take`, `head`, `room`, `slots`), sets `CAN_TAKE`, so the quick-lane rule never takes it and it still gives its answer; `tests/scripts/ops/run-slot-can-take.test.ts` reads each one from the script and runs it beside three short `true` runs in the log.
- run-slot warns when one argument after `--` is a list of existing paths zsh did not word-split, naming the fix (`${=VAR}` in zsh, or xargs), and the run goes ahead.

## ops-unstick

- The job runs `run.py` from the main checkout, which follows `main`, so a change reaches it once the publish step ships it and Ops restarts the job; `tests/scripts/ops/unstick/run.test.ts` tests it.

## Usage forecasts

How to read an account's week for the factory's **usage** rule (`extensions/core/rules/usage.md`).

- The readings are the rows `week-marks.py` appends to `ops/usage/` on each ops tick, each `{t, week, reset, account}`: `week-samples.jsonl` for usage.json's account, the one the factory spends, while `usage.accounts` lists it, and `account-samples.jsonl` for every other account in usage.json's `accounts`.
  An account's rows move from one file to the other as the factory moves onto it or off it, so read an account by its `account` field across both files.
  The move's time comes from the move itself, as the session that made it reported it.
- The pace is the gain in `week` from the first reading at or after the move to the latest, divided by the hours between them, once those readings span 3 hours or more, since each is a whole percent; set the time it reaches 100% against the same rows' `reset`.
- The report's table is each account's latest reading: `login-flip.json`'s `seen` for each account `usage.accounts` lists (`five` and `week`, their resets `fiveReset` and `weekReset`, and `at`), and `stored-login.json` (its `rate_limits` and `writtenAt`) for the stored login.
  The stored login's `seen` entry, when `usage.accounts` lists it, takes login-flip's run time as its `at` (`login-flip.py:101`), so its row and its age come from `stored-login.json` alone.
  `playground accounts list` prints the two percents for each Claude account, and the report marks an account read more than 15 minutes ago stale with its age.
- ops-sweep turns spawn.sh's week pace off by itself from its own week forecast: each pass (`paceOff()` in `packages/scripts/src/ops-sweep/sweep.ts`) projects the week of each account `login-flip.json`'s split gives a share of new sessions (usage.json's account while the split is 30 minutes old or more) by the pace above, to a reading under 30 minutes old, taking the move as that account's first row in `week-samples.jsonl` after another account's latest row there (with none, as for an account the factory has left, the pace runs from its first reading this week, which can come before its last stretch on the factory, so that account's forecast can read a little slower than the rule's), and no forecast until its readings since then span 3 hours.
  While one projects under 100% at its own week reset, it writes `usage-pace-off-until` an hour on, never past that account's reset, renewed each pass, so the pace comes back within the hour of a stopped sweep; once none does, it removes the time it wrote.
  `ops/sweep/pace-off.json` records each pass's forecast, `{at, forecast, until}` (a pass that a hand-written future time holds returns before it forecasts and writes none, so the file keeps the last), each account by its `usage.accounts` label, else `account <n>` by its row, else `unlisted <n>` for one `usage.accounts` does not list, and `until` null while the pace stays on.
  A future time in the file that `until` does not name is a person's, written by hand, and stands as it is; the forecast takes no account floor: no code holds an account floor today, and the Ops lead holds any floor the owner sets by hand.

## Ops switches

An ops switch is a file under the state folder that bends run-slot while it stands: `run-slot.3-off`, `run-slot.4-off`, `run-slot.battery`, `run-slot.clone-off`, `run-slot.focus`, `run-slot.idle-min`, `run-slot.load1-max`, `run-slot.load5-cap`, `run-slot.single`, `runner-host/off` and `runner-host/slot-off`.
`run-slot.focus`, which `playground focus on` sets (playbook's LIFECYCLE.md), names its session as `<who>` and stands 180 minutes at most: while it stands that session is the `run-slot.priority` pick whatever the priority file says, and every other session's heavy run in this Mac's queue waits, its commit build, merge or clone lane included.
The quick slot's short runs, a runner-host box run, a `--model-bound` run, the focused session's own reviewer's and tester's runs (`<id>-reviewer` and `<id>-tester` of an `<id>-worker`, or any checker whose roster row names it as `worker`), and `ops-tick`'s and `ops-dashboard`'s runs go on.
`run-slot.sh preempt`, which Ops runs when it raises focus for an urgent ticket, stops the runs other sessions already hold a slot with: it sends TERM to the process group of each holder's child that focus does not spare.
Each run records that child, the group leader run-slot started for it, in `<slot>.child`, and preempt signals it only while it is still that holder's own child leading its own group, so a process run-slot did not start is left alone.
The stopped run exits with its child's code (143 for TERM), saying focus preempted it and to run it again once focus ends, since run-slot does not run it again itself; with no `run-slot.focus` standing, preempt exits 2 and stops nothing.
`playground focus off` ends it, lifting the switch with the merge hold and ending `focus.json`, so lift it that way rather than by a move or a fresh `set`.
`run-slot.battery` is ops-awake's alone, written by its battery check at the red mark (the **battery** rule, `extensions/core/rules/battery.md`) with a 10-minute expiry pushed on each minute while the mark holds, and lifted by its `.lifted-<ts>` move on the check that sees the charge rise: while it stands every heavy run on this Mac waits, a focused session's included, saying it waits for the Mac's charge to rise, and the quick slot's short runs, a runner-host box run, a `--model-bound` run and `ops-tick`'s and `ops-dashboard`'s runs go on.
Turn one on with `run-slot.sh set <who> <switch> [<value>] --reason "<why>" [--for <n>m|<n>h]`, its switch named without the `run-slot.` or `runner-host/` prefix (`run-slot.sh set ops slot-off --reason "box queue 17 deep" --for 2h`); a set with no reason is refused.
It writes `<who> <iso set> <iso expiry> <reason>`, with the value on the line below, and the default expiry is 4 hours.
For `idle-min` the value is the CPU idle share, a whole number from 0 to 100, that `run-slot-2` to `run-slot-4` open at under the load1 stop (the run-slot bullets above): 40 while the switch is absent, expired or holds any other value, so a machine whose owner wants more of its cores in use takes a lower bar by a set rather than a code change (issue 1431).
For `load1-max` the value is the load1 stop, a whole number from 1 to 999, that `run-slot-2` to `run-slot-4` open under (the run-slot bullets above): 45 while the switch is absent, expired or holds any other value, so a machine whose resting sessions hold load1 up with the CPU half idle opens the lanes under a higher stop by a set rather than a code change (issue 1442).
For `load5-cap` the value is the highest load5 (the third field of `sysctl -n vm.loadavg`) that `run-slot-2` to `run-slot-4` open under (outside single-slot mode, also once the queue's oldest waiter has waited 300 s) and a commit-lane or quick-lane start waits under (the run-slot bullets above), 22 at most, so a low cap holds each such start for up to 300 s too, and holds the hourly trash purge's next batch while load5 is at the cap or over it, until the disk is under the purge's 5 GB floor (`trashPurge` in `packages/scripts/src/ops-tick/tick.ts`).
Every run-slot run drops each switch past its expiry, moving it to `<name>.expired-<ts>` with an `expire` line in `run-slot.runs.log`, so the readers that only look for the file (the merge train, Checks, the leads' sweep) find it gone too.
A file with no such line, as a hand-written one, counts as set at its mtime with the default expiry, and as off while that mtime reads back empty; `run-slot.priority` likewise names no pick then.
Lift one before its expiry by moving it to `<name>.lifted-<ts>` (`mv run-slot.3-off run-slot.3-off.lifted-$(date -u +%Y%m%dT%H%MZ)`).
While one stands, `playground sweep ops` lists it once an hour with its age, expiry and reason (a hand-set `runner-host/slot-off` kept the runner box idle for two days).

## When a job restarts onto new code

A move of the dashboard's checkout or the main checkout restarts each ops job whose own source the move changed: `packages/scripts/src/ops-restart/cli.ts <checkout> <old sha> <new sha>` runs at the end of `dashboard/redeploy-pull.sh` and in the `release` skill's step 5.
ops-tick's canary pull calls none, since it moves only the worktrees on `canary` and the leads worktree, and no job runs from one.
A job's entry is the first path in its `jobs.json` command, or in its launchd plist's arguments, and only a job whose entry, followed through its links, sits in the moved checkout counts: ops-checks-go, ops-merge-train and ops-usage, whose entries link into `scripts/ops/`, are picked, while a job run from a file of the state folder's own is never picked.
Its source is the entry's folder, each repo file the entry imports (TypeScript's relative imports followed through, a Python module beside it or one folder up) and each `@packages/<name>` it imports, whole, with each workspace package that package depends on.
Each picked job is stopped by its heartbeat's pid, only while that pid's command line still holds the entry, and waited on up to 60s.
One `up.py --restarted <names>` pass then starts the stopped herdr jobs again: once any running pass ends, it removes their starts from `up-state.json`, since `up.py` skips a job it started within its 10-minute GRACE; launchd starts its own.
It first renders `jobs.json` from the settings with the new code, as `up.py` does, so a job whose default the move turned on reads as on; when it stopped no herdr job, a plain `up.py` pass starts each herdr job that is on and whose heartbeat pid runs nowhere.
A paused job stays down, ops-herdr is left running for Ops, and ops-dashboard rolls onto new code itself (`dashboard/supervisor.sh`'s reload).

## runner-host

A VPS that runs the suite for run-slot through `ci.sh`, so the suite leaves this Mac's run slots; GitHub's workflows run on hosted runners alone ([README's CI](../../README.md#ci)). `host.sh` reaches it as root with `~/.ssh/playground_runner`, whose public half goes into the VPS provider's panel first.

1. `scripts/ops/runner-host/host.sh survey <ip>` prints the OS, RAM, disk, listeners, services and containers, and changes nothing. Done when it prints `clean:` and exits 0; exit 3 means something live runs there and exit 4 that it could not read the listeners or the containers, and either keeps setup off that host.
2. `scripts/ops/runner-host/host.sh setup <ip>` surveys again, then copies `setup.sh` and `tools.sh` over and runs `setup.sh` with a fresh registration token on its stdin. It leaves a `runner` user with a full name (git needs one) and no sudo, swap (2 GB on 8 GB of RAM or more, else 4 GB), Docker, Bun, uv, Go, Ruby and zsh (what the suite's steps call), a runner per 2 cores and 6 GB as systemd services (labels `self-hosted,playground`, registered to `factory.repo` alone, which `host.sh` passes to `setup.sh`), key-only ssh, ufw allowing ssh alone, and unattended upgrades, then runs `tools.sh`, which names anything the suite needs that is missing. A second run changes nothing. Done when every runner reads `active` and `tools.sh` prints no `missing` line; `host.sh status <ip>` reads both again later.
3. GitHub's `auto-check-build` and `auto-test` run on every pull request on hosted runners, with no label, so nothing on the box starts them.

Before Actions, run-slot sends a checkout's test, type check, lint or build there through `ci.sh exec <dir> -- <command>`, its working tree as it stands, written through a scratch index so the checkout's own index stays as it is: tracked edits go, and an untracked file goes only as source under a source folder (`api/`, `packages/`, `scripts/`, `skills/`, `tests/` or `web/`, ending `.css`, `.md`, `.mdx`, `.mjs`, `.sh`, `.sql`, `.ts` or `.tsx`), since `.gitignore` does not name every key; any other untracked file exits 255, as does a box that cannot take it, and 255 runs it on the Mac instead, and ops' local CI and Checks run their suite there through `ci.sh <rev>`: it uploads a `git archive` of the revision's tree, never a token or a key, and `suite.sh` runs local CI's steps as the `runner` user in a systemd unit of its own, in a tree under `/srv/ci/.claude/worktrees/` (where a Mac worktree sits, since some tests read their own path), beside a Postgres container of its own (a run whose Docker does not answer stops red, or with 255 in exec mode). Since that tree has no history, `ci.sh` also sends the `bun.lock` at the revision's merge base with `canary` as `/srv/ci/<run>.base`, and suite.sh's audit step reads it with `audit.ts --new-over`, so a run fails only on an advisory the revision adds. Its steps find a `docker` shim first on their PATH (`/srv/ci/bin/docker`), which labels every container they start with the run, the tests' own containers included, and the unit's `ExecStopPost` (`suite.sh <run> stop`) removes the run's containers, their volumes and its tree however the unit ends, a stop from outside included; the next run removes those of any run whose unit never reached its stop. Runs wait for the slots `/srv/ci/slots` counts, first come first served (each waiter's ticket in `/srv/ci/queue/`, a dead run's dropped): an exec run takes one slot and a suite every slot, shared, as does an exec of the whole `bun run test` or of a `bun run test:file` naming no file, while `bun run test:skills` takes one slot as any exec does, and one suite runs at a time, the next waiting for it to end, since two suites at once took 632s each against 316s alone (dispatcher, 24 Oct), the old memory gate (`SUITE_PEAK_KB`, `SUITE_MARGIN_KB`) kept in `room()` for the undo, and an exec run waits for every suite, while `ci.sh` reads its lines every 20s, so a dropped ssh never ends a run, and every 5 minutes (`RUNNER_HOST_PROGRESS` seconds) prints one progress line on stderr naming the run's place in the queue, or its state and last line, with the minutes elapsed, its stdout staying the run's own. suite.sh reads the suite's pass or fail from its last `test-sandbox:` line, sums both test passes' counts, and prints one `ok|fail <step> <s>s` line a step and exits 0 or 1, or 255 when the box cannot be reached, and the caller then runs the suite on this Mac under run-slot. `RUNNER_HOST_LINUX_ONLY` names tests known to fail on Linux alone, one a line, in place of ci.sh's own list, which is empty while no test waits for a Linux fix. A failure only in a named test, with no error outside a test and as many failures as named tests, runs that test's file again on this Mac, and passes only when it passes there; the re-run runs only when the caller's checkout is clean and its `HEAD^{tree}` is the tree the box ran, else the run stays red with a `re-run skipped:` line saying why.

A box run stops with its caller.
As the unit starts, `ci.sh` prints `ci.sh: ci-<run> started on the box; ci.sh cancel <run> stops it` on stderr, and a TERM, INT or HUP to `ci.sh` stops the unit too.
To stop a run of your own whose `ci.sh` has gone, or one queued by mistake, run `~/.playground/ops/runner-host/ci.sh cancel <run>` with the id from that line; it takes only a run id and prints the unit's state after, done when that reads `inactive`.
A run whose `ci.sh` died past any trap (a SIGKILL, a restart) stops itself: every poll touches `/srv/ci/<run>.beat`, and suite.sh stops the unit, queued or running, once that heartbeat is 11 minutes old, just past the 10 minutes `ci.sh` waits on a box that does not answer.
Every ssh of every `ci.sh` rides one connection per user (`ControlMaster=auto`, `ControlPersist=60`, its socket `~/.ssh/pg-%C`), so a poll costs the box no new handshake.
ssh refuses a socket path past 86 bytes, so on a `$HOME` over 37 characters every `ci.sh` call exits 255 and the run falls back to the Mac.

A web image build goes there alone through `ci.sh web <rev>`, the route `no-mac-web-build` names while a runner host is set ([why](../hooks/README.md#no-mac-web-build)).
It uploads `<rev>`'s tree as `ci.sh <rev>` does, and suite.sh's web mode takes every slot alone, so it waits for every suite to end.
It prints the build's output and exits with its code, or 255 when the box cannot take it, and nothing falls back to the Mac: commit what it should build first, since only a commit's tree goes.

Every caller runs the live copies, `~/.playground/ops/runner-host/ci.sh` and the `suite.sh` beside it, which `ci.sh` uploads on every run, never this folder's. So a fix to either reaches the box only once it is copied there: after each merge that changes one, Ops copies both from `canary` together (a new `ci.sh` beside an old `suite.sh` runs a stop the old copy refuses), each to a dot-file in that folder, then `mv`s it over the old one, since bash reads a running script as it goes. After `git fetch origin canary`, `host.sh drift` compares both live copies with `origin/canary`'s and exits 1, naming the file, when one differs; done when it prints `same ci.sh` and `same suite.sh`. A change made to a live copy lands in this folder in the same hour, since the next copy from `canary` drops whatever only the live copy holds.

The box runs the suite about 4.8 times slower than the owner's 15-core Mac, so size a box time limit from the box's own times. Measured on 27 Oct with `bun run test`:

- Mac, 15 cores at load 12 to 18: the parallel pass took 252 to 454s in 8 runs (median about 330s) and the serial pass 31 to 66s.
- Box, 4 cores at load 10 to 18: the parallel pass took 1234 to 1830s in 6 runs (median about 1590s) and the serial pass 188 to 215s.

Every job in `.github/workflows/` runs on `ubuntu-latest`, so a fork's pull request never runs its code on a machine of ours (`runnerProblems`, [README's CI](../../README.md#ci)). `auto-check-build`'s `Audit, Lint, and Build` (the result of its `Lint and Build` job and its `Suite (n)` shards, beside the `Suite (n, clock ahead)` jobs that run the suite once more with the clock 30 days on, [.agents/testing.md](../../.agents/testing.md#the-clock-ahead-pass)) and `auto-test`'s `test` run on every pull request into `canary` or `main`, with no label. `auto-canary-into-main` runs on each push to `canary` and by hand (`workflow_dispatch`): it opens the draft ship PR when none is open, through `GITHUB_TOKEN`, which needs the repository's "Allow GitHub Actions to create and approve pull requests" setting, and moves no version, so a ship stays the manual steps Ops runs. `audit-canary` runs on each push to `canary` and keeps one `canary audit: <ids>` issue for `canary`'s own advisories, since a PR's Audit step fails only on what that PR adds (the audit skill). `auto-labeler` is parked: a dispatch carries no pull request, so it does nothing until it gets a trigger of its own. Each workflow holds a `concurrency` group per pull request, so a push cancels the run on the head before it, and `pr:merge` refuses a cancelled check on the head until a run passes there; push again, or tell your lead, who has Ops re-run it. The `runner` user is in the `docker` group, which is root on the box in all but name, so a job can read the runners' registration files; the survey keeps anything else off the box, so that is all it could reach.
