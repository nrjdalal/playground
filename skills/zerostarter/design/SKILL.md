# Design Conventions

When a change establishes or alters a convention, update this file in the same change so it never drifts. Propose a genuinely new design-token choice before committing; the maintainer owns the design language.

## Principles

- **Defaults first.** Use primitives bare at their defaults and add a class only where a spot genuinely needs it. Per-instance overrides are how drift starts. Example: `<Spinner />`, not `<Spinner className="size-5" />`.
- **One source per concern.** Shared styling lives in the component or its variant, never copy-pasted across call sites. Brand identity (name, description, social links) is `@packages/config/site`.

## Cursor

Everything clickable shows the pointer: buttons, links, tabs, menu, select, combobox and command items, options, checkboxes, radios, switches, `summary` and `label[for]`. A disabled one never shows the pointer. A disabled shadcn control whose classes turn it `pointer-events-none` (a natively disabled `Button` or `Toggle`, tabs, sidebar menu buttons, the menu, select, combobox and command items, the Questionnaire's choices) shows the cursor of what lies under it (the arrow, as the inbox draft's disabled Send shows, or an input group's I-beam for a disabled button inside one, as the composer's Send would), and takes no patch for it: the ask is the hand on clickable things, and neither says clickable (the Builder's go). Everything else the rule covers reads `not-allowed` once `:disabled`, `aria-disabled="true"` or `data-disabled` (a `Button` disabled through `aria-disabled` alone, Base UI's `focusableWhenDisabled`, as the stream's Load older is; but not cmdk's `data-disabled="false"`, which it sets on every enabled option).

- One rule sets it, in `globals.css`'s `@layer base` (`POINTER_CURSORS`), so no component needs a `cursor-pointer` class. It sits in the base layer so a component's own cursor still wins: the sidebar rail's `cursor-e-resize`/`cursor-w-resize`, a Plan board card's and an Apps tab row's `cursor-grab` (the whole card or row is the drag handle), an input group's `cursor-text`, and the docs search trigger's `cursor-default` (a readOnly input, kept off the I-beam).
- shadcn's menu, select, combobox and command items ship `cursor-default`, which beats the base layer, so `shadcn-customize.ts` swaps it for `cursor-pointer` (`pointerItems`) and puts the rule back after a sync (`pointerCursors`); `tests/packages/scripts/src/shadcn-customize-cursor.test.ts` fails when a sync drops either, and `bun run verify cursor` reads Send's, Attach's, a plain disabled button's and the rail's computed cursors in a real browser.

## Focus

No focus ring or outline anywhere: a focused control, or the field wrapping it (an input group, the composer's attachment, a code block, combobox chips), shows a lit border or a fill, and an invalid field its red border alone.

- One unlayered rule appended to `globals.css` (`NO_FOCUS_RING`) clears the ring shadow on `:focus-visible`, on `[aria-invalid="true"]`, on those wrapping slots, on a Questionnaire choice (keyed on its input, since `Hint` renames the label's slot), a Pages card, the aside's resize grip and a calendar's focused day (react-day-picker's `data-focused`, which a click sets too), and drops the outline on `:focus-visible` but for forced-colors mode (a transparent outline flashed as `transition-all` faded it), so it outranks every `focus-visible:ring-*` utility and no component needs its ring class removed; `noFocusRing` in `packages/scripts/src/shadcn-customize.ts` puts it back after a sync, and `tests/packages/scripts/src/shadcn-customize-globals.test.ts` fails when a sync drops it.
- Every focusable control still shows its focus, from a second appended block (`FOCUS_MARKS`, restored by `focusMarks` and held by the same test):
  - a control with no fill of its own takes a muted one, from a base-layer `:focus-visible` rule, so a component's own fill or `focus-visible:` utility wins;
  - a focused pane (the stream, the aside's panes) tints with 4% of the foreground, a step that shows in both themes, and the resize handle lights in `--ring`;
  - a valid control whose classes ask for `focus-visible:border-ring` gets it unlayered, since in dark an outline button's `dark:border-input` otherwise wins, and an invalid one keeps its red border;
  - a control whose own fill is the muted one (the open sidebar row or sub-row, an Inbox card's body), or the selected aside square's `bg-foreground/10` (`BAR_ITEM`), deepens it.
- A link laid over a whole card (a sent file chip's open link, `components/dashboard/attachments.tsx`) takes `focus-visible:bg-transparent`, and the card lights its border (`has-[:focus-visible]:border-ring`), since a fill would cover the file.
- A new control needs nothing of its own unless it sets a fill, which then needs its own `focus-visible:` change; `bun run verify focus-marks` fails on a focusable control on its five pages whose focus changes nothing.

## Spacing

- Stay on the Tailwind scale and snap to the nearest step; no off-ladder one-offs (`gap-7.5`, `size-4.5`, `w-45`, `mb-18`, `text-[0.6rem]`).
- `gap-2` is the workhorse for tight clusters.
- Dashboard and console pages use the collapsible `SidebarShell` (`components/shell/sidebar-shell.tsx`) and wrap content in `PageShell` (`components/shell/page-shell.tsx`), which owns `mx-auto` + width + `p-4 sm:p-6` via a `size` variant (`sm`/`md`/`lg`/`full`, default `md` = `max-w-4xl`). The title/description/actions row is `PageHeader` (`components/shell/page-header.tsx`). Never hand-roll `mx-auto`/`max-w-*`/`p-*` or the header layout. The two exceptions are a session's chat view, whose `PageShell` takes `pt-0 sm:pt-0` so its stream touches the top edge (see Chat below), and the Dashboard home's state before a chat shows, which takes the same so nothing moves when the chat arrives.
- A `PageHeader` description is one short line that fits beside its title at 1280px. Text of any length, such as a worker's first ask, goes through `oneLine` (`lib/dashboard.ts`), which cuts it at a word and ends it with `…`.
- Every dashboard page header is exactly two rows, the title and that one muted line. A page's facts (when its data is from, what it read) go in the subtitle as plain text; counts and controls, Refresh included, go in its table toolbar, never a third header line. A session's own view has no header (see Chat below); `AgentSummary`, the line that held its standing (what it is doing, status, last activity, branch, pull request), is kept, unused, for the stats place still to be picked, with what it is doing in full and its last report on hover; `PageHeader`'s text column is `min-w-0` so a long subtitle truncates rather than wraps.
- Marketing pages share one vertical scale: `py-24` sections and a `px-4 md:px-6` container gutter.

## Typography and headings

- Exactly one `<h1>` per page (the page title); sections use `<h2>` and below, never skipping a level.
- Use the existing type scale and tokens; no off-scale font sizes. The scale has one step below `text-xs`: `text-2xs` (0.625rem, a theme token in `globals.css`), for a third, quieter line under a `text-xs` one, such as the state line under a script row's name in the dashboard sidebar, added at the owner's ask.
- **Compact size:** a dense data page takes the sidebar's sizes, which are the source of truth. A sidebar row is the stock `h-8` with `size-4` icons and one `text-xs` line (a script's adds a `text-2xs` line under it), so its controls, rows, chips and counts keep the stock height and icons and take `text-xs`, and a secondary line takes `text-2xs` (the labels line under a Linear ticket's title, the System status's readings; `cn` merges it over a primitive's `text-xs`). The shared table family (`DataTable`, `DataTableToolbar`, `DataTableViewOptions`, `DataTableFacetedFilter`, `FacetedFilter` in `components/data-table.tsx`) takes it as `size="sm"`; a control the page renders itself adds `text-xs`. The page title and its description stay at `PageHeader`'s size, one step larger, and popover and menu content keeps its own. Every dashboard table is on it: Linear, Plan, Sessions, the Dashboard's and Usage's.
- Marketing-page headings are `font-bold`. A sub-heading within a section stays lighter (a `font-semibold` `h3`) to preserve hierarchy; non-heading display text (a stat value) follows its own weight.

## Color and theming

- Semantic tokens only: `text-muted-foreground`, `bg-card`, `border-border`, `bg-sidebar`, and friends. No hardcoded hex, rgb, or hsl in classNames or inline styles. The exceptions are takumi-rendered OG images, which have no theme context, and the Inbox's file tiles, whose icons take Pierre's own palette (Icons, below).
- Dark mode is `next-themes` (`attribute="class"`, `app/providers.tsx`); pair every `dark:` with a token.
- Status colours are Tailwind's 600 in light mode and 500 in dark, every one through a theme token set per mode in `globals.css` as `var(--color-<hue>-600)` under `:root` and `var(--color-<hue>-500)` under `.dark`, never a palette shade in a component (`text-red-500`, `bg-green-600`): `--bravo` purple (the second dispatcher's colour beside Alpha's `--info`, on the Inbox's poster names), `--caution` orange, `--destructive` red, `--inactive` neutral (a gray status icon: idle, ended, a draft PR, the health ring), `--info` blue, `--success` green, `--warning` amber. A status colour with no token gets one there first. `tests/web/next/src/app/globals.test.ts` fails on a token off 600/500 and on a component that hard-codes a shade of a status hue. They are foreground-less: `text-success`, `bg-success/10`, `border-success/20`.

## Restraint (the dashboard)

The owner: "The UI looks so childish". The dashboard follows the console's look and https://dalonic.com's: minimal and text-first, generous whitespace, a clear type hierarchy, no decoration.

- No emoji anywhere in the dashboard UI, labels and counts included. A report that carries them is shown in its words alone.
- Plain muted text where text will do: no Badges, coloured chips or rounded pills for a status, a label or a count (`Needs you · 3 waiting`, not a red badge; a ticket's labels as one muted `Team · Project · label` line). Three exceptions he approved: the red corner mark a square wears (`CountBadge`, Badges and pills, below), a message's thread chip, an outline `Badge` in mono holding its 4-character id that opens the thread (`TranscriptBubble` in `components/transcript-message.tsx`), as asked ("a leading marker renders as a small chip that opens `/dashboard/threads/<id>`"), and each Inbox row's count, a mono outline `Badge` beside its name (`ShelfLabel` on a shelf), as asked ("counts look bad like this, use like this maybe with labels", "still keep showing counts").
- No oversized numbers: no stat cards with `text-xl` values, no Progress bars. A set of readings is a plain table, with a small sparkline where its history matters. The one bar is the usage hover's 10 cells an account (`UsageBar`: "You think I can understand anything via this plan with me via ascii?").
- One neutral accent: charts take `--chart-2` alone. Colour marks only a state that asks something of the owner (a crossed rule's `text-warning` or `text-destructive`); healthy reads muted, never green. Seven exceptions he asked for: the System readings' green, orange and red; the red corner mark on a square: a count is always the red dot holding its number (the Inbox tab, the Changelog's square), and a square with no count wears the plain red dot while what lit the browser tab's red dot is unseen, one mark a square (`cornerMarks`, `CountBadge`); every agent's status icon, never its title, one icon on the left of every row, its shape what the agent is doing and its colour whether anyone needs to act (Worker Lights, `lightOf`, `iconTone` and `STATUS_TONES` in `web/next/src/lib/status-icons.ts`): `text-destructive` Stuck, Down, Failing and No progress, `text-success` Merged, Ready and Done, `text-caution` Fixing, Waiting and Waiting on approvals, `text-info` Working, `text-inactive` Paused · usage limit, Ended, Parked and Idle; and a worker's pull request number (`PR_TONES` there), `text-destructive` while CI fails, `text-caution` in review, `text-inactive` for a draft not reviewed yet or a closed one, and `text-success` when Ready or merged, always with its state in words in the row's tooltip and on the System table's hover; the user menu square's update dot, `bg-success`, shown only while the build is behind (System status, below); and a callout in transcript text, its icon and title in its kind's colour (`CALLOUTS` in `components/transcript-markdown.tsx`: `text-info` Note, `text-success` Tip, `text-caution` Important, `text-warning` Warning, `text-destructive` Caution), its words muted (callouts are the owner's ask: "You can use note and vibe note."); and the Inbox's kinds and states, below.
- Icons only where they carry a reading, small (`size-3` on a `text-2xs` line, `size-4` for a sidebar row's logo and effort) and muted, tinted only past a rule or by an agent's state (Restraint's exceptions, above); never decorative. The Inbox's file tiles are the one exception, a file's type in Pierre's own palette (Icons, below).
- Fewer options: no new control, toggle or UI pattern without a stated reason.
- A toggle's on state stands apart from the surface it sits on, in neutral tones alone: the stock `bg-muted` fill on any other surface, and a fill, border and text of its own on a muted or input fill, as the composer's New thread does (Chat, below).
- An outline `Button` used as a toggle repeats its `aria-pressed:` fill and border as `dark:aria-pressed:` classes, since the outline variant's `dark:bg-input/30` and `dark:border-input` sort after a bare `aria-pressed:` and win.

## Layout and landmarks

- Each top-level page wraps its content in a single `<main>`. Route-group layouts (dashboard via `SidebarShell`, docs, blog) already render their own `<main>`, so add none to the root layout or you nest landmarks.
- The root layout's `<body>` holds `InnerProvider`, the theme provider, as its own child (the next-themes patch needs it there), and inside it one unnamed `<section className="contents">` around everything of ours. React hydrates body by tag, taking the first node of the tag it expects, so a body-level `div` of ours would take an extension's injected div for itself; in the section, React skips an injected div, and `contents` gives the section no box.
- A surface that has footer content renders it in a real `<footer>` as a sibling of `<main>`, never a `<div>` inside it, so the page exposes a `contentinfo` landmark. A surface with nothing to put there renders no footer rather than an empty one.
- Name a `<section>` that has a visible heading with `aria-labelledby` pointing at that heading's id, not a hand-written `aria-label`: internal authoring vocabulary ("Hero", "Call to action") otherwise leaks into the accessibility tree as the region's name. A wrapper with no visible heading (a `role="region"` scroll container) still takes `aria-label`.
- An `<img>` reserves its box with `width` and `height`: an image the changelog serves carries its size, read from the file's header (`imageSize()` in `api/hono/src/plugins/changelog/images.ts`), since one that loads unsized shifts the layout and `bun run verify cls` fails it. An image whose size is not known (a session's markdown image, `TranscriptImage` in `components/transcript-markdown.tsx`) sits in a box of fixed height instead (`block h-48 w-fit`), the image `max-h-full max-w-full` inside it, so the box holds its room from first paint.
- A scrollable region (a code block, a wide table) needs `tabIndex={0}` and an accessible name, or its overflow is unreachable by keyboard.
- No visible scrollbars: one rule in `app/globals.css` hides every native scrollbar (`hideScrollbars` in `packages/scripts/src/shadcn-customize.ts` puts it back after a shadcn sync), so a region scrolls by wheel, trackpad, touch and keys with no bar or track. Add no scrollbar styling of your own and no ScrollArea for looks; keyboard reach still rests on the rule above, and focus moving inside a region scrolls it into view.
- Top-level full-height surfaces (the body, marketing pages, the `SidebarShell` root) use `min-h-svh`, matching the shadcn sidebar; no `dvh`. A surface nested inside the shell content pane (route `error`/`loading`, dashboard/console content) fills it with `flex-1`: the shell `<main>` is `flex min-h-svh min-w-0 flex-1 flex-col`, so do not re-assert `min-h-svh` inside an already-full-height parent.

## Motion

- Every looping or auto-playing animation is gated on reduced motion. For a Tailwind utility use the `motion-safe:` variant (`motion-safe:animate-pulse`). For a keyframe Tailwind does not ship, declare it next to the section that uses it and wrap the rule in `@media (prefers-reduced-motion: no-preference)`; marketing keyframes stay out of `globals.css`.
- Anything that moves for more than five seconds also needs a pause affordance, on both hover and `focus-within`, so a keyboard user can stop it (WCAG 2.2.2).

## Components

## Data tables

Every table uses the `components/data-table.tsx` family, the console's pattern; never hand-roll a `<Table>`. The one exception is a table in a transcript's text, which `TranscriptMarkdown` draws on the stock `ui/table` parts in one bordered box (`.agents/dashboard/messages.md`). A dashboard table follows the console's users table (`console/(access)/users`): one `DataTableToolbar` row of search, at most three `DataTableFacetedFilter`s (Linear's Status, Project and User; the owner: "new filter user, and project like all"), a ghost text button for rows kept out of view (`Show 3 hidden`, `Show 2 idle`) while there are any, and table-level actions such as Refresh in its `actions` slot, over `DataTable size="sm"`. The row wraps only where the screen is narrower than it (a phone), so the page never scrolls sideways. A summary table with no toolbar (the Dashboard's readings and footprints, Plan's and Usage's tables) takes `useStaticTable`, which keeps its sort in local state, since a page can hold several and one `sort` param would drive them all; give each its own `aria-label`, never its section heading's words. The full architecture and behaviors live in ZeroStarter's `manage/data-tables` docs page (zerostarter.dev), which this fork does not carry; the sharp-edge rationale is commented in the module at each site it bites. The pure table logic (width measurement, the column-config fold, the slack rule, and the sort-whitelist lookup) lives in `lib/data-table-layout.ts` and is unit-tested, so change it there and add a case rather than tweaking widths in the renderer. `lib/data-table-features.ts` is the other half: the one `tableFeatures(...)` value every `ColumnDef`, `Column` and `Table` type is generic over. TanStack v9 bundles nothing by default, so a method exists only where its feature is registered, a row model only where its slot is filled, and a `filterFn`/`sortFn` named by string only where that map holds it, an unregistered name being a compile error. Register there, not per table.

- Toasts are raised with `toast.add({ title, type })` from `@/components/ui/toast`, the manager the component itself exports, and are rendered by the `Toaster` mounted in `providers.tsx`. `type` is `error`, `success`, `warning`, `info` or `loading`. No wrapper and no toast library: the component is used the way it ships, but for its loading icon, `RiLoader4Line` like every loader, which `shadcn-customize.ts` swaps back in after a sync (`loader4`). The surface stays neutral and the kind shows in the icon, red for an error.
- Selection actions live in `selectionActions` on `DataTable`, which floats them in a bar over the bottom of the table while rows are selected and always ends them with Cancel. The bar's look is `FLOATING_BAR` (`lib/floating-bar.ts`), which the aside's tab squares, the viewer's bar and its before/after pair's bar share. Do not put them in the toolbar, whose right side is for table-level actions like adding a row. Add a select column only when the table has such an action.
- **Glass** (`GLASS` in `lib/floating-bar.ts`; the owner on #i949: "one glass, one way to light a control"): everything that floats over a page or a picture takes one see-through look, `bg-popover/60` with a border, `shadow-md` and `backdrop-blur-md`: every `FLOATING_BAR` and every tooltip, whose popup has no arrow (`glassTooltip` in shadcn-customize).
  An icon square on a floating bar (the aside's `ICON_TAB`, the viewer's `SQUARE`) takes `BAR_ITEM`: borderless with no ring, lit `bg-foreground/10` alike on hover, keyboard focus, pressed and chosen.
- Compose headless: the page owns the TanStack Table instance (`useDataTable` for server-driven, `useDataTableState` + the shared `features` for client-side, `useStaticTable` for a summary) and renders `DataTableToolbar` + `DataTable`. A page's default view, should one need it, is `useDataTableState`'s `defaultFilters` (no page passes one now: Linear's went at the owner's "don't set default filter bugs or anything"): a facet the URL leaves out takes its default, one it names empty (`?project=`) is cleared on purpose and stays so, and the instance's `initialState.columnFilters` takes the hook's `initialColumnFilters` so the toolbar offers Reset only off that view and Reset returns to it. A table that remembers its picks across visits (Linear's) keeps them in localStorage as the composer's drafts do: it writes them as the person picks or resets (wrapping the hook's `onColumnFiltersChange`), and a URL that names no facet brings them back (`seenFilters` in `lib/linear.ts`). Infinite scroll with virtualized rows everywhere; never numbered pagination.
- Layout lives in a colocated `Record<string, ColumnConfig>` in the table's `data-columns.tsx`, written in column order; never put widths inline in column defs. Widths are Tailwind spacing units; omit `width` to size from the measured `meta.label` plus `extra` (default 10, snapped to the 3-unit grid), measured from build-time font metrics rather than at runtime.
- One `flex: true` column grows; the capability reaches back to every column before it and the last visible capable column takes the slack. Keep a select column left-aligned so inherited growth reads as gap. No trailing spacer columns.
- Prefer `extra` over an explicit `width` on a sortable column: the auto path reserves the allowance for the sort button, a fixed width reserves nothing and the header cell clips.
- A time column renders a relative time through `relativeTime` from `@/lib/time` (`5 min. ago`, `just now` under a minute), not a formatted date, because a reader scanning a log wants how long ago rather than a calendar lookup. Absolute times are for what leaves the screen: a copy, an export, an API response. A row with nothing to show renders `-` rather than an empty cell.
- Column ids say what the column shows, not the backing field (`status` over `banned`), and `meta.label` is the single source for header text, measured width, and the view-options entry (`DataTableColumnHeader` takes no title prop). Cells are plain text via `DataTableCellText` (truncate + tooltip by default, `wrap: true` to fold); no badges in cells for now. The exception is a cell whose control _is_ the row's primary action and belongs on the row rather than behind a menu: the console's role cell is a `Select`, because changing a rung is the one thing that table exists to do. One control, never a cluster. A row's labels are one muted `text-2xs` line under the cell's text, never Badges and never a column of their own.
- A row's actions are one icon-only `RiMoreLine` menu in a headerless `actions` column at `{ align: "center", width: 12 }`, as the console's tables have it. An action that reaches past the dashboard, such as one typed into a session, opens `ConfirmDialog` first, saying exactly what it sends and what that sets going; keep the last intent in a ref so the dialog keeps its words while it closes. What an action left on a row (a request's state) gets a text column of its own, never the menu's cell.
- Sort UI is a plain label plus a bare icon-only sort button toggling asc/desc (icon before the label on right-aligned columns); hiding lives in `DataTableViewOptions`. Give the table a visible `defaultSorting`; tables are single-sort.
- Any file that reads a `table`/`column` instance needs the `"use no memo"` directive, or the React Compiler freezes it one render behind.
- A page hosting a full-height table passes `className="flex h-svh flex-col"` to `PageShell` and keeps `flex-1 min-h-0` on every wrapper down to the region; `min-h-svh` ancestors are not definite, so the flex chain would not fill.

## File and export naming

- Components are grouped by domain folder (`common/`, `shell/`, `console/`, `dashboard/`, `docs/`, `blog/`, `marketing/`, `ui/`), with kebab-case file names. A single-component file's basename matches its export; a multi-export slot file is named `<area>/sidebar.tsx` (console, dashboard, docs) and its exports follow the sidebar-slot rule below. `docs/` holds one of each (`docs/sidebar.tsx` + `docs/copy-as-markdown.tsx`). A domain folder may also hold a context module named for what it carries, whose exports share that name as their prefix (`console/role.tsx` exports `ConsoleRoleProvider` and `useConsoleRole`). A cross-domain family follows the shadcn single-module pattern as one top-level file whose exports share the family prefix: `data-table.tsx` exports `DataTable`, `DataTableToolbar`, `useDataTable`, and friends.
- Sidebar slot exports follow one rule: domain-prefix the generic-role names (`Nav`, `Header`, `Footer`, `Search`) so they read unambiguously and never collide across areas (`console/sidebar.tsx` imports `DocsNav`). So `ConsoleNav`, `ConsoleHeader`, `DashboardFooter`, `DocsNav`, `DocsFooter`, `DocsSearch`. Leave a distinctive content name bare (`OrgSwitcher`, `CopyAsMarkdown`): a domain prefix on a self-explaining name is redundant.
- `shell/` holds the shared app-shell chrome as two families, `Sidebar*` (`SidebarShell`, `SidebarAdaptive`, `SidebarFloatingTrigger`, `SidebarDropdownMenu`, `SidebarUserMenu`) and `Page*` (`PageShell`, `PageHeader`). "Shell" denotes structural layout scaffolding, not one specific component.
