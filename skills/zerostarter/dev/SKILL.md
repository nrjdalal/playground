# Dev Stack

`bun run dev` runs both apps (Next.js web + Hono API) through **portless**: stable named `.localhost` URLs off portless's own proxy, instead of raw ports. A machine puts that proxy on https on 443 once, with its owner's password: `install.sh` does it on a first install (`proxy_service()`, which skips a machine whose proxy a stack would already start on, by `proxyRefusal()`'s rule, the rule `playground doctor`'s `portless proxy` row checks), or by hand in the owner's own terminal in the main checkout, `sudo node_modules/.bin/portless service install` (a root proxy kept at boot, its state in `~/.portless`), then `node_modules/.bin/portless trust` (its CA in the keychain); until then a machine whose proxy portless already keeps on `:1355` serves plain http there, and on a fresh machine `bun run dev` refuses with those two commands (`proxyRefusal()` in `api/hono/src/lib/dev/proxy.ts`), since portless would ask for sudo with no terminal to ask in. Bun's fetch reads no keychain, so `bun run verify` runs itself again with portless's `ca.pem`, the `playground` command's dashboard check passes it on each request, and `packages/scripts/src/portless.ts` gives it to every app it starts as `NODE_EXTRA_CA_CERTS` (`packages/scripts/src/portless-ca.ts`), and agent-browser opens an https stack with `--ignore-https-errors` (the `ui-verify` skill). Every stack follows the move with no change of its own, so read a stack's URLs from `bunx portless get`, never a written port. In a linked worktree the branch name prefixes each host, so parallel worktrees never collide on a port. Each stack signs in on its own: every stack's cookie sits on the shared `.playground.localhost` domain, so it is named by the stack's branch prefix (`dashboard.session_token` on the live dashboard; the main checkout's unprefixed stack keeps `better-auth.session_token`), and a sign-in on one stack leaves every other stack's session alone. Bare `bun run dev` uses turbo's TUI, which needs an interactive terminal; run stream mode in the background instead, as a background task of your own session (Bash `run_in_background`) rather than detached with `( … &)`. A worktree's stack (any checkout under `.claude/worktrees/`, or a session with `PLAYGROUND_ROLE`) reads a **fixture**, a made-up machine under a Test data badge (`.agents/dashboard/stack.md`): the launcher writes it fresh into `.turbo/dashboard-fixture` and drops it when the stack stops, and nothing on the stack reaches cmux or `~/.claude`. The live dashboard's checkout (branch `live.branch`), a stack with `PLAYGROUND_LIVE_READS=true` and a person's own clone read the live machine, through cmux, which answers only a process that descends from one of its terminals: turbo drops cmux's capability token from the environment, so a live-reading stack detached to launchd is refused even when it was started inside cmux, unless cmux holds no live factory session, when it reads herdr alone (Start, below) and the board shows none of your own cmux sessions.

## Start

A worktree that runs no stack (a docs-only or lockfile-only chore) needs no `.env`: it runs `check-types` and the packages build (`bunx turbo run build --filter='./packages/*'`, quoted for zsh; turbo's flags go through `bunx turbo run build`, since `bun run build <flags>` hands them to build-sizes.ts), and commits, under `env NODE_ENV=production SKIP_ENV_VALIDATION=true`, which pass auth's env validation and pre-commit's env-keys step. A worktree that runs a stack starts its `.env` from `.env.example` (a copy of another checkout's `.env` carries that checkout's database, the live dashboard's included) and sets `BETTER_AUTH_SECRET`, which it leaves empty and env-keys requires, to the output of `openssl rand -hex 32`. `POSTGRES_URL` may stay empty for a commit and a stack, since pre-commit's env-keys and the build pass without it (measured 1 Nov) and the stack then starts in first run's setup, whose Start a local container fills it; `bun run test` needs it, since a test that loads the database's env fails without it, so to set it yourself, point it at a container of its own, published on loopback alone: `docker run -d --name playground-<worktree>-db -e POSTGRES_PASSWORD=<pw> -p 127.0.0.1::5432 postgres:alpine`, then `docker port playground-<worktree>-db 5432` for its port (`bun run db:migrate`, the `db-migration` skill's Apply step, migrates it). `REDIS_URL` stays blank unless the work touches the merge lock's Redis; then start `docker run -d --name playground-<worktree>-redis -p 127.0.0.1::6379 redis:alpine` and set it to `redis://127.0.0.1:<port>` from `docker port playground-<worktree>-redis 6379`. Stopping a container started with `--rm` also removes it, data and all: before a stop that must keep the container, check `docker inspect -f '{{.HostConfig.AutoRemove}}' <name>`.

`bun run dev` first refuses while this checkout's stack runs (`api/hono/src/bin/dev-running.ts start`, so its build never cleans that stack's `dist`) and writes a fresh checkout's `.env` (below), then builds the workspace packages the API imports when one resolves to nothing, a fresh worktree or a pull that added an export (`packages/scripts/src/verify/prebuild.ts api`), then runs the launcher, `api/hono/src/bin/dev.ts`, which hands `turbo run dev` its arguments and the shell's environment with these changes (`devEnv()` in `api/hono/src/lib/dev/launch.ts`), besides setting portless's proxy settings. It drops an exported `NODE_ENV` and `SKIP_ENV_VALIDATION` and prints a `dev: ignoring …` line for each, since the worktree commit recipe exports `NODE_ENV=production` and a stack under it boots in the production stage; the stage comes from `.env`, and `/api/health` names it in `environment`. It drops an exported `PLAYGROUND_HERDR_ALONE` the same way, since only its own herdr-alone start sets it. It also sets `GIT_SHA` to HEAD's short sha, which `/api/health` reports. turbo then builds the workspace packages and starts the apps, never building `@api/hono`, whose own dev task's `tsdown --watch` writes the `dist` a build would clean mid-start (turbo.json's `@web/next#dev` lists the packages web's dev builds).

A checkout with no `.env` gets one in that first step, before the build whose packages check it, from `.env.example` with `BETTER_AUTH_SECRET` generated (`firstEnv()` in `api/hono/src/lib/dev/first-env.ts`, a `dev: started .env …` line); an `.env` already there stays as it is.

Before turbo starts, the launcher's `preflight()` (`api/hono/src/lib/dev/launch.ts`) refuses, with a `dev: refusing to start: …` line naming the fix and exit 1. It checks cheapest first:

- the branch, whose last segment portless cleans into a linked worktree's name prefix (`prefixOf()`, lowercased, other characters to hyphens, ends trimmed): a detached HEAD, or `main`, `master` or a branch that cleans to nothing in a linked worktree, would claim the bare `playground.localhost` names, so create a branch (`git switch -c <name>`); a branch other than `live.branch` that cleans to `dashboard` (`feat/dashboard_`) would claim the live dashboard's own names, so rename it (`git branch -m <name>`).
- the bare names: a checkout that is not a linked worktree (the main checkout, or a clone on any branch) gets `playground.localhost` and `api.playground.localhost` from portless, so it is refused while portless's routes hold either (`heldBareHosts()`: the live dashboard's aliases, or another stack); start it in a worktree of its own. First, such a checkout removes each alias of those names whose port nothing listens on (`clearStaleAliases()`), an earlier dashboard's leftover, which portless would otherwise keep forever, printing `dev: portless removed the stale alias <name> -> <port>`.
- the API's settings (`apiSettings()`: `CLAUDECODE`, `PLAYGROUND_CMUX_SESSIONS`, `PLAYGROUND_FIXTURE`, `PLAYGROUND_FIXTURE_DIR`, `PLAYGROUND_HOSTED`, `PLAYGROUND_LIVE_READS`, `PLAYGROUND_ROLE`, `NODE_ENV` and `POSTGRES_URL`, read as the API reads them, from `.env`, the shell, then `.env.<stage>`), once the branch passes; an unreadable one prints the reader's own error.
- where the dashboard reads from (`dashboardSource()` in `api/hono/src/lib/dashboard/fixture.ts`, `.agents/dashboard/stack.md`'s source rule): a hosted build (`PLAYGROUND_HOSTED=1`, the rule's first) reads no machine whatever else is set, so `bun run dev` writes no fixture and asks no cmux there; otherwise a worktree under `.claude/worktrees/`, a session with `PLAYGROUND_ROLE`, a test run or `PLAYGROUND_FIXTURE` reads the fixture, and a person's own clone reads their machine. `PLAYGROUND_FIXTURE` on the live dashboard's checkout, or beside `PLAYGROUND_LIVE_READS`, is refused, and so is a fixture file that does not load (its path and the key that fails are named), and an own-machine start under Claude Code with no `PLAYGROUND_ROLE`. A fixture stack goes on to the database with no cmux check, since asking cmux would open the live socket.
- on a live-reading stack, the opt-in to cmux's sessions: without `PLAYGROUND_CMUX_SESSIONS=true` the stack reads herdr alone, the sessions Playground started, and asks cmux nothing, printing `dev: the dashboard reads herdr alone, the sessions Playground started; …`; the live dashboard's `.env` must set it.
- on a live-reading stack that opts in, cmux, read once (`attachment()` in `api/hono/src/lib/dashboard/cmux.ts`) in the environment the stack's API gets, every `CMUX_` variable dropped as turbo drops them, so it answers only by descent from a cmux terminal: a start from outside cmux, or detached with `( … &)`, is refused, and so is a missing cmux or one that does not answer, each judged by cmux's own answer, while cmux holds a live factory session or whether it does cannot be read; with none live (`cmuxHeld()`, from `ps`, Claude's registry and the roster, never cmux, counting a session the hooks place in the factory alone, so one of your own never holds it), the stack starts reading herdr alone, `PLAYGROUND_HERDR_ALONE=1`, asks cmux nothing and shows none of your own cmux sessions. Start the stack in a cmux terminal or as an agent's background task. A stack started attached and orphaned later passes this check, as a background task whose agent session ends, or `nohup` with its shell closed; the dashboard then reports cmux unavailable, and `bun run dev:stop` ends it.
- `POSTGRES_URL`: unset or empty, the stack starts in setup mode and the remaining checks are skipped, since the API then serves only first run's setup routes and `/dashboard` opens on first run's checks, whose Database row's Start a local container makes this checkout's own container, migrates it and writes its URL into `.env` (`.agents/dashboard/stack.md`); on the live dashboard's checkout (branch `live.branch`) that container is the live dashboard's database, named `live.container` plus pglaunch's 4-character suffix, and the start is refused while `docker ps -a` lists a live dashboard's database pglaunch cannot reuse (`.agents/dashboard/stack.md`), naming it so you point `POSTGRES_URL` back at it.
- the container that publishes its port, read from Docker's metadata alone: `live.container`, the live dashboard's database (or `live.container-XXXX`, the one first run starts there), anywhere but the live dashboard's own checkout (branch `live.branch`), refused by name before anything runs inside it or connects to it.
- the session importer's guard (`api/hono/src/lib/sessions/guard.ts`), which must prove the URL reaches a Docker container on this machine published on loopback alone. It refuses a remote or Neon host, Docker missing or down (start Docker), a port no single running container publishes (a stopped container: `docker start playground-<worktree>-db`, then `docker port` for its port; or a tunnel), a container published on 0.0.0.0, and a server that is not that container's. A container removed between Docker's list and its inspect (another stack's database stopping) is skipped by one re-list rather than refused; the URL's own port must still be proven. A second vanish in a row refuses, naming the container and saying Docker is up, so run `bun run dev` again.

A pass prints `dev: database <proof>`; on the live dashboard's checkout (branch `live.branch`) the launcher then sets `PLAYGROUND_BARE_NAMES`, which `packages/scripts/src/portless.ts` reads to trust the bare web origin beside the apps' own `desk.` URLs, and every 2s points the aliases `playground.localhost` and `api.playground.localhost` at the ports portless gave the apps, read from its routes (`syncAliases()` in `api/hono/src/lib/dev/launch.ts`), printing `dev: portless alias <name> -> <port>` each time one moves. An alias never takes a name a running stack holds; the failure prints once. Then it prints `dev: dashboard source matched <rule>`, then `dev: dashboard reads the fixture written to <dir>` on a fixture stack, or, on a stack reading this machine, a line saying it shows every real session, so take no screenshots of it. On the live dashboard's checkout and a person's own clone it then runs the main checkout's `bun run ops:herdr start` (never this checkout's, which on the live dashboard is its branch's latest head), which brings the herdr servers up when they are down (playbook's LIFECYCLE.md, Ops jobs), and prints its `dev: ops-herdr: …` line; the stack starts whatever that line says. A dry run (`--dry`, `--dry-run`, either with `=json`) starts nothing and skips the launcher's checks; `bun run dev` hands its arguments to the launcher alone, so the running-stack refusal and the prebuild still run before it.

Start the stack on its own, as one Bash call with `run_in_background: true`:

```bash
bun run dev --ui stream > /tmp/playground-dev.log 2>&1
```

Then, in a separate foreground call, wait for it and check it:

```bash
# Resolve this worktree's URLs (branch-prefixed); the proxy needs a moment, so retry
for i in $(seq 1 60); do WEB=$(bunx portless get playground 2>/dev/null); [ -n "$WEB" ] && break; sleep 1; done
API=$(bunx portless get api.playground)
curl -sf --retry 60 --retry-delay 1 --retry-connrefused "$API/api/health" > /dev/null
curl -sS "$API/api/health"                        # {"data":{"db":"ok","dashboard":"fixture","message":"ok",...}}
curl -sS -o /dev/null -w "%{http_code}" "$WEB/"   # 200
```

Ready when the health curl prints `"message":"ok"` with `"db":"ok"` and `"dashboard":"fixture"` (`"live"` on the live dashboard, a live-reads stack or a person's own clone, `"hosted"` on a hosted build) and `/` returns `200`. To fill the Sessions page's tables from the fixture's transcripts, run `bun run ingest` once in the worktree: on a fixture stack it reads the fixture's config folder, and the Sessions pages show only what it read from there, so a database an older stack filled shows none of its old rows. `bunx portless list` shows every active route.

Then run `bun run verify health` (it checks the version against your `HEAD`) and grep the dev log for `Is port`: portless can hand a new API a port another worktree's Next already holds, and `/api/health` then answers from the other stack. `verify` runs one check a call: for several, run each (`verify health`, then `verify cursor`) or `verify all`, which a bare `bun run verify` runs too; a word after any check but `pages`, `extension-node`, `screenshots`, `cls`, `tooltips` or `all` is refused, not ignored, but for `ended`, which takes one session name.

- Web / API base URLs: `bunx portless get playground` / `bunx portless get api.playground`
- Scalar API docs: `$API/api/docs`
- Logs: `tail -f /tmp/playground-dev.log`

**Fixed ports:** `PORTLESS=0 bun run dev` skips the proxy and serves web on `:3000`, api on `:4000` (the ports the curl examples in other skills assume). It runs a single stack only: two worktrees on fixed ports collide, which is why portless is the default.

## Stale-route trap

The API dev task runs `bun --hot src/main.ts` (the dev entry: it serves `src/index.ts`, which picks `local.ts`'s app or, under `PLAYGROUND_HOSTED=1`, `hosted.ts`'s; or setup mode while `POSTGRES_URL` is unset), and **`--hot` does not pick up newly created files** (new routers, new schema exports). The symptom is a route that exists in source returning `{"error":{"code":"NOT_FOUND"}}`. Touching files does not clear it; only a full restart does.

Stop the stack through the background task that started it: `TaskStop` with that task's id ends its whole process tree, turbo and every child it spawned. That includes `next-server`, which would otherwise keep its port, so the next `bun run dev` dies with "Another next dev server is already running", and the `.bin/portless` supervisors that hold this worktree's routes. Signal only processes you started; never select pids by name or pattern, since a pattern matches the live dashboard and every worker's stack. A stack whose starting session has ended is out of `TaskStop`'s reach: `bun run dev:stop` in its worktree ends it. When `dev:stop` or a second start refuses, read [STOP.md](STOP.md): the launcher's record, which processes `dev:stop` may signal, and what each refusal names. The launcher drops a fixture stack's scratch copy as it leaves, so the next start begins from the fixture again; it hands the stack `PLAYGROUND_FIXTURE_LAUNCHED`, so the API, which can outlive the launcher until `dev:stop` kills its group, never writes the copy back. In the live dashboard's checkout (branch `live.branch`) `dev:stop` signals nothing without `--live-dashboard`, since that stack is its runner's. When `dev:stop` refuses, report the stack to your lead, and carry on in a fresh worktree off the same head on a new branch, whose prefix gives it fresh routes and a fresh `.next`. `bunx portless list` showing no route for this branch confirms the old stack is gone; the shared proxy keeps running, since it hosts every worktree's routes.

Then start it again as in **Start**: `bun run dev --ui stream > /tmp/playground-dev.log 2>&1` alone, with `run_in_background: true`, and in a separate foreground call:

```bash
API=$(bunx portless get api.playground)
curl -sf --retry 60 --retry-delay 1 --retry-connrefused "$API/api/health" > /dev/null
```

This worktree's apps re-register with the proxy on restart. Done when the previously-NOT_FOUND route responds.

Stop the stack before you commit: pre-commit's build rebuilds `packages/*` under it and hangs it, so pre-commit refuses while the stack runs. The web's build and check-types clear `web/next/.next/dev/types` first, which `next dev` writes for the pages it served, so a stack stopped mid-write (`TS1128`) or a branch switch away from a page (`TS2307`) leaves no stale type behind; check-types also runs `next typegen` to rewrite `.next/types` for this branch, and turbo runs web's build after it (`@web/next#build` depends on `check-types`), since `next build` deletes and rewrites the `.next/types` its tsc reads.

Restart the same way after changing `@packages/*` exports the API consumes: they resolve to built dist, so run `bunx turbo run build --filter=@packages/<name>` first.

To roll a stack onto a PR's head, stop it, run `git fetch origin <PR branch>` and `git checkout -B <the stack's own branch> <sha>` (`git branch --show-current` names it), then start it again: the stack's own branch keeps its portless names, while the PR's branch is refused (its worker's worktree holds it) and a checkout of the bare SHA leaves a detached HEAD, which the launcher refuses.

`/api/health` reports the sha HEAD had when the stack started: the launcher passes it as `GIT_SHA` (turbo.json's `passThroughEnv` on `dev`, so a commit costs no cache), and `getBuildVersion()` reads it ahead of the sha baked into `@packages/env`, which turbo replays from cache when only the commit moved. A stack started before a checkout keeps reporting the older commit until it restarts, which is what `bun run verify health` catches.

## Docker hung

A stack whose `/api/health` reads `"db":"unreachable"` (`"message":"degraded"`, named by `bun run verify problems`) with the API itself answering means Docker stopped answering: the database is fine, its engine is not. Recover OrbStack itself: `orbctl stop`, then `orbctl start` (`orb restart docker` alone hung; 8 Oct, 01:05Z to 01:47Z). Done when the health curl prints `"db":"ok"` again.
On the live dashboard, ops-unstick runs this restart itself on the first cycle `docker info` times out with the dashboard's db unreachable, so a live outage needs no hand restart.

## The live dashboard's build

The live dashboard runs `origin/canary`'s latest head (`.agents/dashboard/live.md`), and only its runner moves it (playbook's **dashboard** rule). ops-dashboard's supervisor (`scripts/ops/dashboard/supervisor.sh`) rolls it on each canary move, after its holds, or at once on a `roll-now` file, which `playground update` writes (`.agents/dashboard/live.md`); the steps below are the same roll by hand, stop-first, from the dashboard's checkout, for a canary head not in `ops/dashboard/bad-builds`:

1. Stop the stack through its background task (`TaskStop`), the `bun run ingest` follower, and the web the supervisor runs on its own (`bash scripts/ops/dashboard/procs.sh stop dashboard-web`).
2. `bash scripts/ops/dashboard/redeploy-pull.sh <canary sha>` in the dashboard's checkout: it resets `live.branch` to that head (the branch stays `live.branch`, which the dashboard's source and its portless names need), installs when `bun.lock` or a `package.json` moved, builds `packages/*` when a package outside `packages/scripts` moved, and migrates when `packages/db/drizzle` moved, printing `install`, `build` and `migrate` (`migrate-held` for a migration that only builds indexes, one of them on `claude_entry`, which Ops runs at a quiet moment; any other migration runs at once, since a table or a column it adds is one the new head's code uses), then restarts each ops job whose source the move changed, printing `ops-restart:` lines ([ops-restart](../../../scripts/ops/README.md#when-a-job-restarts-onto-new-code)).
3. Build the head by `supervisor.sh`'s `build_head` lines: its `bun run build` with the settings that line sets, then its `cp` lines into `ops/dashboard/builds/<sha>`. Serve it with `PLAYGROUND_BUILD=<that folder> bun run serve`, then start the follower, both as background tasks of the runner's own cmux session.
   This serves the web and the API together under the launcher, the stop-first roll without the supervisor's web swap; stop that stack through its task before ops-dashboard starts again, since the supervisor runs its own web and moves the web's route, which this stack's web holds until it stops (until then the supervisor's start reads as refused and is retried).
   Done when `ops/dashboard/builds/<sha>/web/web/next/server.js` exists and the stack answers.
4. `bun run --cwd <dashboard checkout> verify --expect <live.branch>`, which finds the dashboard's URLs through portless.

Done when verify passes. When the pull exits non-zero once it reset to that head, the stack does not start, or verify fails, add the sha to `bad-builds` (a stack that refused to start, a `dev: refusing to start:` line, joins it only for the settings refusal, on its third of the same head: `.agents/dashboard/live.md`), roll back to the head it ran before by the same steps (never after a migration, which stays for Ops), and report it to Ops.

## Agent login

Sign in as `LocalAgent` (local only, trusted Origin required). The route is gated on `AGENT_SIGNIN_ENABLED`: set it to `true` in `.env` first, or the route 404s. It is off by default, so a fresh clone and any deploy expose no session-minting route.

```bash
WEB=$(bunx portless get playground); API=$(bunx portless get api.playground)
curl -sS -c cookies.txt -X POST -H "Origin: $WEB" "$API/api/agents/sign-in-as"
curl -sS -b cookies.txt "$API/api/v1/user"
```

In the browser: a visit with no session to `/dashboard` shows first run's pane, which signs the one owner in again by itself, or, with no owner yet, lists this Mac's checks and on Continue makes and signs in this Mac's owner. To sign the browser in as `LocalAgent` instead, post the request above as a form from a page on the web origin, as `signIn` in `packages/scripts/src/verify/checks.ts` does from `/robots.txt`.
