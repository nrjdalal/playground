# UI Verify

A green type-check and a clean lint prove the code compiles, not that the page renders. Drive it in a real browser before the PR.

## 1. Run the stack

Start the dev servers (`dev` skill). Under the default portless dev the base URLs are named and branch-prefixed, so resolve them once: `WEB=$(bunx portless get playground)` and `API=$(bunx portless get api.playground)` (or `PORTLESS=0 bun run dev` for the fixed `http://localhost:3000` / `http://localhost:4000`). Done when `$WEB/` returns 200 and `$API/api/health` responds ok with `"dashboard":"fixture"`: the stack reads the fixture, a made-up machine, so nothing it shows is real (`.agents/dashboard/stack.md`). A stack reading `"live"` (the live dashboard, `PLAYGROUND_LIVE_READS`, or a person's own clone outside `.claude/worktrees/`) is for checks by text alone.

## 2. Drive the affected route

Load the `agent-browser` skill, then open the route you changed and act on it:

```bash
agent-browser open "$WEB/<route>"
agent-browser snapshot   # read the page, then click/type/verify
```

agent-browser sessions are machine-wide: name yours (`--session <your-name>`), close each by that name, and never `close --all`, which closes every agent's browser. Headless Chrome plays sound, so a drive of a page that plays media (the sidebar's music player) launches muted: `--args "--mute-audio"` on the session's first command, which `bun run verify` passes itself. It then sets the player's stored volume to 0 and reloads, since the player reads it once as it mounts: `agent-browser --session <your-name> eval 'localStorage.setItem("playground:music:volume", "0")'`, then `agent-browser --session <your-name> reload`. After each check, close the session by its name, which stops any playback. Give `screenshot` an absolute path, since a relative one resolves against agent-browser's daemon, not your shell. Open an https stack with `--ignore-https-errors`, since its certificate comes from portless's own CA, not a public one.
An Inbox card's action buttons pause about 1s after the card moves (`MOVED_PAUSE_MS`), and separate agent-browser calls cost about 0.5 to 1s each (both measured), so to land the click and the keys inside the pause, drive the move and the click with `Runtime.evaluate` and the keys with `Input.dispatchKeyEvent`, all on one CDP session (Keys, below).
A new `bun run ask` item shows in a fixture Inbox only after the Inbox's next fetch (`INBOX_REFRESH_MS`), about 5 to 7s later (measured), so wait for the item to render before you assert: `agent-browser wait --text "<the item's title>"` waits for it to appear (substring match).

Behind auth, sign in first: a signed-out browser landing on `/dashboard` is signed in as this Mac's owner by the first-run pane, or post the agent sign-in as a form (`dev` skill, Agent login). For an end-to-end change, or whenever asked, drive the whole flow, not just the screen you touched. Done when you have watched the change render and behave, not merely that the route loaded.

Every agent-browser session runs headless, its default: open each one with no `--headed` and `AGENT_BROWSER_HEADED` unset, except an `--extension` session, which also takes `--args "--headless=new"` (below). A headful window opens only on the owner's yes.
On that yes, a headful window for the owner to use or watch (a sign-in, a demo) runs Google Chrome, opened with `agent-browser --executable-path "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headed open <url>`, not agent-browser's own Chrome for Testing and not Helium, and is set right after it opens with `agent-browser set viewport 1512 850 2`, 16:9 at the owner's 1512 width with 850.5 rounded down, the third argument the device scale factor, so pages render at retina density as the owner's does; the verify screenshot viewports below stay as they are.
An unpacked extension loads in a headless session on agent-browser's own Chrome for Testing:
`agent-browser --session <name> --extension <dir> --args "--headless=new" open about:blank`.
Before the page opens, confirm `--headless` in the browser's own argv: diff `pgrep -f "Chrome for Testing"` across the launch and read `ps -o command= -p <pid>` on the new main process, the one carrying `--load-extension` and no `--type=`; without the flag an `--extension` session launches headed, its argv holding `--load-extension` and no `--headless` (measured from the argv, 27 Oct). Every Chrome flag goes in one `--args` value, comma-separated: agent-browser keeps the last `--args` and drops the rest, so `--args "--headless=new" --args "--mute-audio"` launched with the mute flag alone and no `--headless=new` in its argv, while `--args "--headless=new,--mute-audio"` carried both (measured 27 Oct; the media page's `--mute-audio` above shares the value).
Then open the page, `agent-browser --session <name> open <url>`, and read its effect back with `agent-browser --session <name> get url`, since `open` itself has timed out while the URL already carried the effect (measured 27 Oct). The extension's content scripts run from the first load, with no reload and no CDP call (agent-browser 0.38.1, Chrome for Testing 154, measured 27 Oct in that shape: a repo's `/pulls` came back as `/pulls?q=is%3Apr+is%3Aopen+sort%3Aupdated-desc`, rewritten by the extension's content script). Google Chrome ignores the `--load-extension` switch in every form, `--disable-features=DisableLoadExtensionCommandLineSwitch` included, which is why the extension shape runs Chrome for Testing and not the headful Google Chrome above.
A script added through CDP's `Page.addScriptToEvaluateOnNewDocument` goes away when its CDP session detaches, so re-add it after a reattach.
Init scripts go in at launch, `--init-script <path>`; there is no `addinitscript` subcommand to add one later (agent-browser 0.38.1), though `skills get core --full` documents one. In the headless extension shape they run (measured 27 Oct: a `window.__initRan` marker set by `--init-script` read back `"yes"`; a `document.documentElement` attribute marker read back null three of three, cause not pinned down, so mark on `window`), and `bun run verify`'s own sessions run the init scripts they register on their first command (`Browser.command` in `packages/scripts/src/verify/checks.ts`). In a headful Google Chrome window by `--executable-path` and `--profile`, `--init-script` and `AGENT_BROWSER_INIT_SCRIPTS` ran nothing even at launch, cause unknown (measured with Google Chrome 155); an init script belongs in a headless session.
A page checked with its scripts off (a CSS-only mock, a no-JavaScript render) opens with `--blink-settings=scriptEnabled=false` on the session's first command, in the one `--args` value above, comma-separated beside any other flag (`--args "--headless=new,--blink-settings=scriptEnabled=false"`). Prove the scripts stayed off with a probe page whose script retitles it: done when `get title` still reads the title the HTML wrote, not the one its script sets. `eval` still runs, since CDP evaluation ignores the setting (agent-browser 0.41.0, measured 31 Oct).
With scripts off, `screenshot --full` can repeat the first viewport down the whole image: five probe pages from 1100 to 2200px tall, each shot at 1440x900 or 1440x1000, showed its top again at every viewport's height where the rest of the page belongs (measured 31 Oct), and a wait after `set viewport` or a viewport set before `open` kept the repeat (4 of 4, measured 1 Nov). So read the page's height with `eval 'document.documentElement.scrollHeight'`, `set viewport <width> <that height>`, then shoot; for a before and after pair, shoot both at the taller page's height. With scripts on, a 1183px probe shot at 1440x900 right after `set viewport` repeated too (3 of 3 from `file://`, 2 of 3 over http), and shot clean with the viewport set before `open` or after `wait 1500` following `set viewport` (8 of 8, `file://` and http, measured 1 Nov): so with scripts on, set the viewport before `open`, as `bun run verify screenshots` does before each visit. The repeat is filed upstream as [agent-browser issue 2285](https://github.com/vercel-labs/agent-browser/issues/2285).
A layout-shift check on an extension needs a no-extension baseline in the same browser (a second session) and several loads before blaming the change: GitHub's own shift on a public PR varies by page and from load to load (0 to 0.19 across public PRs and loads, measured 25 Oct).

## 3. Check it holds up

- **Visual:** capture before and after, full page, on a fixture stack, at the same viewports: `bun run verify screenshots --label before` on the pre-change state (before you edit, or a worktree of the base commit on a branch of its own), then `--label after` on the change, each taking every dashboard page at 1280×800, 1782×972 and 390×844, light then dark (`-dark` in the file name; `--out <dir>`, routes to narrow it). It fetches each route once before its first shot, `/robots.txt` before its sign-in, so a cold `next dev` compiles there rather than in the browser (`warmUp()`; under load 48 a cold first open wedged it). Each shot waits for its page's ready marker (`READY` in `packages/scripts/src/verify/checks.ts`), since network idle passes before the board's WebSocket data draws, and fails naming the marker when it never shows: a new dashboard page gets its marker in the same change. It refuses a stack that does not read the fixture. With more than one stack up (another session's, or the live dashboard), pass `--web <url> --api <url>` naming the stack the shots are for, and check the version its `/api/health` reports with `bun run verify health` and the same two flags, adding `--expect <base sha>` for `before` (it expects this checkout's HEAD by default): a version that differs means the shots came from another stack, so retake them. A fixture's times are set once, as the stack starts, so take the shots soon after: past 10 minutes its usage windows read stale, so restart the stack (`bun run dev:stop`, then `bun run dev`) for fresh ones, and to shoot the page's stale usage reading, wait past 10 minutes instead of restarting. For a state a route alone cannot reach (a dialog open, a card expanded), drive it with agent-browser on the same stack and take `agent-browser screenshot --full before-<what>.png`, then `after-<what>.png`. Run one stack at a time: take the before shots, stop that stack with `bun run dev:stop` in its worktree, then start the after stack and shoot it, reusing one browser session; two `next dev` stacks up with their browsers pushed the Mac's swap-ins past 100 a second twice on 25 Oct.
- **Fixture states:** the fixture always holds a roster and a usage reading, so reach the empty-roster, no-reading and stale-window states by editing the fixture's scratch copy, `<worktree>/.turbo/dashboard-fixture/claude/playground/` (`.agents/dashboard/stack.md`), while the stack runs, then reload: for one stale window (its hover), open the System page first, so the sampler has seen both windows, then keep one of the two windows in `usage.json`'s `rate_limits` (`five_hour`, `seven_day`) and drop the other, since emptying `rate_limits` leaves no stale reading at all. Undo an edit with a restart, as stack.md says.
- **Dashboard socket:** for a dashboard test with no first frame, hold only the dashboard socket: an `--init-script` that replaces `WebSocket` for URLs containing `/api/v1/ws` with one that never connects; the page loads, and `window.__wsBlocked` lists the held URL (measured).
- **Responsive:** check mobile, tablet, and desktop with `agent-browser set viewport <w> <h>`, and confirm no horizontal overflow: `agent-browser eval 'document.documentElement.scrollWidth <= document.documentElement.clientWidth'`.
  Loop over the sizes as one word each and split it inside the loop, the shape zsh and bash read alike (zsh keeps an unquoted `$vp` holding a space as one argument): `for vp in 390x844 768x1024 1280x800; do agent-browser set viewport "${vp%x*}" "${vp#*x}"; done`.
- **Chat scroll:** for a change to a stream, the composer or the chat's Checkpoint bar, run `bun run verify send-top` and `bun run verify cls` on a fixture stack. send-top takes Playground's session past the stream's 400-entry limit after its first send, as the live one always is, then drives both of the chat's modes at 1280×800 and 390×844 (its `--help` lists every case): in Reading the owner's send must rest 12px below the top with nothing of the step before showing and hold there through replies, other sessions' messages and a turn's end, a view the owner moves must stay where the owner put it (the owner's scroll up just after a send included, by wheel or by a long scrollbar drag, in either mode), and Scroll to end must stay Reading while the toggle counts what lands; in Watching a send must land at the end, a long turn must read behind and then Watching with the view at the end and never moving up on its own, and the owner's scroll up and back to the end must switch the mode. cls must find no shift in a chat with no composer, nor as the bar switches modes, shows and hides Scroll to end and jumps.
- **Changelog link:** for a change to the Changelog page, run `bun run changelog fixture`, then `bun run verify changelog-entry` on a fixture stack: at 390 it opens a link naming a merge older than the newest change by its PR (`?entry=pr-209`) and fails when no drawer opens, when the drawer shows another change, or when Escape leaves `?entry=` in the URL.
- **Theme:** toggle the app's theme control and check light and dark whenever the change touches either.
  After `localStorage.setItem("theme", …)`, reload the page, since reopening the URL with only a `#hash` added stays on the page it loaded. localStorage is per origin, so set it again on each host, the before stack's and the after stack's.
- **Cursor:** for a change to a control, its styles or `globals.css`, run `bun run verify cursor` (also in `verify all`): Send and Attach must read the pointer, a plain disabled button `not-allowed`, and the sidebar rail its own resize cursor (the design skill's Cursor section). With no live dispatcher, /dashboard draws no composer, so the check skips Send and Attach and says why in its line; to check those two, use a fixture whose dispatcher is live.
- **Rail:** for a change to the sidebar shell, its rail or its toggle, run `bun run verify rail` (also in `verify all`): at 1280, on `/dashboard` and on `/docs`, it clicks the sidebar rail twice, then presses Cmd+B twice, and fails unless the sidebar collapses and expands on each (a tooltip's trigger had replaced the rail's own click).
- **Scrolling a stream by hand:** in headless Chromium, agent-browser's mouse wheel and `scroll` reach no element in the chat stream. Focus `[data-slot=message-scroller-viewport]` from `eval`, then send End or PageUp (Keys, below), or dispatch a `WheelEvent` and `scrollBy` as `verify send-top` does (`SCROLL_UP` in `packages/scripts/src/verify/send-top.ts`). Those events are untrusted; for a change whose behaviour hangs on a trusted wheel, attach to the page through `agent-browser get cdp-url` and send `Input.dispatchMouseEvent {type: "mouseWheel", x, y, deltaX: 0, deltaY}` with x,y inside the stream, since agent-browser 0.38.1's `mouse wheel` fires at 0,0, over the sidebar, even after `mouse move`.
- **Keys:** agent-browser's `press` floods the page with trusted keydowns of the wrong `code` until its session closes, and its `keydown` of a modifier never holds for a later `press` (0.38.1 and 0.39.2), so attach to the page target through the browser endpoint `agent-browser get cdp-url` returns (`Target.attachToTarget` with `flatten: true`), send each key on that session as CDP's `Input.dispatchKeyEvent`, a `keyDown` carrying `key`, `code`, `windowsVirtualKeyCode` and, for a key that types, `text`, then a `keyUp`, with `modifiers` summed from Alt 1, Ctrl 2, Meta 4 and Shift 8, end by closing your own session (`agent-browser --session <name> close`), and drop this line once `press` sends one keydown with the right `code`.
- **Socket host:** `agent-browser network requests` and its HAR leave a WebSocket open out, so to check which host a socket opens on, attach to the page as Keys does, run `Network.enable` on that session, and read the `url` of each `Network.webSocketCreated` (measured: the dashboard's `/api/v1/ws` seen on the API's host, absent from `network requests`).
- **Error status:** `agent-browser network route` answers its `--body` with 200 alone, so to mock a 404 or a 500, attach as Keys does, run `Fetch.enable` with the read's `urlPattern`, and answer each `Fetch.requestPaused` with `Fetch.fulfillRequest`: its `responseCode`, a base64 `body` and, for a cross-origin read, `access-control-allow-origin` and `access-control-allow-credentials` (measured: the page's own read got the mocked 404, then 200 after `Fetch.disable`).
- **Show and hide timing:** for a change to when an element shows or hides (a delay, a hold, a fade), log two readings every frame, with `requestAnimationFrame` from `eval`: its effective opacity (its own times every ancestor's), which the eye sees while above 0, a fade included, and `closest("[inert]")`, which lets it take a click only while null. Read neither from the element's own `data-active` or opacity, since a wrapper can fade or disable it while those still read shown (whose wrapper sets `inert` at once and fades over 200ms). A requestAnimationFrame logging loop injected with `agent-browser eval` stalled the page's timers once: a setInterval counted 0 beats in 2s and the app's 1s pause never finished; the cause is not pinned down, an earlier browser session saw no stall (measured), so read a setInterval heartbeat's beats and trust the log only while the beats keep counting, and log discrete state changes with a MutationObserver on body attributes and children, which logged the same states with the timers still running. For a state that shows only while a request is in flight, such as a sending state, wrap `window.fetch` to delay that one request (an answer POST delayed by 1.5s, say), so the per-frame log spans the whole state. Run the log through every case that moves the view, the owner's wheel and keys while the element shows among them (Scrolling a stream by hand, above): one change's first head blinked Scroll to end off under the owner's own scroll, a case no unit test had.
- **Animated triggers:** fire an accordion or any other animated trigger one at a time, and before the next click run `agent-browser wait 1000`, or, sooner, wait until `agent-browser eval` reads the opened panel's `getBoundingClientRect().height` the same twice, 100ms apart. A click sent while the layout is still moving can miss the next trigger and read a false FAIL (three back-to-back clicks left Merged and closed unchanged; a 1s pause fixed it).
- **Paste:** for a change to the composer's paste or input handling, paste with the page's own objects, each event made with `bubbles: true`, since React and a listener on `window` hear only an event that bubbles. A `ClipboardEvent("paste")` carrying a page-local `DataTransfer` as its `clipboardData` reaches `onPaste` and proves its branches: the composer inserts that event's own text/plain itself, so its words land in the box with one `input` event a line, which you check in the box's value after the dispatch, and files or a long paste become a file. `beforeinput` and `input` with `inputType: "insertFromPaste"` prove what their listeners record and insert nothing, since an untrusted event runs no default action. A busy loop in the page before a dispatch stands in for a slow page, never for a race with an app outside the browser. The Mac's clipboard is the person's own, so a test leaves it untouched: no Chrome copy or paste command, no `pbcopy`, no accessibility value set (a tester's copy runs landed on the owner's pasteboard while the owner dictated).
- **Slash menu:** for a change to the composer or its `/` menu, run `bun run verify slash-menu` on a fixture stack (also in `verify all`, which skips it on any other): at 1280 and 390 it types `/` into Playground's box and fails when the menu is over 7 rows tall, its rows differ in height, it does not scroll, it runs past the composer's edge, or the skill the arrows reach is cut off, after ArrowDown to the last skill, after the wrap back to the first, and with a `/` typed mid-line near the right edge, where a skill once drew partially, about 80%, in the view. It sends nothing and empties the box after.
- **Aside bar:** for a change to the tab squares beside a chat, the panes under them or `FLOATING_BAR`, run `bun run verify aside-bar` on a fixture stack: at 1440 it scrolls the Inbox, Pages and each app's pane to its end and fails when the aside's bottom edge, where the bar hides, cuts off any of its last line (shown, the bar floats see-through over it by the owner's ask), and, with the bar called up as a pointer near the aside's bottom calls it (it hides as a dock does), lays a layer at the highest z-index over each pane and fails when it covers the bar; at 390 it fails when the bar covers the composer or holds no Menu square; at both, when a square has no name or Tab reaches a pane before the bar. An Inbox with cards in it (posted with `bun run ask new` into this checkout's database) is what makes its pane scroll.
- **Focus marks:** for a change to a control, its styles, `globals.css` or a focusable pane, run `bun run verify focus-marks` on a fixture stack (not in `verify all`): on five dashboard pages (`FOCUS_PAGES`) at 1280, in one theme and with no menu open, it focuses every focusable control as a key would and fails naming each whose border, fill, text, underline and visible shadow or outline, on it, its parent and its field, all read the same before and after (with no ring, 96 controls showed no focus).
- **Reply focus:** for a change to an Inbox card's Chat about it or to the composer's focus, run `bun run verify reply-focus` on this checkout's own fixture stack (also in `verify all`, which skips it on any other): at 1280 it posts a card with `bun run ask`, waits for the card and for Playground's box, which can mount after the card on a loaded host, clicks its Chat about it and fails unless focus is in Playground's box in that same frame, where a dictation app's Cmd+V sent at once lands. It settles the card after.
- **Send focus:** for a change to the composer's send or its focus, run `bun run verify send-focus` on a fixture stack (not in `verify all`, since it sends the fixture's dispatcher one message): at 1280 it clicks Send on words the composer refuses (a trailing backslash it would keep), then types a message and sends it with a real click on Send, and fails unless focus is back in the box 0.5s after the refusal and 0.5, 2 and 6s after the send, where a dictation app's late Cmd+V lands.
- **Typing lag:** for a change to what a board frame or a new stream step redraws (the sidebar's rows, the stream's rows, the selectors over them), run `bun run verify typing-lag` on this checkout's own fixture stack (not in `verify all`) at load1 under the core count: at 1280 it streams a 20-session board each second and a growing stream, types a sentence into Playground's box at 100ms a key, and fails when the page's own work on a key (the wait for the main thread, its handlers, its frame's render) passes 50ms at the 95th percentile. The keydown-to-paint it prints beside that is not judged, since on a loaded machine most of it is the browser waiting for a frame. It empties the box after, sending nothing, and ends the dispatcher's and the peer's turns with an end-turn line; the long turn it wrote stays in the fixture's scratch copy until the stack restarts.
- **Upload keep:** for a change to the composer's uploads, run `bun run verify upload-keep` on a fixture stack (not in `verify all`): at 1280 it refuses the upload route at the browser, as the page sees it while the API restarts, pastes an image into Playground's box and fails unless its chip reads Queued, reads Queued again after a reload, and uploads once the route answers. It removes the chip after, sending nothing.
- **Hydration:** read a hydration error from Next's dev overlay, since a recoverable one reaches neither agent-browser's `console` nor its `errors`. The overlay and its Issues badge live in `nextjs-portal`'s shadow root, which `agent-browser find text` cannot reach: read the count (`[data-issues-count]`) and click through the issues from `eval`, through `document.querySelector("nextjs-portal").shadowRoot`. For a change to the root layout, the shell or what renders at body level, run `bun run verify extension-node` (also in `verify all`): each page loads with a screen recorder's node in body, a div as Scrnli adds it after the theme script, and fails when the overlay counts any issue. The body's shape that keeps it green is the design skill's (Layout and landmarks).
- **Tooltips:** for a change that adds or moves a hover, run `bun run verify tooltips` (also in `verify all`): on each page it counts the elements the browser would show its own title box for (a `[title]` but a previews iframe, or an `svg title`, that has words; recharts' empty chart `<title>` draws nothing) and fails on any, then times the dispatcher row's usage Tooltip opening on hover, failing before `TOOLTIP_DELAY_MS` (1s) or 300ms past it, and the header GitHub icon's on Tab, failing past 300ms. A hover is shadcn's Tooltip through `Hint` (the design skill's Tooltips).
- **Hint-wrapped controls:** a control wrapped in `Hint` reads `data-slot=tooltip-trigger` instead of its own, so a test selects it through its parent label: `label:has(> [data-slot=questionnaire-choice-input])` for a Questionnaire choice.
- **Faceted filters:** for a change to `FacetedFilter` or the `ui/command` parts it uses, run `bun run verify facets`: at 1280 and 390 it opens every faceted filter on the Changelog page and passes when each one's counts end at one x, a right-aligned column, with at least two counts compared. On a fixture stack, run `bun run changelog fixture` first, which gives the Changelog the entries its facets count. It picks nothing.

Done when Visual, Responsive, Chat scroll, Changelog link, Theme, Cursor, Focus marks, Rail, Show and hide timing, Paste, Slash menu, Aside bar, Reply focus, Send focus, Hydration, Tooltips, and Faceted filters are each exercised (or consciously marked N/A) for the surfaces this change touches.

## 4. Attach evidence to the PR

Attach each screenshot with the GitHub CLI, which uploads it as an asset of the PR; never commit a binary screenshot.

```bash
gh pr comment <n> --body-file body.md \
  --attach './before.png#Before: what it shows' --attach './after.png#After: what it shows'
```

`--attach` takes `<file>#<alt text>`, repeats, and needs gh 2.100 or newer (`brew upgrade gh` on an older one); it is the one place a screenshot goes. A `![alt](./before.png)` in the body is rewritten to the uploaded asset; files the body does not reference are appended.

To view an image on a private repo's PR, send gh's token to `github.com/user-attachments` alone: it answers with a redirect to a signed URL, which you fetch with no token (`printf 'Authorization: token %s\n' "$(gh auth token)" | curl -sS -o /dev/null -w '%{redirect_url}' -H @- <attachment URL>` prints it, keeping the token out of curl's argv, then `curl -sS -o <file> '<that URL>'`).

Done when every screenshot (before+after pairs for a visual change) is on the PR.
