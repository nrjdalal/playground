# Settings and extensions

Playground keeps the code public and your own values private.
Your values (people, repos, channels, models, limits) and your own rules, skills and notes live in your extensions, git folders in your data folder, never in the code.

## Settings

Every knob is a typed key with a default, read where it is used, so a change takes effect on the next read with no restart.

```bash
playground settings list                                    # every key with its default, then each value set
playground settings get <key> [--org <org>]                 # its value, as an org or you read it
playground settings why <key>                               # every change to it, with its reason
playground settings set <key> <value> --reason "<why>" [--scope <scope>]
playground settings reset <key> --reason "<why>" [--scope <scope>]
playground settings import-jobs <jobs.json> [--launch-agents <dir>] [--scope <scope>] [--dry-run]   # once, at the switch: see Ops jobs
```

- A setting is set at a scope: your GitHub login (the default) or an org's name, each its own folder in `~/.playground/extensions/` holding a `settings.json`.
  Your value wins over your org's, your org's over Playground's own in `core`, and `core`'s over the key's default.
  `core` is read-only here: it changes by a pull request to the Playground repo.
- A value that reads as JSON (`3`, `true`, `["a","b"]`) is stored as JSON; anything else is stored as text.
- Every change is one git commit in its scope's folder: its message is the reason, its author who made it (`--by <name>`, `owner` by default), so `why` is that folder's `git log`, and you can read it by hand with `git -C ~/.playground/extensions/<scope> log -p settings.json`.
- `policy.json` at the folder's root holds the settings every session reads, rebuilt on each change.
- A machine with no settings of its own runs on the defaults.

## Extensions

Your extensions hold your own items besides settings, each under a scope, a kind and a key:

- a scope is your GitHub login, an org, or `core`, Playground's own, which ships with the checkout and takes no write;
- `doc`, `learning`, `rule` and `template` hold a body of text, and a `script` holds a body or, put from a folder, its files;
- `skill` holds a skill's folder, file by file;
- `list` holds a JSON value, such as a guard list.

```bash
playground ext list [--scope <scope>] [--kind <kind>]
playground ext show <scope> <kind> <key> [--rev <sha>]
playground ext put <scope> <kind> <key> <path> --reason "<why>" [--attach <file>]...
playground ext search <words> [--kind <kind>]
playground ext import-scripts <ops-folder> <job>... --org <org> [--dry-run]   # once, at the switch: see Ops jobs
```

- `list` names every scope's items, `core`'s among them marked `readOnly`, and passes over a folder's `.gitkeep`.
- `put` writes the item's next revision from a file, from a folder for a `skill` or a `script`, or from standard input with `-`, as one commit in its scope.
- A `list` revision lands accepted.
  Any other kind lands under `proposed/`, for review, unless you write it from the dashboard yourself.
- `--attach` takes a file, repeated for more, kept under `attachments/` by the hash of its bytes; a file over 50 MB is refused.
- `search` reads each scope's accepted items, line by line, at most 50 lines.
- A value that looks like a secret (a token or a key) is refused: an extension keeps a secret's name, such as its Keychain item, never its value.

## Which scope wins

A session reads its scopes in one order: `ext.order`'s, with your login's first when the list leaves it out, each extension kept only when `ext.links` links it to the org that owns the repo it runs in or to every repo (`*`), then `core`. By default, with no `ext.order` set, that is your login's, then the linked extensions, then `core`.

- A skill, a rule or another item resolves by its name: the first scope in that order that holds the name wins, so your copy shadows the org's and the org's shadows core's.
- A setting resolves key by key in the same order, then falls to the key's default.
- A list is the union of every scope's copy, so a guard reads every entry any scope adds.
  Arrays join item by item and objects key by key, while a single value such as the terms' `probe` keeps the first scope's, and core is read last, so an org's list holds only the items it adds and leaves each single value to core.

`playground ext which <skill> [--repo <dir> | --org <org>]` prints the copy a session in that folder (or a repo of that org) loads, and `playground ext why <skill> [--repo <dir> | --org <org>]` prints it with its scope and each scope whose copy it shadows.

## A Playground skill is an Agent Skill

Each skill in an extension is an [Agent Skill](https://agentskills.io/specification): a folder holding a `SKILL.md` whose frontmatter gives the two required fields, `name` (the folder's name) and `description` (what it does and when to use it), with reference files under `references/`, runnable code under `scripts/` and static files under `assets/`.
The Claude Code keys a skill needs beside the spec's (`hooks`, `disable-model-invocation`, `user-invocable`, `argument-hint`, a fork's `context`, `disallowed-tools` and `background`) stay where Claude Code reads them, and the skills check refuses any other key.

## From the terminal

`playground ext` and `playground settings` read and write the folders themselves, so they need no dashboard running; the dashboard's own calls take the same lock, so two writes never land at once.

## How sessions read it

Sessions and their guards read files, never the database, so a stopped database changes nothing for a running session.
They read the extensions, `extensions/` in the data folder: one git folder per scope, your GitHub login's and each org's, beside two files every write derives at the root.

- `<scope>/settings.json`, the settings set at that scope.
- Each accepted item in its scope's folder: `rules/<key>.md`, `skills/<key>/` with the skill's files, `lists/<key>.json`, `scripts/<key>/` for a script added from a folder, and the same for docs, learnings and templates.
- `policy.json` at the root, the settings as a session with no org reads them and as each org's session does.
- `hooks/<list>.json` at the root, each guard's list: every scope's `lists/<list>.json` together, yours, each org's and core's.
- `login` at the root, the login `playground ext init` wrote, which names your own scope.

`core`, Playground's own scope, is read from `extensions/core/` in your checkout and never written.
Each write lands in its scope's folder as one commit whose author is who asked and whose message is the reason, so `git -C <data folder>/extensions/<scope> log` lists that scope's history.
Each file is written under a temp name and renamed into place, so a session never reads a half-written file.
The root existing is what says a machine has extensions, so a machine with them never falls back to the lists in its checkout.

A root that lacks a guard's list refuses that guard's calls, so a guard never runs without its list.
On a new machine, seed the guards' lists from the checkout:

```bash
playground ext import --from-tree extensions/core/lists   # the guards' list files, into your login's lists
```

A script reads a file of the extensions through their reader, a path at the root or under a scope:

```bash
bun packages/scripts/src/playground/rendered.ts hooks/release-owners.json
```

| Exit | Meaning                                                              |
| ---- | -------------------------------------------------------------------- |
| 0    | It prints the file's path.                                           |
| 2    | The extensions lack the file; the refusal names how to write it.     |
| 3    | This machine has no extensions, so the script takes its own default. |

A script reads one setting the same way, as JSON, its default when this machine has no extensions, exit 2 when the set cannot be trusted:

```bash
bun packages/scripts/src/playground/setting.ts factory.repo   # "owner/name"
```

## A worked example

An org's extension is a private repo under its owner's GitHub login, `<login>/playground-<org>`, cloned to `extensions/<org>/`, so a session in one of the org's repos loads its skills beside core's and its lists join every guard's.

- `skills/<name>/`: the org's skills, each with its own `tests/`, which the repo's `bun run test` runs.
- `rules/channel.md` and `lists/glm-refused-sources.json`: one rule and one guard list.
- `settings.json` as `{}`, so the org runs on the defaults until it sets a key.
- A pre-commit hook that runs gitleaks, so no secret lands in a commit.

`playground ext list --scope <org> --kind skill` names its skills.

## Review

A setting changes at once with its reason, and so does a list.
A new revision of prose (a rule, a skill, a doc, a learning, a script or a template) written from the terminal lands under `proposed/`, and sessions keep reading the accepted one until it is accepted; your own edits from the dashboard apply at once.
A revision is the commit that wrote it, named by its sha.

```bash
playground ext score <scope> <kind> <key> <sha> <0-5> --reason "<why>" --by <reviewer>
playground ext accept <scope> <kind> <key> <sha> --reason "<why>"
playground ext reject <scope> <kind> <key> <sha> --reason "<why>"
```

- A score below 5 is recorded as a commit of its own and leaves the proposal for a later revision or another score; a 5 accepts it.
- An accepted proposal moves out of `proposed/` over the accepted copy, and sessions read it at once.
- `accept` is your own call, so it takes no `--by` but yours, and `reject` removes the proposal.
- Each judges only the proposal the sha names: one rewritten since is refused, so read it again first.
- Each decision is a commit whose trailers name the verdict, the score and the reviewer, so `playground ext why` lists it beside each revision.
- Every call from the terminal acts as you, so the name given with `--by` is recorded for the history, not checked.

## History

```bash
playground ext why <scope> <kind> <key>                         # every commit that wrote or judged it, with its reason
playground ext why <skill> [--repo <dir> | --org <org>]         # the copy a session loads, and each scope it shadows
playground ext diff <scope> <kind> <key> --from <sha> --to <sha>
```
