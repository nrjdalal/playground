# Settings

## The user menu

The square with this Mac's initials, at the right end of the toolbar beside every page, is the user menu. In the Console it is the card at the bottom of the sidebar, its top line naming this Mac and its second the Claude account your usage numbers come from. Click it to open the menu:

- **Auto-hide tab bar** shows first, in the Dashboard on a wide screen: untick it to keep the tab bar shown.
- **Update now** shows next, in the Dashboard only, while an update is available (see below).
- **Settings** opens the Settings page.
- **Console** opens the console, when your role reaches it.
- **Sessions** lists every Claude Code and Codex session Playground has run, live and past ([the Dashboard](/docs/dashboard) says how to list every one on this machine).
- **Documentation** opens these pages.
- **Feedback** opens the feedback board in a new tab, when one is set up.
- **Log out** shows in the Console only, and signs you out.

## The Settings page

`/dashboard/settings` holds one section for each thing you can set up.
Open it from the user menu, or from the Settings square after Apps in the bar beside every page.
On the hosted Yard it shows Remote alone, under the line "Read-only on Yard: send from your Mac", since pairing is the one change Settings takes from there.

### Things to fix

While something Playground needs is missing on this Mac, or an optional row has a button that fixes it (such as **Set up the web address** or **Trust the certificate** for portless), Settings lists it under **N things to fix** with the same rows as **Let's check this Mac**, each with the button that fixes it, and **Re-check**; the section goes once every one is fixed.

### Accounts

Accounts lists every Claude account and GLM key your sessions spend: a Claude account by its label or email, a GLM key by its label, each saying whether its token is kept, and Logged in on the one Claude Code is logged in as.
Each Claude account has an **Own account** switch: turn it on for your personal account, and new sessions go to it at a fifth of its share until its week resets (or its plan ends) within a day, so its week is still spent before it resets; the switch sets `own` on its row in `usage.accounts`.
Accounts are kept in your settings (`usage.accounts`), so a machine needs a GitHub login and its settings set up first: until then the section reads **Your settings aren't set up yet** over **Set up settings**, which names the private repo it reuses or makes on GitHub and sets it up once you confirm, and **Add account** stays off ([Where to start](/docs#where-to-start) gives the order).

#### Add an account

Add as many Claude and GLM accounts as you like.
On this page, **Add account** takes the provider.
A Claude account takes its email (and an optional label), then three steps: open sign-in, which opens in a new window on a fresh profile of Chrome, Brave, Edge or Firefox (the button names the browser), deleted when the sign-in ends, so the sign-in uses the new account, not the one already signed in; sign in there with the account you are adding and approve access; then paste the code the page shows.
While Claude checks the code the dialog reads **Checking the code with Claude…**, for up to about 70 seconds; a code Claude refuses, no answer in that time, a sign-in that ended (most likely because Playground restarted) and a lost connection each say what happened over **Start again**, which opens a new sign-in.
When this Mac has none of those (Safari alone takes no fresh profile), the dialog shows the link with **Copy link**: open it in a private or guest window yourself.
The account is listed once the sign-in names the email you gave; a sign-in for another account is refused and its token dropped, and one whose account cannot be read back is listed with **account not confirmed**.
A GLM key takes its label and your Z.ai API key.
The token goes to this Mac's Keychain and is never shown again, and **Remove**, the bin on each row, takes the account off the list and its token out of the Keychain.

From a terminal, `playground accounts add --provider claude --email <email>` signs one in through Claude Code and keeps its token in the Keychain, and `playground accounts add --provider glm --label <label>` keeps a Z.ai key there under that label.
`playground accounts list` shows each with its usage and `playground accounts remove <email|label>` takes one off; no token or key is ever shown ([The playground command](/docs/cli#accounts-playground-accounts)).

### Harness

Harness shows a card for each harness Alpha can run on, Claude Code and Codex, the same cards as first run's ([Pick what Alpha runs on](/docs/install#pick-what-alpha-runs-on)), its radio on the one Alpha runs on now.
Pick the other card, and once it reads Installed and Signed in, **Switch Alpha** asks you to confirm, then sends Alpha a message in your chat asking it to write its handoff and stop; once the handoff is written, Alpha starts again on the new harness from it and the pick saves as `harness.alpha`, so a switch that stops partway leaves the setting on the harness Alpha still runs.
The section shows each step while it runs, or why it stopped.
When Alpha is not running, it starts on the new harness at once.

### Templates

Templates lists the sessions the plus on Alpha's row in the sidebar can start ([the Dashboard](/docs/dashboard)), each with its kind, its model or GLM, its effort, its account and its brief, and whether it is a **Default**, an **Edited default**, one you **Added** or a **New default**.
**Edit** opens a form of its kind and backend, then on Claude its model, effort and account (**Default**, or a Claude account from Accounts), and its brief, a file name in the data folder or `scripts/briefs`; one you added also takes a new label, while a default keeps its name.
A default's own values stay in Playground, and **Reset** puts them back.
A save keeps the whole list as it is then: a default Playground changes later reads **Edited default**, with Reset taking the new values, and a default Playground adds later shows as **New default**, and **Add** puts it in your list with your edits kept.
The plus's list starts a new default once it is added.
A save that changes nothing writes nothing.
**Add template** makes a new one, and **Remove** takes one you added away; Reset and Remove each ask first.
Each save is the same change `playground settings set sessions.templates` makes, checked the same way: a brief that is not a file name, or an account `usage.accounts` does not list, is refused, and the reason shows beside its field.
**Edit templates** at the foot of the plus's list opens this section.

### Extensions

Extensions lists every extension in the order sessions read them, first wins: one card each with its place, name and repo, the orgs it is linked to (or everywhere), its skills, rules and lists counted, and when it last synced.
Before your settings are set up the section holds no extensions and shows the same **Set up settings** step as Accounts.
Drag a card by its handle, or focus the handle and use Space and the arrows, to change the order; core, built into Playground, stays last and locked.
A chip's cross unlinks an org, **+ org** links one (or `*` for every repo), and your login's extension is linked everywhere and stays so.
Each card's menu holds **Sync now**, **Open on GitHub**, **Why…** (which extension a session in a repo of an org takes a skill from, and the copies it hides) and, on every card but your login's, **Remove**, which takes it out of the order, links and repos while its folder stays.
**Add extension** takes a name (a-z, 0-9 and -), a repo or none (your login's `playground-<name>`) and its links.
As you type it checks GitHub, making nothing: a repo that is there reads whether it is private and how many skills its `skills/` holds, and one that is not reads that it will be created, private, which a confirm names again before it is made.
Each of these is the same change `playground ext add|order|link|unlink|remove|sync|why` makes, and the check is `playground ext add --dry-run` ([Settings and extensions](/docs/extensions#extensions)).

Below them, **Bundled with Playground** lists each extension Playground ships in its own checkout under `extensions/`, Slack and WhatsApp today, each off until you turn its switch on.
One that is on gives its skills to the sessions started after that, read after your extensions and before core, and one that is off loads none.
The switch sets `ext.bundled` at your login's scope, so the group shows once your settings are set up ([Settings and extensions](/docs/extensions#which-scope-wins)).
WhatsApp's card also holds its two numbers, **Device number** (`wa.device`, the spare number it links) and **Your number** (`wa.owner`, the one it answers), each `+` and 8 to 15 digits; Save writes each field you typed into at your login's scope, and a saved number shows by its last 4 digits alone, so an empty field keeps it.

### Privacy

Privacy holds two settings: **Names you go by**, your first name and handles, lowercase and separated by commas (`owner.names`, which the trace count and the inbox gate read), and **Private archive repository**, as owner/name, whose links count as private history (`factory.archiveRepo`, which the trace count and the leak guard read).
**Save** writes each field that holds a value, and each one you cleared, at your login's scope, so it also rebuilds a settings file a guard could not read; a value the setting refuses shows under its field.
A name that is one word, such as a first name alone, also matches a made-up name or a common word, so after a Save each one shows under **Names you go by** with the tracked files the trace count finds it in; the save still goes through.
Until both are set, the trace count counts nothing, and a session that runs it asks you, through its lead, to fill them in here.
Before your settings are set up the section shows the same **Set up settings** step as Accounts.

### Jobs

Jobs lists every ops job Playground ships and each org's own job, A to Z: its name, what it does, when it runs, and whether its value is the default, set in your settings or set in an org's settings.
Its switch saves at the job's scope: for a job Playground ships, its `enabled` field alone at your login's scope, so the job keeps the command and schedule Playground ships; for an org's own job, its row at that org, and the runner starts or stops it on its next pass.
A job with a config shows it in a box you edit, with the job's last refusal of it in red, and **Save** writes it at once; [Change a job's config](/docs/jobs#change-a-jobs-config) has the rest.
When you approve an Inbox guard card that turns a job on or off or gives it a new config, the list reads again with no reload.
Before your settings are set up the section shows the same **Set up settings** step as Accounts; [Ops jobs](/docs/jobs) has the rest.

### Remote

Remote pairs one browser with this Mac, so sending from the hosted Yard can count only what that browser signs.

1. On the hosted Yard, open Settings and press **Pair** under Remote. The browser makes its own key, which never leaves it, sends its public half to this Mac and shows the key's fingerprint.
2. On this Mac, open Settings: the pair request shows under Remote with the same fingerprint. Press **Approve** only if the two match.

One key is paired at a time: pairing another browser replaces it, and **Revoke** removes it, so a lost device can sign nothing more.
Once paired, that browser can send a message and answer the Inbox from Yard ([From the hosted Yard](/docs/dashboard#from-the-hosted-yard)).
Under the key, this Mac lists the last 20 writes from Yard that your paired key signed: when, how it answered, the key's fingerprint and which kind of write, a card your Mac kept for itself included.

## From the terminal

`playground settings` reads and changes your settings from a terminal, each change with its reason ([Settings and extensions](/docs/extensions#settings)).

## Updates

When the branch this copy follows (`main` or `canary`) has new changes, the user menu's square wears a green dot, and the menu shows **Update now** at its top, under Auto-hide tab bar on a wide screen.

**Update now** sends that update to the dispatcher as a message from you, then opens your chat. On the `live.branch` branch, which updates itself on a schedule, the message asks for the update now; on any other branch it carries the update and how to take it. The app never updates by itself.

## If the app restarts

When the app restarts, for example after an update, the page waits for it to come back and keeps you signed in. There is no sign-in window: a visit with no session signs you back in as this Mac's owner. If the app stays down for more than a short time, the page says something went wrong, with **Try again**.
